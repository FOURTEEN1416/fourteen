3. P0 严重问题 必须立即修复

3.1 MiMo TTS API Key 硬编码在配置文件中
安全配置
config/system.yaml 中 MiMo TTS 的 API Key 以明文形式存储，任何能读取配置文件的人都能获取。
config/system.yaml: mimo: api_key: "sk-c2tmjxs4acn2d5z0fyj0mi9zj516grd8zryt8upf6nnyhks7" # ← 明文密钥 # 应改为从环境变量读取: mimo: api_key: "${MIMO_TTS_API_KEY}"
将 API Key 移至 .env 文件，通过环境变量注入，system.yaml 中仅保留占位符。
3.2 content_safety.py 缺少 import time，安全日志完全失效
Bug安全
content_safety.py 第 108 行使用 time.time()，但文件未导入 time 模块。运行时抛出 NameError，被 except Exception: pass 静默吞没。结果是所有安全拦截事件永远不会被记录到安全日志中。
security/content_safety.py: # 第 1-11 行导入列表中没有 import time # 第 108 行: log_entry = {"timestamp": time.time(), ...} # ← NameError # 第 111 行: except Exception: pass # ← 静默吞没 NameError，安全审计形同虚设
在文件顶部添加 import time；将 except Exception: pass 改为 except Exception as e: logger.error(f"安全日志写入失败: {e}")。
3.3 PII 脱敏器返回值中保留原始 PII 明文
安全
pii_anonymizer.py 的 anonymize 方法返回的 detected 列表中，每项包含 "original" 字段（原始 PII 值）。如果此列表被日志记录或持久化，脱敏就失去意义。
security/pii_anonymizer.py: # 第 49-53 行: detected.append({ "type": pii_type, "original": original, # ← 原始 PII 明文！ "replacement": replacement, "start": start, "end": end, })
从返回值中移除 "original" 字段，或仅在 debug 模式下包含，或对 original 做部分遮蔽处理。
3.4 MiMoTTSProvider 初始化必崩（AttributeError）
Bug
voice/mimo_tts_provider.py 第 90 行引用 self._api_base，但类中只定义了类属性 API_BASE（无下划线前缀），没有 _api_base 实例属性。当 base_url 参数为 None 时，右侧 self._api_base 在赋值前被读取，直接抛出 AttributeError。
voice/mimo_tts_provider.py: # 第 37 行: 类属性 API_BASE = "https://api.xiaomimimo.com/v1" # 第 90 行: 构造函数 self._api_base = base_url if base_url else self._api_base # ↑ 当 base_url=None 时, self._api_base 不存在 → AttributeError
改为 self._api_base = base_url or self.API_BASE。
3.5 config_manager.py env 变量未定义导致启动崩溃
Bug
observability/config_manager.py 第 85 行中，env 变量仅在 system.yaml 文件存在时定义。若配置文件不存在或未安装 yaml 库，第 86 行引用 env 会抛出 NameError，导致整个应用无法启动。
observability/config_manager.py: # 第 83-86 行: if HAS_YAML and system_yaml.exists(): env = data.get("env", "prod") # ← 仅在此块内定义 ... env_file = system_yaml.parent / f"system_{env}.yaml" # ← env 可能未定义
在 if 块之前初始化 env = "prod" 默认值。
3.6 Nginx 静态文件路径不匹配，前端部署后 404
部署
deploy/nginx.conf 配置 root /var/www/ai-girlfriend，但 deploy.sh 将前端构建结果复制到 /opt/ai-girlfriend/frontend/dist。两个路径不匹配，部署后前端页面全部 404。
deploy/nginx.conf: root /var/www/ai-girlfriend; # ← 配置路径 deploy/deploy.sh: rsync ... /opt/ai-girlfriend/frontend/dist/ # ← 实际部署路径 deploy/nginx-ai-girlfriend.conf: root /opt/ai-girlfriend/frontend/dist; # ← 另一个配置文件的路径
统一使用一个路径。建议将 nginx.conf 的 root 改为 /opt/ai-girlfriend/frontend/dist，或删除其中一个 nginx 配置文件。
3.7 deploy.sh npm ci --only=production 导致前端构建失败
部署
deploy.sh 第 47 行使用 npm ci --only=production，此标志会跳过 devDependencies。但构建前端需要 typescript、vite 等 devDependencies，会导致 npm run build 失败。
deploy/deploy.sh: npm ci --only=production # ← 跳过 devDependencies npm run build # ← 缺少 vite/typescript, 构建失败
改为 npm ci（不加 --only=production），或分两步：先 npm ci 再 npm run build，最后 npm prune --production。
3.8 Nginx SSL 配置对裸 IP 地址不可行
部署安全
nginx.conf 配置了 SSL 证书路径 /etc/letsencrypt/live/139.199.199.174/，但 certbot 无法为裸 IP 地址签发 SSL 证书。HTTP→HTTPS 强制重定向会在 SSL 未配置时导致网站完全不可访问。
deploy/nginx.conf: # 第 24 行: HTTP→HTTPS 强制重定向 return 301 https://$host$request_uri; # 第 33-34 行: SSL 证书路径（对 IP 不可能存在） ssl_certificate /etc/letsencrypt/live/139.199.199.174/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/139.199.199.174/privkey.pem;
使用域名替代 IP 地址，或暂时注释掉 SSL 重定向，仅使用 HTTP。
3.9 加密默认关闭 + Debug 模式开启
安全配置
config/system.yaml 中 encryption_enabled: false 且 debug: true。生产环境下，所有 PII 数据以明文存储，且 debug 模式可能泄露堆栈信息。加密管理器在密钥缺失时静默降级为明文模式，仅记录 warning 日志。
config/system.yaml: debug: true # ← 生产环境不应开启 encryption_enabled: false # ← PII 明文存储 security/encryption.py: # 第 37-38 行: 密钥缺失时静默降级 if not key_hex: self.enabled = False # ← 静默降级, 无异常
生产配置中设置 debug: false, encryption_enabled: true，并提供有效的加密密钥。加密失败时应抛出异常而非静默降级。
3.10 SSRF 防护可被重定向绕过
安全
character_crawler_tool.py 的 _try_fetch 方法使用 allow_redirects=True，但仅校验初始 URL。服务端 302 跳转到内网地址（如 http://127.0.0.1）可绕过 _BLOCKED_HOSTS 检查。此外，IP 编码绕过（十进制/十六进制/八进制）和 DNS Rebinding 也未防护。
tools/builtin/character_crawler_tool.py: # _try_fetch 使用 allow_redirects=True, 仅校验初始 URL resp = self._session.get(url, allow_redirects=True, ...) # ↑ 服务端 302 → http://127.0.0.1 → 绕过检查 # _BLOCKED_PREFIXES 用字符串前缀匹配: _BLOCKED_PREFIXES = ["127.", "10.", "192.168.", "172.16.", ...] # ↑ 无法拦截 2130706433 (十进制) 或 0x7f000001 (十六进制)
禁用重定向（allow_redirects=False）并手动验证每个跳转目标；使用 ipaddress 模块解析 IP 而非字符串前缀匹配。

4. P1 高优先级问题 需尽快修复

4.1 双编排器大量代码重复
架构
orchestrator.py（根目录）和 orchestrator/optimized_orchestrator.py 存在大量重复代码：相同的会话锁逻辑、相同的 LLM 调用流程、相同的人格注入逻辑。两个类同时被使用，维护时容易遗漏同步更新。
# orchestrator.py (根目录, ~600行) class Orchestrator: async def process_message(self, user_id, text, character_id=None): # 会话锁 + LLM调用 + 人格注入 ... # orchestrator/optimized_orchestrator.py (~800行) class OptimizedOrchestrator: async def process_message(self, user_id, text, character_id=None): # 几乎相同的逻辑, 但有额外优化 ... async def process_message_stream(self, ...): # 又复制了一遍 process_message 的逻辑
合并为单一编排器，通过策略模式或配置开关区分行为。process_message_stream 应复用 process_message 的核心逻辑。
4.2 安全层反向依赖 API 层
架构
security/content_safety.py 在函数内部延迟导入 from api.deps import deps，造成安全层（底层基础设施）反向依赖 API 层（上层应用），违反分层架构原则，存在循环导入风险。
security/content_safety.py: # 第 99-100 行 (函数内延迟导入): from api.deps import deps # ← 安全层 → API层 (反向依赖!) from observability.logging_setup import get_user_id
通过依赖注入将 deps 传入安全模块，或使用事件/回调机制解耦。
4.3 语音层反向依赖 shisi 领域层
架构
voice/tts_manager.py 导入 from shisi.voice.emotion_tts import EmotionVoiceMapper，使通用语音基础设施层反向依赖 shisi 领域层。若 shisi.voice 反向引用 voice，即形成循环依赖。
voice/tts_manager.py: # 第 163 行: from shisi.voice.emotion_tts import EmotionVoiceMapper # ↑ 通用层 → 领域层 (反向依赖)
将情感映射逻辑下沉到 voice 基础层，或通过依赖注入传入。
4.4 封装破坏：直接访问私有成员
架构
knowledge_service.py 直接读写底层服务的 _retrievers、_use_bm25、_chunk_counts 等私有属性。persona_service.py 调用 PersonaEngine 的多个私有方法（_build_emotion_layer 等）。适配层穿透底层内部实现，任一重构都会破坏适配层。
shisi/application/knowledge_service.py: # 第 171-176 行: self._service._retrievers[role] = retriever # ← 直接操作私有属性 self._service._use_bm25 = True self._service._chunk_counts[role] = len(chunks) retriever._chunks.extend(chunks) # ← 穿透到 retriever 内部
为底层服务添加公开 API 方法，适配层仅通过公开接口操作。
4.5 LLM 安全分类器自身可被注入
安全
content_safety.py 和 prompt_injection.py 都将用户原始文本直接拼入检测 LLM 的 prompt 中。恶意用户可构造文本欺骗安全分类器返回 "normal" 分类，从而绕过安全检查。
security/content_safety.py: # 第 162-166 行: prompt = f"文本：{text[:500]}\n" # ← 用户输入直接拼入 security/prompt_injection.py: # 第 101-103 行: prompt = f"用户输入: {text}\n" # ← 检测器自身可被注入
使用结构化的 prompt 格式（如 JSON 包装），对用户输入进行转义，或使用专门的安全分类模型而非通用 LLM。
4.6 线程安全问题：共享 Session 和限流器
安全Bug
character_crawler_tool.py 的 _session 是类级共享 requests.Session，非线程安全。base_tool.py 的 _check_rate_limit 读写 _call_times 字典无锁保护，并发场景下限流失效。
tools/builtin/character_crawler_tool.py: _session = requests.Session() # ← 类级共享, 非线程安全 tools/base_tool.py: # 第 147-155 行: def _check_rate_limit(self, key): now = time.time() self._call_times[key].append(now) # ← 无锁, 并发竞态
使用 threading.Lock 保护共享状态，或改用 asyncio.Lock（若在异步上下文中）。
4.7 prompt_injection 检测 fail-open 不一致
安全
prompt_injection.py 的 detect 方法中，LLM 检查在普通异常时返回 False, 0.0（fail-open，放行），超时时返回 True, 0.6（fail-closed，拦截）。不一致意味着大部分 LLM 故障情况下注入检测被绕过。此外 sanitize 方法在 LLM 检测到注入但规则未命中时，文本原样返回，净化无效。
统一 fail-open/fail-closed 策略；sanitize 方法在 LLM 判定有注入时，应拒绝处理或使用 LLM 进行净化重写。
4.8 重复实例化导致状态分裂
架构
shisi/api/registry.py 创建 FavoriteManager() 和 ForwardManager()，而 ShisiMemoryService.__init__ 又各自 new 了一份。两套实例独立存在，收藏/转发状态可能不一致。
shisi/api/registry.py: # 第 79-80 行: favorite_mgr = FavoriteManager() forward_mgr = ForwardManager() shisi/application/memory_service.py: # 第 86-87 行: self._favorite_mgr = FavoriteManager() # ← 另一个实例! self._forward_mgr = ForwardManager() # ← 另一个实例!
通过依赖注入共享同一实例，或使用单例模式。
4.9 日志系统无 PII 脱敏
安全
observability/logging_setup.py 的 RingBufferHandler.emit() 直接记录原始日志内容，不做 PII 过滤。/api/logs 端点暴露的日志可能包含手机号、密码等敏感信息。
在日志 handler 中集成 PII 脱敏器，对所有日志消息进行过滤后再存储。

5. P2 中优先级问题 计划修复

5.1 tracing.py 内存泄漏
Bug
_active_traces 字典无 TTL 和清理机制。若 end_trace 未被调用（因异常或遗漏），trace 数据永久驻留内存。长期运行的服务会逐渐耗尽内存。
添加 TTL 清理机制，或使用 weakref + 定期清理。
5.2 异步/同步接口不统一
架构
ShisiMemoryService 同时提供同步 retrieve_context 和异步 retrieve_context_async，方法命名不一致。ToolDispatcher.dispatch 完全同步，无法接入异步工具。工具体系与语音体系缺乏统一的异步执行路径。
统一为 async 接口，同步调用通过 asyncio.to_thread 包装。
5.3 多处异常被静默吞没
Bug
多个文件中存在 except Exception: pass 模式，吞掉所有错误信息：
文件行号问题
tts_manager.py168情感映射失败无任何日志
mimo_tts_provider.py255/266/277降级失败原因被吞
content_safety.py111安全日志写入失败被吞
registry.py88except (ImportError, Exception) 过宽
将 pass 替换为 logger.error(f"...") 记录错误信息。
5.4 前后端版本号不一致
配置
三处版本号互相矛盾：
位置版本
frontend/package.json2.0.0
pyproject.toml3.0.0
app_factory.py FastAPI title2.0
统一版本号，建议使用脚本同步。
5.5 依赖管理不一致
配置
requirements.txt 和 pyproject.toml 对同一依赖的版本要求不同：httpx (>=0.27.0 vs >=0.26.0)。requirements.txt 包含 structlog 和 cryptography 但 pyproject.toml 未列出。pyproject.toml 同时配置了 black + isort + ruff，工具冗余。
以 pyproject.toml 为唯一依赖来源，删除 requirements.txt 或自动生成。
5.6 RingBufferHandler 性能问题
Bug
logging_setup.py 的 RingBufferHandler 使用 list.pop(0) 移除旧记录，这是 O(n) 操作。在高频日志场景下会严重影响性能。
改用 collections.deque(maxlen=capacity)，O(1) 操作。
5.7 config_manager 竞态条件
Bug
config_manager.py 的 _config 无锁保护。reload() 和 save() 修改 _config 时，其他线程可能正在读取，导致数据不一致。_deep_merge 使用浅拷贝，嵌套 dict 仍共享引用。
添加 threading.RWLock 或 asyncio.Lock 保护配置读写。
5.8 两个冲突的 systemd service 文件
部署
deploy/ 目录下同时存在 ai-girlfriend.service（User=www-data, 4 workers, 安全沙箱）和 ai-girlfriend-backend.service（User=root, 1 worker, 无安全沙箱），两者都定义名为 ai-girlfriend 的服务。setup.sh 安装前者，但后者存在且配置完全不同，容易混淆。
删除其中一个，或重命名以区分用途。

6. P3 低优先级问题 有空处理

6.1 相对路径硬编码
配置
persona_service.py 使用 Path("config/characters") 硬编码相对路径，非项目根目录启动时失效。mimo_tts_provider.py 的 API_BASE 和 extra_tools.py 的 Agnes-AI 配置也有硬编码。
基于 __file__ 或项目根常量构建绝对路径。
6.2 BaseTool.parameters_schema 可变类属性
架构
base_tool.py 第 37 行 parameters_schema: dict = {} 是类级可变默认值，Python 经典陷阱。
改为 field(default_factory=dict) 或类方法返回。
6.3 prompt_injection 线程池频繁创建
架构
prompt_injection.py 的 _llm_check 每次调用都创建新的 ThreadPoolExecutor(max_workers=1)，与 content_safety.py 使用共享线程池的做法不一致。
改用模块级共享线程池。
6.4 registry.py 残留废弃代码
架构
第 108-109 行注释掉 _mount_v2_routes 调用但保留函数定义（第 139-147 行），标记"2026-05-31 废弃"。
彻底删除废弃代码。
6.5 setup.sh sed 替换无效
部署
setup.sh 第 172 行 sed 替换 unique-you.example.com，但 nginx.conf 中已硬编码 139.199.199.174，不存在该字符串，sed 替换是空操作。
修正 sed 替换的目标字符串，或改用环境变量注入域名。
6.6 mypy 忽略大量模块
配置
pyproject.toml 中 mypy overrides 对多个模块设置 ignore_errors = true，类型检查形同虚设。
逐步修复类型错误，移除 ignore_errors 配置。

7.2 双编排器问题

项目同时维护 orchestrator.py（根目录，约 600 行）和 orchestrator/optimized_orchestrator.py（约 800 行），两者共享约 70% 的代码逻辑但独立维护。api/deps.py 中 deps 单例使用的是 OptimizedOrchestrator，但 orchestrator.py 仍被 main.py 和测试引用。这种"新旧并存"的模式导致：

  • 修复一个 bug 需要同时改两处，容易遗漏
  • 两者的行为差异不明确，缺乏文档说明何时用哪个
  • process_message_stream 又复制了 process_message 的逻辑，三处重复

9. 部署脚本审查

部署流程: Windows 桌面 → deploy_ai_girlfriend.bat → deploy_ai_girlfriend.ps1 │ ├─ git archive → scp → remote_deploy.sh (服务器端) │ ├─ pip install │ ├─ npm run build (前端构建) │ ├─ systemd restart │ └─ nginx reload │ └─ setup.sh (首次安装) ├─ git clone (会失败! 服务器无法直连 GitHub) ├─ npm ci --only=production (会失败! 缺 devDependencies) ├─ install nginx.conf (root=/var/www/ai-girlfriend) └─ install ai-girlfriend.service 问题标记: ✗ git clone 会失败 ✗ npm ci --only=production 会导致 build 失败 ✗ nginx.conf root 路径与 deploy.sh 部署路径不匹配 ✗ SSL 证书对裸 IP 不可行 ✗ 两个冲突的 systemd service 文件 ✗ sed 替换目标是空操作

部署脚本问题总结：setup.sh 适用于首次安装，包含多个会导致失败的 bug；remote_deploy.sh 用于增量部署但缺少前端文件部署步骤。两个脚本的 Nginx 路径配置互相矛盾。建议以 remote_deploy.sh 为基础，修复路径和依赖问题后统一使用。
