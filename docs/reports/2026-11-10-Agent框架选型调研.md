### 1.1 与我们的目标架构逐项对照

| 我们的目标 | Harness 现状 | 判断 |
|---|---|---|
| 一个发声者 | agent loop 是插件，一轮 turn 由同一 loop 产出 | ✅ 天然一致 |
| 能力即工具 | `ctx.tools` 注册 + MCP | ✅ 一致，且 MCP 能接我们 Python 能力 |
| 事件日志 | append-only SessionEvent + "model-visible means logged" | ✅ 就是我们想要的 |
| 触发器只投事件 | `schedule_*` 把 prompt 当「用户消息」投进 session | ✅ 正是「不再由调度器写文案」 |
| 灵魂可替换 | system-prompt 组装可换 + 预设按 session | ⚠️ 可换，但没有「人格块」原语，需自己做 |
| 承诺账本 | 无 | ❌ 需自建（可做成工具 + 投影） |
| 微信通道 | 无（浏览器/桌面/SDK/ACP） | ❌ 需自建适配 |
| 记忆/画像/知识库 | 只有通用 session 与 MCP | ❌ 需自建（Python 侧） |

**结论：Harness 覆盖了「循环 + 会话日志 + 调度 + 工具」这四层，正好是我们最想少写的那部分；但灵魂/记忆/通道仍然必须自建。**

## 2. 关键权衡：它是 Node 运行时，我们是 Python 产品

这是采用 Harness 的唯一硬约束，必须说清楚：

- Harness 是 **TypeScript/Node**；官方 Python SDK 是**子进程 SDK**（stdio JSON-RPC 启动 `dsh --profile sdk`），不是把 loop 嵌进 Python。
- 因此采用它意味着：**Python 产品 + Node sidecar 两套运行时**。
- 我们的核心资产（三层记忆、画像、RAG、出站守卫、微信 iLink/silk、APScheduler 节奏闸）都在 Python；接入方式是 **MCP server**（Harness 侧 `mcp-client` 已具备）。
- 部署形态变化：4 worker 的 FastAPI 之外，多一个（或每用户一个）Node 进程；需要评估并发、内存、重启、可观测性。
- **v0.1 preview + 明确 breaking changes**：生产稳定性风险必须计入。

反过来，它带来的收益也很实在：会话日志、turn/step 语义、schedule-to-session、工具管线（`tools/pre-execute → execute → post-execute`）、MCP、DeepSeek V4 适配，都是现成的。

|---|---|---|---|---|---|

| **Pydantic AI（Python loop）** | ★★★☆（loop/typed tools；无日志/调度/人格） | 低（单运行时） | 中 | 稳（MIT，成熟） | 保底方案 |
| OpenAI Agents SDK | ★★★（loop/sessions/guardrails） | 低 | 中 | 稳 | 备选 |
| LangGraph | ★★（图编排） | 低 | 高 | 稳 | 过度设计 |
| Agno | ★★★（storage/scheduling，但转向 AgentOS 平台） | 中高 | 高 | 中 | 不推荐 |
| Letta | ★★★（persona block 最佳） | 高（独立服务） | 高 | 中 | 只借模式 |
| smolagents | ★★（CodeAgent 执行模型写的 Python） | 低 | 中 | 中 | 安全面不适合 |

- Harness：官方自研，天然适配；

- MS Agent Framework / AgentScope / OpenAI SDK 的 LiteLLM·JS 路径：有已知 400。

## 4. 三条可执行路线

### 路线 A：直接采用 Harness 作为「大脑运行时」

```
微信 ⇄ Python 适配层（通道/记忆/守卫/灵魂渲染）
              ⇅ MCP（我们的能力：memory / reminder / send_message / voice）
        dsh runtime（agent loop + session log + schedule）
```

- 优点：最大化复用官方架构；调度天然是「向 session 投消息」，碎片续话在结构上消失；DeepSeek V4 适配免费。
- 代价：Node 运行时；v0.1 破坏性变更；多租户/并发要压测；`send_message` 需由我们 MCP 工具真正投递。
- 适用：愿意把 agent runtime 作为独立服务、接受 preview 风险。

### 路线 B：借架构，不引运行时（Python 内实现同形）

- 用 Pydantic AI（或自研 loop）实现：SessionEvent 日志 + loop + `schedule` 投消息 + MCP 工具。
- 优点：单运行时，部署不变，无 preview 风险。
- 代价：session log/调度/工具管线要我们自己写（约 600–1000 行），但设计已被 Harness 验证。

### 路线 C（推荐）：**双轨 spike，用数据裁决**

| 轨道 | 内容 | 度量 |
|---|---|---|
| **A 轨** | `pip install deepseek-harness-sdk`，起 `dsh --profile sdk`；用 MCP 挂 1 个我们的工具（memory）；跑 20 轮 | 启动/单轮延迟、并发 session 数、内存、事件流能否接微信、`dsh_home` 隔离 |
| **B 轨** | Pydantic AI + DeepSeek provider + 同 3 个工具 | 同上 + 集成摩擦力 |
| 共同 | 用 11-10 事故回放：一次 turn 是否产出完整一段话 | 是否消除「半句 + 半天后另半句」 |

**裁决标准**：A 轨若单轮延迟、并发与运维成本可接受 → 采用 Harness；否则走 B 轨，但把 Harness 的 session-log 语义与 schedule-to-session 形态照搬。

## 5. 重量评估与「专精化二改」路径

### 5.1 到底重不重：分档看

| 形态 | 组成 | 重量 |
|---|---|---|
| 默认 `web` profile | CLI + base bundle + Web 应用 + settings + telemetry + 40+ 工具 + shell/fs/browser/computer-use | **重**（完整 agent 工作区） |
| `sdk-minimal` profile | 独立树，**不含 base/web/settings/telemetry/skills/subagents**；只留 SDK JSON-RPC + 单模型适配器 + agent core + MCP + JSONL 会话 + shell/fs | **中轻**（仍保留 coding agent 的 shell/fs） |
| 我们可做的 `companion` profile | 以 sdk-minimal 为底，**patch 掉 shell/fs/subprocess/image/working-directory**，只留 loop + session + MCP + schedule | **轻**（接近纯 agent loop + 状态） |

硬指标：`@deepseek-ai/dsh` 包本体 76KB / 20 文件，但依赖 **90 个包**；**Node ≥ 24.9.0**；仓库 53 个包域 / 360MB（monorepo，不是安装体积）。

> 结论：**默认形态确实重；但它的 profile/patch 机制允许裁到「loop + session + MCP」这一层**。真正不可裁的成本是：Node 24 运行时 + Cordis 插件内核 + 跨语言边界。

### 5.2 二改的三条路径（推荐第 1 条）

| 路径 | 做法 | 代价 | 建议 |
|---|---|---|---|
| **① 组合式专精（推荐）** | 自定义 profile + `cordis.patch.yml` + `dsh plugin` 装外置插件；不改 monorepo | 只需写 TS 插件/MCP | ✅ 主路径 |
| ② 外置插件 | 写 `dsh-plugin-*`（persona / commitment / wechat-send），挂到 `ctx.*` 扩展点 | TS 开发 + 版本跟随 | ✅ 配合① |
| ③ Fork 整个仓库 | 直接改 core/agent-loop 等 | 跟随 v0.1 breaking changes 的成本极高 | ❌ 除非核心语义必须改 |

**companion profile 草案**：

```
base: sdk-minimal（显式树，不继承 base）
patch out: shell / fs / subprocess / read_image / working_directory / browser / computer-use
patch in:
  - dsh-mcp-client  → 我们的 Python MCP servers（memory / reminder / send_message / voice / knowledge）
  - dsh-tool-schedule → 主动跟进的定时投递（prompt 作为用户消息进 session）
  - 自定义 system-prompt 插件 → 按 (user_key, character_id) 渲染 SoulProfile
  - 自定义 SessionPersistence（可选）→ 落我们的 SQLite，而不是 JSONL
system prompt: DSH_SYSTEM_PROMPT 或插件渲染（per-session，可热换）
```

## 6. 结论（修正后）

1. **DeepSeek 有官方 Harness，而且它的架构（插件内核 / append-only 会话日志 / loop 即插件 / schedule 向 session 投消息 / 能力 seam / MCP）就是我们要的「单一个体」形状。**
2. 唯一硬约束是 **Node 运行时 + v0.1 preview**；我们的灵魂/记忆/通道仍在 Python，需要 MCP 桥。
3. 因此不建议「拍脑袋整体搬迁」，也不建议「无视它自己造」——**先双轨 spike，用延迟/并发/稳定性数据决定**。
4. 无论选哪条，**SoulProfile / 承诺账本 / 线程状态 / `send_message` 唯一出站**这四件仍然要我们自己做，因为两个候选都不提供。
