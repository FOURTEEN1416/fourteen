# 让 AI 聊天「像人」的插件与方案生态调研

> 调研日期：2026-10-27
> 调研范围：SillyTavern 扩展生态、AstrBot / MaiBot / LangBot / NoneBot 等中文 IM 机器人生态、DeepSeek Harness（DSH）插件生态、开源自托管 AI 陪伴项目、反 AI 腔提示词项目。
> 方法：GitHub-First（`gh search repos` / `gh api` 读取仓库元数据、README 与源码），不以 WebSearch 做代码仓库发现；所有关键结论附来源链接，代码结论尽量落到具体文件与行号。
> 限制：本轮没有运行任何被调研项目，也没有跑本项目测试；成熟度按 GitHub star、最近 push、issue 数做静态判断，不等于生产可用性。

---

## 0. 结论摘要（先看这 8 条）

1. **生态里真正有效的「拟人化」，绝大多数不是一句「请像真人一样说话」，而是把「何时说、说几条、隔多久、记住什么、状态怎么变、什么不该发」做成模型之外的系统。** 纯 prompt 方案主要集中在「语言风格 / 反 AI 腔」，而节奏、时机、状态、记忆、抑制几乎都在工程层。
2. **中文 IM 生态里机制密度最高的是 AstrBot 插件群和 MaiBot**：AstrBot 的 `group_chat_plus` 把「读空气 + 概率 + 注意力衰减 + 疲劳 + 沉默状态机 + 错别字 + 打字延迟」做成了完整管线；MaiBot 把「回复概率 logistic 模型 + 消息防抖 + 表达库检索 + LLM 断句 + 拼音错字」做成了主链前置层。两者都比 SillyTavern 扩展更接近本项目需要的「微信一对一陪伴」。
3. **DSH 本身不是拟人化方案，而是「万物皆插件」的 Agent 宿主**；它的价值在于插件可以接管宿主级定时、会话恢复、角色扮演前端与状态结算。`dsh-proactive` 是目前看到的最干净的「宿主级主动唤醒」参考实现（jitter、免打扰、每日预算、静默等待、静默收尾墓碑）；`dsh-tavern` 的「前台模型只写正文、后台模型结算变量」是降低 prompt 竞争的直接工程手段。
4. **SillyTavern 扩展生态里没有形成「拟人化/延迟/humanize」这一独立品类**：官方 `Extension-TypingIndicator` 只是 UI 上的「正在输入」动画，不产生任何延迟或节奏；社区扩展目录里更多是记忆、世界书、图像、剧情工具。真正影响「像人」的是角色卡、预设与提示词，不是扩展。想从 ST 生态抄「节奏层」，基本抄不到。
5. **主动消息的关键不是「定时发」，而是「发之前有决策、发之后有记账、没内容能静默退出」**：`dsh-proactive` 用 host 闹钟 + `proactive_reclaim` 墓碑；AstrBot `private_companion` 用「候选生成 + 时机/频率/权限/投递四道检查 + 独立 persona judge 只允许/不允许、失败即不发送」；AstrBot `proactive_chat` 用随机区间 + 未回复计数器 + 免打扰。三者可以拼成一套完整主动链。
6. **情绪/关系状态必须持久化并衰减，不能每轮让模型「重新决定心情」**：Front Porch 的 bond/trust 双层刻度与修复窗口、Persisto 的「独立 affect judge 只判涨跌不判绝对值」、companion-emergence 的 per-emotion half-life、GCP 的 attention 300s / emotion 600s 半衰期，都是可复用的工程模式。注入时只给一小段状态摘要，不要把整套规则写进 system prompt。
7. **反 AI 腔要区分「写作」与「聊天」**：`blader/humanizer`（26 条模式、盲测 16/16 偏好）与 `lieflat-less-ai-tone`（283 万字语料、26 项候选特征仅 11 项通过检验）都很有价值，但它们是「文本改写」而非「对话策略」；`lieflat` 还发现比喻、设问、排比在人类文本中反而更多，盲目按网络清单删改会误伤。它们适合做出站后处理/审稿清单，不适合作为聊天主 prompt 的主体。
8. **许可证是硬约束**：MaiBot GPL-3.0、AstrBot 及其多数插件 AGPL-3.0、Front Porch/AI Virtual Phone/dsh-tavern AGPL-3.0；`private_companion` 没有任何 LICENSE（默认版权保留）；`KouriChat` 是 DeepAnima 1.2 非商用许可且 README 明确禁止接入微信/QQ；`lieflat` 是 CC BY-NC 4.0。**机制可以学，代码不要直接并进闭源商用项目。**

## 2. 机制分类学总表

### 2.0 七层模型：人类感 = 节奏 + 时机 + 语言 + 状态 + 记忆 + 抑制 + 临场

把「像人」拆成七个正交层，比按「prompt/插件」分类更有解释力：

| 层 | 回答的问题 | 典型机制 | 主要实现位置 |
|---|---|---|---|
| **R 节奏层** | 怎么发？发几条？隔多久？ | 打字指示器、分条发送、打字延迟、错别字、防抖 | 传输层 / UI / 后处理 |
| **T 时机层** | 什么时候说？要不要主动说？ | 主动定时、随机抖动、免打扰、每日预算、读空气、注意力、疲劳、沉默状态机 | 调度器 / 决策门 |
| **L 语言层** | 说什么样的话？ | 长短句波动、口语碎片、表达库、黑话、风格学习、断句 | 检索 + prompt + 后处理 |
| **E 状态层** | 带着什么心情/关系说？ | 情绪向量、衰减、惯性、bond/trust、身体时钟、睡眠、梦境 | 状态机 + 紧凑注入 |
| **M 记忆层** | 凭什么记得？记得多牢？ | 摘要、反思、向量/BM25/图谱召回、衰减、强化、遗忘、分支隔离 | 存储 + 检索 + 工具 |
| **A 抑制层** | 什么不该发？ | 反 AI 腔、去模板、去列表、去元解释、系统标记剥除、post-draft judge | 出站守卫 / 后处理 |
| **I 临场层** | 在什么界面/身体里说？ | 角色卡、世界书、手机 UI、朋友圈、语音打断、Live2D 表情 | 前端 / 多模态 |

> **对本项目最重要的判断：** 你们历史上「硬指令堆叠互相竞争」的问题，本质是把 R/T/E/M/A 层的问题塞进了 L 层（prompt）。真正该加的不是更多「请自然」，而是把节奏、时机、状态、记忆、抑制搬到工程层，prompt 只保留「声音」和「边界」。

---

### 2.1 R 节奏层：输出节奏与消息形态

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 打字指示器 / 正在输入 | SillyTavern `Extension-TypingIndicator`；AI Virtual Phone；GCP | ST 扩展只在 generation 开始显示、结束隐藏，是纯 UI，不产生延迟；AI Virtual Phone 通过 iLink `sendtyping` 的 `status: 1/2` 表达开始/结束；GCP 由 `TypingSimulator` 真正 `asyncio.sleep` | 工程/UI |
| 分条发送 | AstrBot `proactive_chat`；`private_companion`；MaiBot；AI Virtual Phone；KouriChat | proactive_chat：正则/分段词切分，默认随机 1.5–3.5s 或 log 缩放间隔；private_companion：显式 split marker + 最大段数 + 保护 Markdown 块；MaiBot：LLM 只做断句、不改写、代码/公式 `no_split`；AI Virtual Phone：多气泡间隔 800ms；KouriChat：智能分段 + 情感化表情包 | 工程 |
| 打字延迟 | GCP；proactive_chat | GCP `TypingSimulator`：15 字/秒、0.5–3s 夹取、±30% 随机；proactive_chat `calc_interval`：random 1.5–3.5s 或 `log(word_count+1, 1.8)+0–0.5s` | 工程 |
| 错别字 / 口语瑕疵 | GCP；MaiBot | GCP：拼音同音字替换，默认 2% 概率，跳过代码/URL/短消息；MaiBot：pypinyin 同音/近调 + 词频替换，按字/词概率，类默认 `error_rate=0.3`、示例实例化 `0.03` | 工程后处理 |
| 防抖 / 等补充消息 | MaiBot；GCP；AI Virtual Phone | MaiBot 四档：自然 2/5/2/0.5s，整批 8s 上限、@ 1s 上限；GCP 静默状态机；AI Virtual Phone 由 anxiety 值线性映射追问延迟 | 工程 |
| 已读 / 输入状态 | AI Virtual Phone；SillyTavern | AI Virtual Phone 通过 iLink `sendtyping`；ST 只有本地动画，没有真实已读回执 | 工程/UI |

**关键结论：** 「分条 + 延迟」是投入产出比最高的拟人化工程，但它必须发生在**生成之后**，不能靠 prompt 让模型「请分多条回复」。模型只负责写一段完整文本，传输层负责切分与节流，才能既稳定又不破坏语义。

### 2.2 T 时机层：发言时机与主动触达

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 宿主级主动闹钟 | `dsh-proactive` | `once/every/cron/file` 四种调度；`jitter_seconds` 0–86400 随机抖动；`respect_quiet_hours` 免打扰；`min_idle_seconds` 等目标会话安静后再唤醒；每日投递预算；`proactive_reclaim` 静默收尾并折叠为 ~70B 墓碑 | 工程 |
| 随机区间 + 未回复计数 | AstrBot `proactive_chat` | 长时间无消息后随机区间触发；`{{unanswered_count}}` 注入 prompt 形成「轻微失落/想念」；免打扰时段；持久化任务；群聊先判断冷场 | 工程 + prompt |
| 读空气 + 概率 + 决策 AI | AstrBot `group_chat_plus` | 两层过滤：概率筛选 + 独立决策 AI；注意力/疲劳/时段概率共同调制；@/关键词旁路；Smart 模式合并追加消息 | 工程 |
| 注意力衰减 + 疲劳 | AstrBot `group_chat_plus` | 每个用户 0–1 注意力，指数衰减 `0.5^(elapsed/half_life)`，注意力半衰期 300s、情绪半衰期 600s；注意力溢出、候选冷却→正式冷却、对话疲劳 | 工程 |
| 沉默状态机 | AstrBot `group_chat_plus` | 连续 3 次不回复进入静默；被 @、超 600s、积累 8 条、命中兴趣关键词时退出；决策历史注入保持一致性 | 工程 |
| 回复概率模型 | MaiBot | 8 特征 logistic：是否@、是否@他人、问号、纯媒体、近 5 分钟自我发言占比、消息数、距上次发言秒数、待处理条数；先判断要不要进 Planner | 工程 |
| 主动候选 + post-draft judge | AstrBot `private_companion` | 生活/日程/关系/记忆生成候选；planner 加权选择；时机/频率/权限/投递检查；独立 persona judge 只允许/不允许，失败即不发送 | 工程 |
| 心跳冲动 | Persisto Mate | heartbeat 把记忆变成 impulse，模型决定是否开口、说多短、还是放过 | 工程 |
| initiate + D-reflection | companion-emergence | 从梦境/反射/研究/情绪峰值/回忆共鸣排队 outbound 候选；D pass 提升/降级/学习校准 | 工程 |
| 焦虑驱动追问 | AI Virtual Phone | `anxiety` 值 ≥ 阈值才排追问；延迟按 `threshold→maxDelay, 100→minDelay` 线性插值；用户发言取消 | 工程 |

**关键结论：** 主动消息要有「四件套」——**触发条件、决策门、投递预算、静默退出**。只做「定时器 + 生成」会变成打卡式骚扰；只做 prompt 会让模型把「主动」理解成「找话说」。

### 2.3 L 语言层：语言形态与风格学习

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 表达库（situation → style） | MaiBot；AstrBot `self_learning`；`private_companion` | MaiBot 从群聊学习 `situation/style/count`，选择时「高命中加权采样 + 随机采样 → LLM 选 id」；self_learning 从 user→bot 对话对提取表达模式/few-shot，经审查后注入；private_companion 有表达规则、风格轮换与证据审查 | 混合（检索 + prompt） |
| 群组黑话 | MaiBot；AstrBot `self_learning` | 统计预筛高频词，结合上下文推断含义，在 LLM 请求前注入解释；避免模型把「黑话」当普通词 | 混合 |
| 人格演化 | AstrBot `self_learning`；`private_companion` | 学习结果先进入审查/回滚链路；支持批准、拒绝、删除、回滚、影子模式；避免人格漂移 | 工程 + prompt |
| 长短句 / 口语 / 不用 Markdown | MaiBot；KouriChat | MaiBot 明确以「不是长篇大论或 markdown 分点，而是或长或短的闲谈」为设计目标；KouriChat 做沉浸式角色扮演与分段 | prompt |
| 断句 | MaiBot | `llm_sentence_splitter.py` 用 LLM 只做断句：只能选原文切分点、不改写、不增删、代码/公式返回 `no_split` | 工程 |
| 错别字 | GCP；MaiBot | 见 R 层；本质是后处理，不是 prompt | 工程 |
| 反 AI 腔 | `blader/humanizer`；`lieflat` | 见 A 层；写作改写，不是聊天策略 | prompt |

**关键结论：** 语言层最值得抄的是「**从用户自己的话里学表达**」，而不是「让模型假装口语化」。MaiBot 的表达库和 self_learning 的 few-shot 审查链，都是把「像这个人」变成可检索、可回滚的数据，而不是一次性 prompt。

### 2.4 E 状态层：情绪、身体与关系状态

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 情绪向量 + 衰减 | companion-emergence；Front Porch；Persisto；GCP | companion-emergence：每种情绪独立 half-life，低于 0.01 噪声地板删除；Front Porch：情绪惯性，上一轮 mood 作为下一轮起点；Persisto：per-emotion decay；GCP：mood 默认 300s 衰减 | 工程 + 紧凑注入 |
| 关系刻度 | Front Porch；AstrBot `self_learning`；`private_companion`；AI Virtual Phone | Front Porch：short-term bond −300..+300 缓慢回中（每 10 轮 1 点）、long-term bond 更慢更粘；trust −100..+100 只由用户行为改变；单轮掉 trust ≥20 触发 repair window；承诺 +12 trust/+6 bond，毁约 −22/−10；self_learning 有好感度/心理状态；private_companion 有关系卡 | 工程 + prompt |
| 身体时钟 / 睡眠 / 梦境 | Persisto；companion-emergence；`private_companion`；Front Porch | Persisto：作息从用户出现时间学习；睡眠 ~90 分钟周期；梦境由当天真实记忆拼接，早晨只保留最后一个；companion-emergence：energy/words/session hours + dream consolidation；private_companion：睡眠、疲倦、日程、位置、天气、日记、成长；Front Porch：故事时钟、天气、梦 | 工程 |
| 执念 / 反刍 | Front Porch；Persisto | Front Porch fixation 持续 3 轮，轻微染色但不劫持场景；Persisto rumination 让 sadness 持续更久 | 工程 |
| post-draft affect judge | Persisto；`private_companion`；Front Porch | Persisto：独立 reader 只判「每种情绪涨还是跌」（−2..+2），不判绝对等级，避免小模型乱编绝对值；private_companion：post-draft persona judge 只允许/不允许，失败即不发送；Front Porch：realism evals | 工程 |
| 状态注入 | 全部 | 只注入「当前心情/关系/身体」的一小段摘要 + 行为倾向，不注入整套规则 | 混合 |

**关键结论：** 情绪层的正确姿势是「**独立 judge 更新状态 → 状态持久化/衰减 → 下一轮只注入摘要**」。让主模型每轮重新判断「我该是什么心情」既不稳定，也会和语言规则竞争注意力。

### 2.5 M 记忆层：长期连续性与自然引用

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 摘要 / 反思 | LivingMemory；`private_companion`；MaiBot | LivingMemory 达到轮次后总结，反思按会话/语义聚类；private_companion 有 episode/fact/reflection；MaiBot 有 A_memorix 记忆内核 | 工程 |
| 混合检索 | LivingMemory；dsh-liketavern；Persisto | LivingMemory：BM25（jieba + 中文二元组）+ FAISS 向量 + 图谱，RRF 融合；相关性 0.5 / 重要性 0.25 / 新鲜度 0.25；文档路 0.65 / 图谱路 0.35，按查询意图调整；dsh-liketavern：BM25 + 时间衰减；Persisto：topic 标签 + 时间衰减强度 + 标签词匹配 | 工程 |
| 衰减 / 遗忘 | LivingMemory；Persisto；companion-emergence | LivingMemory：importance 每日约 1% 衰减（`decay_rate=0.01`），访问降低有效衰减率，访问次数每次衰减后 ×0.5；原子 TTL：事件 7d、计划 2d、事实 180d、关系 90d、偏好 60d、未知 30d；状态 active/dormant/superseded/expired/forgotten；Persisto：ACT-R 指数衰减 + 检索即强化；companion-emergence：真实遗忘与「哀悼」 | 工程 |
| 记忆工具 | LivingMemory；dsh-liketavern；Persisto | Agent 可调用 `recall_long_term_memory` / `memorize_long_term_memory`；dsh-liketavern 按需 `tavern_*` 工具读写；Persisto `remember`/`ponder` 由模型自己决定什么值得留下 | 工程 + prompt |
| 分支 / 世界状态 | dsh-liketavern；dsh-tavern | dsh-liketavern：角色资产全局共享，剧情状态按分支隔离，每轮先 WAL 再落盘，regenerate/edit 先回滚派生记忆/世界状态/变量；dsh-tavern：变量由后台模型按规则结算 | 工程 |
| 自然引用旧事 | Persisto；LivingMemory；Front Porch | 通过 topic/关键词/语义召回后注入，不要求模型「记住所有事」；Front Porch 用 Journal/Dreams 把旧事变成可引用的叙述 | 混合 |

**关键结论：** 记忆层不要追求「存得越多越好」，而要追求「**写入有门槛、检索有排序、遗忘有路径、引用有由头**」。LivingMemory 的 TTL + 衰减 + 访问强化，Persisto 的「检索即强化」，都是可复用的最小闭环。

### 2.6 A 抑制层：反 AI 腔与出站后处理

| 机制 | 代表项目 | 实现要点 | 层级 |
|---|---|---|---|
| 反 AI 写作模式清单 | `blader/humanizer` | 26 条模式：not X but Y、one-line closer、伪深刻、staged run-up、无对手争论、强制三连、重复句首、破折号、堆叠限定词等；盲测 16/16 偏好；明确「不是为过检测器」 | prompt |
| 中文语料统计 | `lieflat-less-ai-tone` | 629 篇 / 283 万字 / 95,551 句；26 项候选特征仅 11 项通过检验；最强「段首零回指评论」4.4×；15 项无区分力；人类比喻 2.4×、正文设问 17×、句内排比更高 | prompt / 审稿 |
| 出站重写 | SillyTavern `Final Response Processor`；`Prose Polisher` | 在 assistant 消息发送前清理/重写；但采用度极低（8★ / 7★），且是写作润色，不是聊天策略 | 工程 |
| 系统标记/元解释剥除 | 本项目已有 `terminal_reply_guard` | 剥 `[主动]`、`[MM-DD HH:MM]`、元记忆解释、复述、无由头反问等；属于「确定性出站守卫」 | 工程 |
| 后置 judge | `private_companion`；Persisto | 只判「发/不发」或「情绪涨/跌」，不让 judge 改写正文；失败即不发送 | 工程 |

**关键结论：** 反 AI 腔最适合做「**出站审稿/后处理**」，不适合做「聊天主 prompt」。`lieflat` 的统计尤其重要：网络流传的很多「AI 味」清单并没有区分力，盲目删比喻/设问/排比会把人的特征删掉。聊天场景应优先删「模板句、元解释、复述、无由头反问」，而不是删「所有看起来像书面语的东西」。

### 2.8 Prompt 层 vs 工程层：总判定

| 类型 | 机制 | 判定 | 风险 / 备注 |
|---|---|---|---|
| **纯 prompt** | 「请像真人」「口语化」「长短句」「不要 markdown」「不要追问」「不要复述」 | 只能做「声音/边界」的轻量约束 | 规则越多越互相竞争；本项目历史已证明会恶化 |
| **纯 prompt** | `humanizer` / `lieflat` 的反 AI 腔清单 | 适合写作审稿/离线改写 | 不适合直接做聊天主 prompt；会误删人类特征 |
| **工程** | 打字指示器、分条发送、打字延迟、错别字 | 必须工程 | 生成后处理；prompt 做不到稳定节奏 |
| **工程** | 主动定时、jitter、免打扰、每日预算、min_idle、静默退出 | 必须工程 | 只靠 prompt 会变成打卡式骚扰 |
| **工程** | 概率门、决策 AI、注意力、疲劳、沉默状态机 | 必须工程 | 把「要不要说」从主模型注意力里拿走 |
| **工程** | 情绪/关系状态持久化、衰减、惯性 | 必须工程 | 状态要独立存储；prompt 只接摘要 |
| **工程** | 记忆摘要、检索、衰减、强化、遗忘、分支隔离 | 必须工程 | 记忆是数据问题，不是 prompt 问题 |
| **工程** | 出站守卫、系统标记剥除、post-draft judge | 必须工程 | 确定性规则优先于模型自觉 |
| **混合** | 情绪状态注入、风格 few-shot、记忆片段、主动消息文案 | 工程状态 + prompt 表达 | 工程决定「给什么」，prompt 决定「怎么说」 |
| **混合** | 角色成长 / 关系事件 | 工程记录 + prompt 摘要 | 不要每轮重写人格 |

#### 3.1.1 MaiBot（麦麦 / MaiSaka）

- **链接**：https://github.com/Mai-with-u/MaiBot
- **一句话定位**：QQ 群聊「数字生命」，明确以「最像而不是好」为设计原则，不追求完美助手，而追求会犯错、有自己感知的类人存在。
- **成熟度**：6,619★ / 692 fork / 105 open issues / 最近 push 2026-10-26；**GPL-3.0**。
- **机制级做法**：
  - **回复概率模型**：`src/maisaka/turn_trigger/reply_likelihood.py` 用 8 个特征拟合 logistic 概率（是否@、是否@他人、问号、纯媒体占位、近 5 分钟自我发言占比、近 5 分钟消息数、距上次发言秒数、待处理条数），先判断「这批消息值不值得进 Planner」，而不是让主模型在 prompt 里自己克制。
  - **消息防抖**：`src/chat/debounce/README.md` 四档等待（自然档 2/5/2/0.5 秒），整批最多 8 秒、@/提及最多 1 秒；先等补充消息合并再判断，减少「刚回完又补一句」的碎片感。
  - **表达库选择**：`src/chat/replyer/maisaka_expression_selector.py` 从 `situation/style/count` 表达库中「高命中加权采样 + 随机采样」，再让 LLM 只选 id；表达是检索出来的，不是每次让模型即兴「口语化」。
  - **LLM 断句**：`src/chat/utils/llm_sentence_splitter.py` 只做断句，要求只能在原文切分、不改写、不增删，代码/公式返回 `no_split`；切分与生成解耦。
  - **拼音错字**：`src/chat/utils/typo_generator.py` 用 pypinyin 同音/近调 + 词频替换，按字/词概率；类默认 `error_rate=0.3`，示例实例化 `0.03`，不要理解成「每条消息 30%」。
- **对本项目可借鉴**：**决策与生成分离 + 等待合并 + 表达库检索 + 生成后断句**。GPL-3.0 代码不建议直接并入，机制可以重写。
- **来源**：README https://github.com/Mai-with-u/MaiBot ；关键代码见上列路径。

#### 3.1.2 AstrBot `astrbot_plugin_group_chat_plus`（读空气群聊增强）

- **链接**：https://github.com/Him666233/astrbot_plugin_group_chat_plus
- **一句话定位**：以「AI 读空气」为核心的群聊增强插件，让 Bot 先判断该不该说话，再决定说什么。
- **成熟度**：177★ / 23 fork / 21 open issues / 最近 push 2026-09-23；**AGPL-3.0**。
- **机制级做法**：
  - **两层过滤**：概率筛选 + 独立「读空气」决策 AI；@/关键词旁路；Smart 模式会参考同批追加消息，而不是只看单条。
  - **注意力机制**：`utils/attention_manager.py` 为每个用户维护 0–1 注意力，指数衰减 `0.5^(elapsed/half_life)`；注意力半衰期 300s、情绪半衰期 600s；支持注意力溢出、候选冷却→正式冷却、读空气未回复衰减。
  - **疲劳/时段**：连续对话后降低回复意愿；时段概率模拟作息；频率调整器自动分析群聊节奏。
  - **沉默状态机**：`utils/humanize_mode.py` 连续 3 次不回复进入静默；被 @、超 600s、积累 8 条、命中兴趣关键词时退出；决策历史注入保持判断一致性。
  - **错别字**：`utils/typo_generator.py` 拼音同音字替换，默认 2% 概率，跳过代码/URL/短消息。
  - **打字延迟**：`utils/typing_simulator.py` 15 字/秒、0.5–3s 夹取、±30% 随机。
- **对本项目可借鉴**：**这是最接近「微信/QQ 一对一 + 群聊」的完整工程参考**；尤其适合把「是否回复/是否主动/是否沉默」从主 prompt 拿出来。AGPL-3.0，只借机制。
- **来源**：README https://github.com/Him666233/astrbot_plugin_group_chat_plus ；`utils/attention_manager.py`、`utils/humanize_mode.py`、`utils/typing_simulator.py`、`utils/typo_generator.py`。

#### 3.1.3 AstrBot `astrbot_plugin_proactive_chat`（主动消息）

- **链接**：https://github.com/Pancakes-Labs/astrbot_plugin_proactive_chat
- **一句话定位**：给 Bot 一个「主动关怀的灵魂」：会话长时间无消息后，用随机间隔发起上下文感知、符合人设、带动态情绪的主动消息。
- **成熟度**：463★ / 25 fork / 21 open issues / 最近 push 2026-10-26；**AGPL-3.0**。
- **机制级做法**：
  - **随机触发区间**：不是固定 cron，而是在配置的下限/上限之间随机选下一次触发时间。
  - **未回复计数器**：`{{unanswered_count}}` 注入 prompt，让模型表达轻微失落/想念；有未回复上限，超过就停。
  - **免打扰时段**：配置时间段内不主动。
  - **上下文来源**：`conversation_history` / `recent` / `hybrid` 可选，避免主动消息只会「在吗」。
  - **分段回复**：`core/services/sender_service.py::calc_interval` 支持 random 1.5–3.5s 或 log 缩放（`log(word_count+1, 1.8)+0–0.5s`）；分段阈值默认 150 字，超长不切。
  - **持久化**：重载/重启后恢复未执行任务。
- **对本项目可借鉴**：主动消息的「随机感 + 未回复情绪 + 免打扰 + 分条间隔」可以直接映射到现有 `proactive/` 调度器。注意它的主动消息本质是「模拟一条用户消息」触发主链，prompt 依赖较重；本项目应把「何时发」留在调度器，「发什么」交给角色主链。
- **来源**：README https://github.com/Pancakes-Labs/astrbot_plugin_proactive_chat ；`core/services/sender_service.py`。

#### 3.1.4 AstrBot `astrbot_plugin_private_companion`（陪伴小屋）

- **链接**：https://github.com/menglimi/astrbot_plugin_private_companion
- **一句话定位**：面向私聊/群聊的角色陪伴插件：角色有自己的生活（状态、睡眠、日程、位置、天气、日记、成长），并围绕生活/关系/记忆生成主动联系。
- **成熟度**：498★ / 49 fork / 28 open issues / 最近 push 2026-10-27；**未声明 LICENSE（GitHub 404）→ 默认版权保留，不可直接商用/二次分发**；版本 7.0.0test α，迁移中。
- **机制级做法**：
  - **生活状态**：睡眠/疲倦、日程、位置、天气、日记、成长、生活事件；主动消息可以基于「角色此刻在做什么」而不是凭空问候。
  - **主动候选 + 四道检查**：`companion_v2/proactive/planner.py` 加权选择候选；README 明确「检查时机、频率、权限及投递结果」；不是生成即发送。
  - **post-draft persona judge**：`companion_v2/proactive/persona_judge.py` 在正文已 sealed 后独立判断「允许/不允许发出」；judge 不能改写正文、不能改受众/身份/来源/授权；**不可用/失败/未知 = 不发送（fail-closed）**。
  - **分段控制**：`companion_v2/conversation/segment_control.py` 支持显式 split marker（`{{split_marker}}` / `<<PRIVATE_COMPANION_SPLIT>>`）、最大段数、最小段长、保护 Markdown 块/列表/表格，避免把代码或格式拆坏。
  - **表达学习**：`companion_v2/expression/learning.py` 要求候选必须给出具体 `expression`（style 的具体说法或 grammar 的句法结构），禁止用「口语化、自然、简短」这种空话凑候选；带证据引用与审查。
- **对本项目可借鉴**：**主动链的「候选 → 检查 → judge → 投递」四段式**非常值得抄；`persona_judge` 的 fail-closed 语义尤其适合本项目「宁可不发，也不发错」的主动消息。许可证是硬伤，只能读机制。
- **来源**：README https://github.com/menglimi/astrbot_plugin_private_companion ；`companion_v2/proactive/persona_judge.py`、`companion_v2/conversation/segment_control.py`、`companion_v2/expression/learning.py`。

#### 3.1.5 AstrBot `astrbot_plugin_self_learning`（自主学习）

- **链接**：https://github.com/NickCharlie/astrbot_plugin_self_learning
- **一句话定位**：让 Bot 从真实 user→bot 对话中学习表达风格、群组黑话、社交关系与人格演化，并带审查/回滚。
- **成熟度**：436★ / 37 fork / 0 open issues / 最近 push 2026-10-26；**AGPL-3.0，但 README 声明部分个人组件 All rights reserved，存在许可歧义**。

  - **人格演化审查**：学习结果先进入审查链路，支持批准、拒绝、删除、回滚、自动应用策略；避免人格漂移。

#### 3.1.6 AstrBot `astrbot_plugin_livingmemory`（长期记忆）

- **链接**：https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory
- **一句话定位**：带动态生命周期的长期记忆：自动总结、关键词/向量/图谱召回、归档/衰减/访问强化。

- **机制级做法**：
  - **混合检索**：BM25（jieba 词元 + 中文连续段字符二元组）+ FAISS 向量 + 图谱；RRF 融合；相关性 0.5 / 重要性 0.25 / 时间新鲜度 0.25；文档路 0.65 / 图谱路 0.35，按查询意图调整；同一记忆双路命中加 0.08 交叉奖励。
  - **生命周期**：`docs/architecture.md` 定义 importance 每日按 `decay_rate=0.01`（约 1%/天）衰减；访问降低有效衰减率，访问次数每次衰减后 ×0.5；原子 TTL：事件 7d、计划 2d、事实 180d、关系 90d、偏好 60d、未知 30d；状态 active/dormant/superseded/expired/forgotten；归档可恢复。
  - **Agent 工具**：`recall_long_term_memory` / `memorize_long_term_memory`，让模型按需读写，而不是每轮把全部记忆塞进 prompt。
  - **反思/整合**：按每日或反思触发，按会话/语义聚类（相似度阈值 0.7）合并，保留策略归档或删除。
- **对本项目可借鉴**：**记忆的「排序权重 + TTL + 强化」比「更大的向量库」更重要**；这套参数可以作为本项目记忆层的起点。AGPL，机制借鉴。
- **来源**：README https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory ；`docs/architecture.md`。

### 3.2 DSH（DeepSeek Harness）生态

> 先说结论：**DSH 不是拟人化插件，而是「一切皆插件」的 Agent 宿主**。它的插件可以接管宿主定时、会话恢复、角色扮演前端、状态结算，所以能做拟人化，但拟人化不是 DSH 内置能力。

#### 3.2.1 `dsh-proactive`（宿主级主动唤醒）

- **链接**：https://github.com/john-walks-slow/dsh-proactive （monorepo 子包 `packages/dsh-proactive`）
- **一句话定位**：让 DSH 的模型具备「主动跟进」能力：模型自设 host 级闹钟，到点唤醒冷会话；无事可报可静默退出。
- **成熟度**：7★ / 1 fork / 1 open issue / 最近 push 2026-10-26；**README 标注 MIT，但仓库根没有 LICENSE 文件（GitHub license=null）**；极早期，机制参考价值大于生产可用性。
- **机制级做法**：
  - **四种调度**：`once`（相对秒/绝对时间）、`every`（≥300s）、`cron`（五字段，相邻触发≥300s）、`file`（JSON 时间表句柄，同步为子闹钟）。
  - **随机抖动**：`jitter_seconds` 0–86400，每次触发追加 `uniform(0, jitter)`，防止整点扎堆。
  - **免打扰**：`respect_quiet_hours=true` 时安静时段直接跳过、不补发；循环闹钟推进到窗外下一个锚点。
  - **静默等待**：`min_idle_seconds` 仅对 `resume` 目标生效；目标会话最近活动不足该秒数则顺延，每分钟复查一次，不计入审计/预算。
  - **每日预算/频率**：默认每日 50 条可见消息、全宿主每小时最多 60 次唤醒；静默回合不扣额度。
  - **静默收尾**：`proactive_reclaim(reason)` 作为唯一动作、不输出可见文本，宿主把整轮折叠成 ~70B 墓碑，不污染长期上下文。
  - **唤醒 framing**：注入明确说「Host-scheduled wake: the user did NOT send this」，避免模型误以为是用户开口。
- **对本项目可借鉴**：**这是「主动消息不变成打卡」的最完整工程模板**。本项目已有 `proactive/` 与 `commit_sent` 记账，可对照补：jitter、quiet hours、daily budget、min_idle、静默退出、墓碑折叠。
- **来源**：README https://github.com/john-walks-slow/dsh-proactive

#### 3.3.1 Front Porch AI（Realism Engine）

- **链接**：https://github.com/linux4life1/front-porch-AI
- **一句话定位**：本地优先的角色聊天/角色扮演应用，核心是「Realism Engine」：bond、trust、情绪惯性、需求、时间、执念、成长。
- **成熟度**：80★ / 16 fork / 4 open issues / 最近 push 2026-10-27；**AGPL-3.0**。
- **机制级做法**：
  - **双层 bond**：short-term bond −300..+300，普通对话每次 1–2 点，每 10 轮向中性回漂 1 点；long-term bond 更慢、更粘，来自长期模式而非单次事件。
  - **独立 trust**：−100..+100，只由用户行为改变；单轮掉 trust ≥20 触发 repair window，下一句真诚修复可挽回；承诺 +12 trust/+6 bond，毁约 −22/−10。
  - **情绪惯性**：上一轮 mood 作为下一轮起点，模型「从旧情绪移动」而不是每轮重判；26 类情绪映射表情图，ONNX 分类约 300ms。
  - **故事时间**：每轮推进，单轮最多 180 分钟；裸 0/失败按 2 分钟；12 轮不动则跳到下一时段；六个时段、真实日历、天气、梦。
  - **执念**：fixation 持续 3 轮，轻微染色但不劫持场景；成长 rings 有证据、可审查、可退休。
- **对本项目可借鉴**：**bond/trust 双刻度 + repair window + 情绪惯性 + 时间下限/上限**是最适合情感陪伴的关系模型；比单一「好感度」更抗极端、更像人。AGPL，机制借鉴。
- **来源**：README https://github.com/linux4life1/front-porch-AI ；`docs/realism-engine.md`。

#### 3.3.2 Persisto Mate

- **链接**：https://github.com/m-rui001/Persisto-Mate
- **一句话定位**：终端里的「数字生命」：会睡、会做梦、会记忆、会主动联系，身体时钟从用户出现时间学习。
- **成熟度**：4★ / 0 fork / 0 open issues / 最近 push 2026-10-18；**MIT**；极早期，但是目前看到的最精细的「affect judge + 记忆衰减」参考实现之一。
- **机制级做法**：
  - **独立 affect judge**：`packages/mate/src/judge.ts` 明确「DELTAS, NOT LEVELS」：不问「这段对话里有多少悲伤（0..1）」，而问「每种情绪是涨还是跌」，−2..+2 阶梯；因为小模型没有绝对锚点，绝对评分会乱编。情绪按 wheel 顺序排列，joy 与 sadness 是对立轴。
  - **身体时钟**：不是用户时区，而是「用户实际出现的时间」；只在凌晨 1 点出现，它就凌晨 1 点清醒；24 小时都在，它就不困；消失一天，它就睡一天。
  - **睡眠/梦境**：约 90 分钟睡眠周期；梦由当天真实记忆拼接，早晨只保留最后一个；关终端不等于睡觉，它知道被关掉。
  - **记忆模型**：`packages/mate/src/memory.ts` 用 ACT-R 风格：强度随时间指数衰减（`stored · exp(-(now-t)/τ)`，τ 以天计），检索即强化（testing effect）；`remember`/`ponder` 由模型自己决定什么留下，`private` 笔记也参与召回。
  - **心跳主动**：heartbeat 把记忆变成 impulse，模型决定是否开口、说多短、还是放过；`alarm` 工具可以把自己叫醒。
- **对本项目可借鉴**：**affect judge 的「只判涨跌」**是低成本、高稳定的情绪更新方式；**ACT-R 衰减 + 检索强化**可以直接映射到本项目 `user_facts`/记忆层。MIT，代码级参考友好。
- **来源**：README https://github.com/m-rui001/Persisto-Mate ；`packages/mate/src/judge.ts`、`packages/mate/src/memory.ts`。

## 4. 对本项目的适配性初判

### 4.1 先排除三类不适用方案

1. **纯 prompt 的「请像真人」大段规则**：本项目 v1.54/v1.55 已经证明「把像真人拆成互相竞争的硬指令」会恶化输出；生态里也没有一个高质量项目是靠一大段「be human」prompt 成功的。`humanizer`/`lieflat` 是写作改写，不是聊天策略。
2. **直接搬 AGPL/GPL 代码**：MaiBot GPL-3.0、AstrBot 插件 AGPL-3.0、Front Porch/AI Virtual Phone/dsh-tavern AGPL-3.0；本项目是 MIT，直接并代码会改变许可证义务。**只借机制、重写实现**。
3. **许可有硬伤的**：`private_companion` 无 LICENSE；`KouriChat` 非商用 + 禁腾讯系；`lieflat` CC BY-NC。都不能作为商用项目的直接依赖。

### 4.2 P0：五个工程层改造（建议优先）

| 优先级 | 机制 | 参考项目 | 为什么适合本项目 | 建议落点（需代码复核） |
|---|---|---|---|---|
| **P0-1** | **发言决策与生成分离**：概率/规则门 + 独立 decision AI + 静默状态机 + 注意力/疲劳 | GCP、MaiBot | 直接解决「回复太多/太碎/不会看气氛」；把「要不要说」从主模型注意力里拿走，减少 prompt 竞争 | `orchestrator/` 前置 gate；`proactive/` 决策线；会话级状态表 |
| **P0-2** | **主动触达四件套**：jitter + quiet hours + daily budget + min_idle + 静默退出 | dsh-proactive、proactive_chat、private_companion | 解决「打卡式主动」「生成了却没发」「半夜打扰」；本项目已有 `commit_sent` 记账，可补齐 | `proactive/` + `user_scheduler`；持久化闹钟/预算；`proactive_reclaim` 等价物 |
| **P0-3** | **生成后分条 + 打字延迟**：句级切分、保护代码/Markdown、1.5–3.5s 随机或 log 缩放、typing indicator | proactive_chat、MaiBot、GCP、AI Virtual Phone | 投入产出比最高；微信里「一条长文」最像机器；分条后每条有呼吸感 | `utils/stream_guard.py` 之外新增 transport segmenter；`api/`/`wechat_direct/` 发送层；前端 typing |
| **P0-4** | **post-draft judge**：主动/出站消息在发送前由独立小模型判「发/不发」，失败即不发，不允许改写正文 | private_companion、Persisto | 比「让主模型自觉」可靠；特别适合主动消息、低置信度回复、情绪敏感场景 | `terminal_reply_guard` 之后新增 `reply_judge`；只判 send/drop，不改写 |
| **P0-5** | **记忆生命周期**：重要性衰减 + 类型化 TTL + 访问强化 + 混合检索 + 按需 recall 工具 | LivingMemory、Persisto | 解决「记得太多/记错/不会自然引用」；比继续扩 context 更有效 | `context/` / `shisi/memory/`；`user_facts` 增加 importance/TTL/访问计数；召回排序 |

### 4.3 P1：三个增强

| 优先级 | 机制 | 参考项目 | 说明 |
|---|---|---|---|
| **P1-1** | **情绪/关系状态机**：mood/trust/intimacy/fatigue 独立存储，按半衰期衰减，每轮由独立 judge 更新，主链只注入一小段摘要 | Front Porch、companion-emergence、Persisto | 比「每轮让模型重新决定心情」稳定；注意不要注入整套规则 |
| **P1-2** | **表达库 + 审查/回滚**：从用户自己的话里学 situation→style，few-shot 检索，候选先审查再注入 | MaiBot、self_learning | 解决「角色说话不像这个用户熟悉的人」；避免人格漂移 |
| **P1-3** | **错别字/已读/输入状态**：1–2% 拼音同音错字、`sendtyping`、已读回执 | GCP、MaiBot、AI Virtual Phone | 高感知拟人，但错字可能损害信任；建议只在沉浸模式/休闲话题开启 |

### 4.4 P2：体验型 / 高成本

| 优先级 | 机制 | 参考项目 | 说明 |
|---|---|---|---|
| **P2-1** | 语音打断 + Live2D/表情 | Open-LLM-VTuber、Front Porch、companion-emergence | 微信文本阶段不需要；做语音/视频陪伴时再上 |
| **P2-2** | 虚拟手机 UI（朋友圈/语音/转账卡片） | AI Virtual Phone | 高沉浸、高成本；可作为长期产品形态 |
| **P2-3** | 分支隔离/WAL/世界状态 | dsh-liketavern | 剧情线复杂到多分支时再上；当前可先做会话级 |

### 4.5 与现有模块的落点（按项目 AGENTS.md 的结构推断，需代码复核）

| 现有模块 | 可承载的机制 | 备注 |
|---|---|---|
| `proactive/` + `user_scheduler` | 主动闹钟、jitter、quiet hours、日预算、min_idle、静默退出 | 本项目已有 `commit_sent`「投递成功才记账」，与 dsh-proactive 的「静默不扣预算」一致；补 jitter/预算/墓碑即可 |
| `orchestrator/` | 发言决策 gate、注意力/疲劳、沉默状态机、决策历史 | 建议把「要不要回」做成独立前置层，不塞进主 prompt |
| `utils/stream_guard.py` | 保持内容守卫职责；**不要**把分条/延迟塞进 guard | 新增独立 transport segmenter，职责分离 |
| `terminal_reply_guard.py` | 系统标记剥除、元解释/复述/无由头反问抑制 | 已有；可再加 post-draft judge 作为第二道 |
| `context/` / `shisi/memory/` | 记忆生命周期、TTL、衰减、访问强化、混合检索 | `user_facts` 需要 schema 变更；先做只读评估 |
| `shisi/`（affinity/emotion_stage） | 情绪/关系状态、衰减、惯性、repair window | 与现有 affinity 刻度对齐，避免双真源 |
| `config/characters/` | 表达库/风格 few-shot/审查 | 每角色独立表达库，避免串角色 |
| `api/` + `wechat_direct/` | typing indicator、sendtyping、已读、分条发送 | iLink 有 `sendtyping` 能力（AI Virtual Phone 已用） |
| `frontend/` | typing 动画、气泡逐条、已读状态 | 与后端 segmenter 配套 |

### 4.6 不建议的做法

- **不要**再往主 system prompt 里加「请像真人」「不要复述」「不要追问」「回复要短」等长串硬规则；生态里的成功案例都把这些问题移到工程层。
- **不要**把 `humanizer`/`lieflat` 整份清单直接作为聊天 prompt；它们是写作审稿，且 `lieflat` 已证明很多「AI 味」规则没有区分力。
- **不要**在没有 post-draft judge 的情况下放开主动消息；主动消息的错误成本远高于被动回复。
- **不要**为了「像人」而默认加错别字/已读不回；这些是产品策略，不是技术默认。
- **不要**直接复制 AGPL/GPL/NC 代码；本报告只建议借鉴机制。

## 5. 未确认事项

1. **本轮没有运行任何被调研项目**：所有机制结论来自 README/源码静态阅读；「作者自述」的性能/效果数据（如 dsh-tavern 缓存 95%、humanizer 盲测 16/16）未独立复现。
2. **Star / push 时间是 2026-10-27 的快照**：DSH/AstrBot 插件生态迭代很快，数字可能迅速变化；成熟度判断不等于生产可用。
3. **许可证存在多处歧义**：
   - `private_companion` 无 LICENSE（默认版权保留）；
   - `dsh-proactive` README 写 MIT 但仓库无 LICENSE；
   - `self_learning` 是 AGPL-3.0 但 README 声明部分个人组件 All rights reserved；
   - `Open-LLM-VTuber` GitHub 识别 NOASSERTION，但 LICENSE 文件是 MIT；
   - `lieflat` 是 CC BY-NC 4.0（非商用）；
   - `KouriChat` 是 DeepAnima 1.2 非商用且禁腾讯系。
   **建议由用户/法务拍板许可证政策，再决定哪些项目可以代码级参考。**
4. **SillyTavern / NoneBot 的「未找到」是检索结论，不是存在性证明**：可能有些插件不在 GitHub、或命名不带 humanize/拟人；本轮只覆盖 GitHub 可检索范围。
5. **机制与项目的对应关系是「可借鉴」，不是「可直接移植」**：本项目是 Python/FastAPI + React + 微信 iLink，AstrBot 插件是 Python 但依赖 AstrBot 事件模型；MaiBot 是 Python 但 GPL；DSH 是 TypeScript 插件。移植需要重写适配层。
6. **需要用户拍板的产品问题**：
   - 是否接受「分条发送 + 1.5–3.5s 延迟」作为默认体验？还是只对特定角色/时段开启？
   - 是否允许 1–2% 错别字/口语瑕疵？可能提升「真人感」，也可能损害信任。
   - 是否愿意为「发言决策」增加一次小模型调用（成本/延迟）？还是先用规则+轻量分类器？
   - 是否要做情绪/关系状态持久化（schema 变更 + 迁移）？还是先用会话级内存？
   - 许可证政策：AGPL/GPL 只借机制，还是允许引入？NC 项目是否完全不考虑？
7. **DSH 生态的长期稳定性未知**：`dsh-proactive` 只有 7★，`dsh-tavern` 1,315★ 但 AGPL，`dsh-liketavern` 225★ MIT；建议只做概念验证，不作为生产依赖。
