# 系统性升级调研汇总（2026-10-27）

> 本文件是四路调研与两份引入设计的索引，不重复正文细节。所有外部事实与仓库坐标分别见各报告与设计文档。

## 一、四路调研各一句话结论

1. **DSH 专项调研**（`docs/reports/2026-10-27-DSH专项调研.md`）：DSH 不是「仿真人化插件」，而是 DeepSeek 官方开源的 Agent Harness；真正值得借的是其生态插件 `dsh-im-humanize` 的阅读延迟、typing、活跃响应曲线、`message_break` 与声明式 schema，**借机制、不借运行时**（《DSH 专项》§1.2/§4）。
2. **仿真人化插件生态调研**（`docs/reports/2026-10-27-仿真人化插件生态调研.md`）：生态里有效的「像人」绝大多数不是 prompt，而是 R/T/L/E/M/A/I 七层工程机制；本仓历史「硬指令互相竞争」的根因正是把 R/T/E/M/A 层问题塞进了 L 层 prompt（《生态调研》§2.0/§2.8）。
3. **BreezeTTS2 调研**（`docs/reports/2026-10-27-BreezeTTS2调研.md`）：Breeze TTS 2 是 3B 英中双语 open-weight TTS，质量/延迟亮眼，但**权重为非商用许可、自托管需 12–24GB NVIDIA GPU**；对本仓「无 GPU Linux 生产 + Windows 开发机」，**托管 API 是唯一不新增硬件的生产路径**，且需先过跨境合规与商业许可门（《Breeze 调研》§2.4/§3.2/§3.3）。
4. **本仓语音链路与拟人机制测绘**（`docs/reports/2026-10-27-本仓语音链路与拟人机制测绘.md`）：语音是 MiMo-only 单引擎且仅非流式主链触发；拟人机制已覆盖出站守卫/时间/主动/模式/称呼/拆条六层，**真正缺的是生成前阅读延迟、typing、以及 humanize 配置的按用户覆盖**（《测绘》§0/§2.8）。

## 二、两项设计的核心推荐

### 1. 仿真人化引入方案（`docs/reports/2026-10-27-仿真人化引入方案.md`）

**先补工程底座，不补 prompt。** P0 主线做两件事：① 把 `utils/humanize_config.py` 收敛成声明式字段表并增加 `user_humanize` 按用户覆盖（防 v1.56 R7 类键漂移）；② 以 opt-in 方式上线「阅读延迟 + typing + 活跃响应曲线 + supersede 显式契约」，默认关闭、1%→10%→50%→100% 灰度，且延迟期新消息必须静默取消旧回合；并先落 G-5 观测/灰度底座。已覆盖的守卫/时间/主动/拆条/记忆机制全部标注「勿重复引入」；群聊注意力/疲劳/沉默状态机、错别字、完整打字时长模拟、`humanizer`/`lieflat` 清单进主 prompt、复活追问链均判不适合。所有涉及产品形态/花钱的项列入 Q1–Q6 待裁决；每批均要求新增测试 + AGENTS §4.3 全量基线（当前 3900 收集 / 3898 通过 + 2 跳过 / 250 文件 / 42 卡；vitest 217/217；ruff 0）。

### 2. BreezeTTS2 引入设计（`docs/reports/2026-10-27-BreezeTTS2引入设计.md`）

**（Q0 确认引入后）首版生产走 Breeze 托管 API，MiMo 保持默认主力，Breeze 按角色 opt-in。** 新增 `voice/breeze_tts_provider.py`（aiohttp 直连，mp3 → 现有 `SynthesizedAudio` → `to_silk`/`to_amr` → 微信发送链，首版不改 orchestrator 整段合成形态）；`TTSManager` 从「单引擎 + 失败永久切引擎」改为「多引擎注册 + 按调用路由 + 回退链 + 冷却」，并明确：Breeze 失败回落 MiMo，MiMo 失败不自动回落付费 Breeze。`engine/model/voice_id` 三层白名单按引擎分域扩展：`VoiceCatalog` 以 `(engine, voice_id)` 为唯一键（旧条目默认 `mimo-tts`），`CharacterVoiceSpec` 增加 `breeze_model`/`breeze_instructions` 并在 `synth_kwargs()` 输出 `engine`；Breeze 请求必须显式发送 `model_id` 与 `language_code=zh`（官方 API 已核实 body 支持可选 `model_id`，省略时会按语言/默认自动选型）。两个硬门先过：商业许可/跨境合规（Q10/Q13）与生产到 `api.breeze.blue` 的中国网络实测（A2）；未过门前 `breeze-tts.enabled=false`，代码合入但不启用。自托管仅开发机 GGUF/8GB recipe 试听，不作为生产。**注意：`AGENTS.md:222` L6 仍为「MiMo 唯一引擎」，`LOG.md` 末尾为 2026-10-22，未见 2026-10-27 新裁决落账；因此「是否引入」列为 Q0，未确认前本节仅为候选设计。**

## 三、待用户裁决问题汇总（统一编号）

> 选项后的「代价」均为相对代价；未列推荐的事项默认按设计文档的保守路径执行。

**仿真人化（Q1–Q6）**

- **Q1 阅读延迟 + typing 是否上线？** A. 上线，默认关闭 + 灰度（推荐）；B. 只上 typing；C. 都不上。代价：A 首字变慢、需 1–2 周灰度；B 秒回仍在；C 维持机器感。
- **Q2 humanize 是否做按用户覆盖？** A. 做（推荐）；B. 保持全局。代价：A 多一张表 + 管理端复杂度；B 无法兼顾快/慢偏好。
- **Q3 主动消息是否加 post-draft judge（多一次小模型调用）？** A. 加，fail-closed（推荐）；B. 不加；C. 只对高价值主动类型加。代价：A 每条多一次调用/延迟；B 错误主动消息仍可能发出；C 规则复杂。
- **Q4 是否接受 1–2% 错别字/口语瑕疵？** A. 不接受（推荐）；B. 仅沉浸模式可选；C. 接受。代价：B/C 有信任与品牌风险。
- **Q5 是否进行情绪/关系 schema 改造（per-emotion half-life、bond/trust 双刻度）？** A. 暂不做，先观测（推荐）；B. 做 P2 改造；C. 只做只读评估。代价：B 需迁移与双真源治理。
- **Q6 是否放宽拆条 2 段上限/引入 `message_break`？** A. 保持 2 段（推荐，现行用户裁决）；B. 放宽到 3–4 段并做模型断点；C. 仅实验环境评估。代价：B 需单回合上限/空断点/尾部去重，且与现裁决冲突。

**BreezeTTS2（Q0、Q7–Q13）**

- **Q0 是否引入 BreezeTTS2 / 是否修订 AGENTS L6？** A. 确认引入（MiMo 默认 + Breeze opt-in，推荐若确有此意）；B. 暂不引入，仅保留技术预研；C. 直接替换 MiMo（不推荐）。代价：A 需同步修订 L6 与「唯一引擎」文档/配置口径；B 本次调研不进入实施；C 成本/合规/稳定性风险全量暴露。
- **Q7 Breeze 部署形态？** A. 托管 API（推荐）；B. 自托管 GPU + 商业许可；C. 仅开发机试听。代价：A $60/1M 汉字 + 跨境合规 + 中国延迟未测；B 12–24GB GPU + 商业许可 + 运维；C 不满足生产引入。
- **Q8 Breeze 角色定位？** A. MiMo 默认 + Breeze 按角色 opt-in（推荐）；B. Breeze 默认替换 MiMo；C. 仅 1 角色灰度 1 周。代价：B 成本/合规/稳定性全量暴露；C 验证慢。
- **Q9 音色策略？** A. 42 角色固定设计音色（推荐首版）；B. 每用户克隆；C. 混合（平台固定 + 少量高价值用户克隆）。代价：B voice slots 随用户爆炸；C 需权限/计费/审核。
- **Q10 商用范围与许可？** A. 仅 C 端免费/非商用；B. B 端商业化 → 购买 BreezeBlue 商业许可；C. 先 POC 不商用（推荐短期）。代价：A 仍需法务确认「免费」边界；B 商务/成本；C 不产生商用收入。
- **Q11 是否要求真流式（句级 TTS）？** A. 首版整段合成（推荐）；B. 句级流式（二期）。代价：B 需改 orchestrator + `IncrementalReplyGuard` 句界 + 音频分段下发。
- **Q12 MiMo 失败时是否自动回退到付费 Breeze？** A. 不允许（推荐）；B. 允许。代价：B 需每日字符预算/告警，否则账单无声放大。
- **Q13 跨境数据合规？** A. 允许（需法务书面确认 + 用户同意 + 隐私政策）；B. 不允许（法务结论前按此执行）；C. 仅发送文本、不发送参考音频。代价：B 托管 API 出局、只能自托管 + 商业许可；C 克隆不可用且文本仍跨境。

## 四、未确认事项（跨两份设计）

1. **Breeze 托管 API 的 `model_id`/`language_code` 行为**（假设 A1）：官方 API Reference 已核实 body 支持可选 `model_id`（1–120 字符）与 `language_code`，且 `model_id` 省略时由语言/默认自动选型（显式 en/zh → `breeze-tts-2`，其他/省略 → `breeze-tts-2-multilingual`）；仍需用试用 key 实测显式 `model_id` 生效与不兼容组合的报错行为，provider 必须显式发送 `model_id` + `language_code=zh`。
2. **生产（中国大陆）到 `api.breeze.blue` 的可达性与 TTFA**（假设 A2）：需生产机 20 次 curl + 并发 2/4 压测；未测前不能承诺托管方案可用。
3. **商业许可边界**：免费计划按 Breeze FAQ 不可商用；C 端免费是否构成 commercial purpose、自托管权重商用许可费用，均需 BreezeBlue 书面确认 + 法务（Q10）。
4. **跨境数据合规**：参考音频/聊天文本发美国公司是否满足 PIPL、隐私政策、用户同意；未确认前按 Q13-B 不启用托管。
5. **生产是否真无 GPU / 是否安装 pilk**：前者依据部署文档与 `.venv-cpu` 记录，未远程 `nvidia-smi`；后者本机实测 `pilk=False`，生产未核实（《测绘》§6.2）。两者都影响「自托管」与「微信语音转码」的可行性。
6. **Breeze 中文女声/角色音色主观质量**：AA Provider Voice #11 / Elo 1227 不是中文角色克隆评测；需定义 10–20 条样本、3 人双盲听评、MOS/偏好阈值。
7. **iLink 是否支持 `sendtyping`（status 1/2）及其余辉/频控**：未实测前 typing 不上线；阅读延迟在无 typing 时封顶 ≤5s（《DSH 专项》§2.2.10；《测绘》§2.8）。
8. **MiMo `/audio/speech` 与官方 `/chat/completions` 是否等价**：影响现有 MiMo 链路稳定性；需同文本对比（《Breeze 调研》§4.3 末条）。
9. **用户所说的「DSH」具体指哪个插件**：本汇总按「DSH = DeepSeek Harness 本体」处理；若用户实际指 `dsh-im-humanize` 或 `dsh-humanizer` 家族，需插件名/链接/截图做源码级结论（《DSH 专项》§5.1）。
10. **基线口径**：本汇总引用 AGENTS §4.3 的 3900 收集 / 3898 通过 + 2 跳过 / 250 测试文件 / 42 卡；落地前必须重新确认「42 卡是否在位 + 工作树是否含并行在制品」，否则数字不可比。
