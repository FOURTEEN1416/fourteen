## 4. 数据层契约（①）

### 4.1 表结构（`data/sqlite.db`，幂等 `CREATE TABLE IF NOT EXISTS`）

```sql
CREATE TABLE IF NOT EXISTS topic_state (
    session_key    TEXT NOT NULL,
    character_id   TEXT NOT NULL,
    topic_id       TEXT NOT NULL,
    title          TEXT NOT NULL,
    summary        TEXT NOT NULL DEFAULT '',
    status         TEXT NOT NULL CHECK(status IN ('active','parked','closed')),
    salience       REAL NOT NULL DEFAULT 0.5,
    mention_count  INTEGER NOT NULL DEFAULT 0,
    turn_count     INTEGER NOT NULL DEFAULT 0,
    anchors        TEXT NOT NULL DEFAULT '[]',
    -- 内部记账列（契约未列，但两条规则必须有载体）：
    idle_turns     INTEGER NOT NULL DEFAULT 0,
    last_active_at TEXT NOT NULL,
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL,
    expires_at     TEXT NOT NULL,
    PRIMARY KEY (session_key, character_id, topic_id)
);
CREATE INDEX IF NOT EXISTS idx_topic_state_session_status
    ON topic_state(session_key, character_id, status, last_active_at DESC);

CREATE TABLE IF NOT EXISTS topic_plan (
    session_key  TEXT NOT NULL,
    character_id TEXT NOT NULL,
    topic        TEXT NOT NULL DEFAULT '',
    intent       TEXT NOT NULL DEFAULT '',
    planned_at   TEXT NOT NULL,
    next_at      TEXT NOT NULL,              -- planned_at + wait_minutes；到点才允许注入
    expires_at   TEXT NOT NULL,
    consumed_at  TEXT,
    PRIMARY KEY (session_key, character_id)
);

CREATE TABLE IF NOT EXISTS topic_meta (
    session_key     TEXT NOT NULL,
    character_id    TEXT NOT NULL,
    turns_since_llm INTEGER NOT NULL DEFAULT 0,
    llm_calls       INTEGER NOT NULL DEFAULT 0,   -- 按本地日重置（Q5 预算固定 0，不设上限）
    last_llm_at     TEXT NOT NULL DEFAULT '',
    -- 内部记账列：同 turn_id 重放幂等（_after_process 可能重试）
    last_turn_id    TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (session_key, character_id)
);
```

**为什么多三列**（必须在实施说明中保留，不得被"字段对齐"误删）：
- `topic_state.idle_turns`：实现「连续 3 个用户轮未提及 → park」的唯一确定性载体；没有它就得每轮回读最近 3 条用户消息，既慢又易被窗口裁剪。
- `topic_meta.last_turn_id`：`_after_process` 在异常/重试时可能重复调用；同 turn_id 必须幂等，否则 `mention_count/turn_count` 会被重复计。
- `topic_plan.next_at`：`planned_at + wait_minutes`，是「到点才注入」的确定性载体；只靠 `expires_at` 会在重启/账本丢失时提前注入。

**只存摘要与短锚点**：`title ≤40`、`summary ≤80`、`anchors` 最多 3 条且每条 ≤40 字；**不存整段对话原文**。日志只打 `topic_id/action/status`，不落标题与锚点原文。

`topic_meta` 行数 = 会话×角色（远小于消息量），不参与 7 天 TTL（保留 judge 计数与 `last_turn_id`）；账号删除若要求立即清除，按 §13 风险条目另行处理。

```python
# utils/topic_state.py
_DB_PATH = project_path("data", "sqlite.db")          # conftest 可 monkeypatch
_CONFIG_PATH = project_path("data", "scheduler_config.json")
_READ_TIMEOUT_MS = 50      # 主链 pre-turn 读：绝不拖首字
_WRITE_TIMEOUT_MS = 5000   # 后处理/主动线写

DEFAULTS: dict[str, Any] = {
    "enabled": False,
    "llm_judge_enabled": False,
    "judge_every_turns": 4,
    "daily_llm_budget": 0,      # 0 = 不限（Q5）
    "active_cap": 3,            # Q6-B
    "retention_days": 7,        # Q4-B
    "recall_after_hours": 6,    # Q3-A
    "recall_max": 2,
    "park_idle_hours": 6,
    "switch_theta1": 0.2,
    "switch_theta2": 0.35,
}

# Q1/Q3/Q4/Q5/Q6 的固化边界：这些值不是"可调建议"，而是裁决；
# 管理端写入越界一律 400/422，读侧坏值回落默认，绝不放宽裁决。
_BOUNDS = {
    "judge_every_turns": (4, 4),      # Q1：每 4 轮一次，不能改成每轮
    "daily_llm_budget": (0, 0),       # Q5：不设每日 LLM 上限
    "active_cap": (1, 3),             # Q6：上限 3，不能放宽到 5
    "retention_days": (7, 7),         # Q4：全部 7 天
    "recall_after_hours": (6, 168),   # Q3：不得低于 6h
    "recall_max": (1, 2),             # Q3：最多 2 条
    "park_idle_hours": (6, 6),        # Q2/状态机：6h 无活动
    "switch_theta1": (0.0, 1.0),
    "switch_theta2": (0.0, 1.0),
}

def read_topic_config() -> dict[str, Any]:
    raw = json_state.read_json(_CONFIG_PATH, default={})
    block = raw.get("topic_state") if isinstance(raw, dict) else None
    if not isinstance(block, dict):
        block = {}
    cfg = dict(DEFAULTS)
    for key, default in DEFAULTS.items():
        value = block.get(key)
        if isinstance(default, bool):
            cfg[key] = value if isinstance(value, bool) else default
        elif isinstance(default, int):
            cfg[key] = value if isinstance(value, int) and not isinstance(value, bool) else default
        else:
            cfg[key] = float(value) if isinstance(value, (int, float)) and not isinstance(value, bool) else default
        if key in _BOUNDS:
            lo, hi = _BOUNDS[key]
            if not (lo <= cfg[key] <= hi):
                cfg[key] = default
    if cfg["switch_theta2"] < cfg["switch_theta1"]:
        cfg["switch_theta1"] = DEFAULTS["switch_theta1"]
        cfg["switch_theta2"] = DEFAULTS["switch_theta2"]
    return cfg


def write_topic_config(**partial: Any) -> dict[str, Any]:
    payload = {k: v for k, v in partial.items() if v is not None}
    unknown = sorted(set(payload) - set(DEFAULTS))
    if unknown:
        raise ValueError(f"未知的 topic_state 字段: {unknown}")
    merged = {**read_topic_config(), **payload}
    for key, (lo, hi) in _BOUNDS.items():
        value = merged.get(key)
        if isinstance(value, bool) or not isinstance(value, (int, float)) or not (lo <= value <= hi):
            raise ValueError(f"{key} 越界或类型非法: {value!r}（允许 {lo}..{hi}）")
    if merged["switch_theta2"] < merged["switch_theta1"]:
        raise ValueError("switch_theta2 不得小于 switch_theta1")
    if not isinstance(merged.get("enabled"), bool) or not isinstance(merged.get("llm_judge_enabled"), bool):
        raise ValueError("enabled / llm_judge_enabled 必须是 bool")
    def _mutate(data: dict[str, Any]) -> None:
        data["topic_state"] = {k: merged[k] for k in DEFAULTS}
    json_state.update_json(_CONFIG_PATH, _mutate)
    return read_topic_config()
```

```python
    默认**不消费**（发送成功才 consume=True）；这是「发送成功消费计划」
    与「到点注入」能同时成立的关键。"""

def purge_expired(*, now: datetime | None = None, force: bool = False) -> int:
    """删除 expires_at < now 的 topic_state / topic_plan。
    enabled=false → 0，不连库（六 API 零 DB 契约）；
    force=True 仅供每日维护：即使已关闭也清理过期行，避免"启用过再关闭"留下永久残留。"""
```

辅助（不属于对外六 API，但实施时需要）：
- `render_topic_state_block(snapshot: dict) -> str`：状态数据块（≤160 字）。
- `run_llm_judge(..., llm: Any, timeout: float = 8.0) -> dict | None`：稀疏 LLM 判定；失败/低置信度 → `None` + 保留原状态。
- `should_run_llm_judge(session_key, character_id, cfg) -> bool`：读 `topic_meta` 判断是否满 4 轮/预算。

### 4.4 连接、事务与容错纪律

```python
def _connect(*, ensure_schema: bool = False, busy_timeout_ms: int | None = None) -> sqlite3.Connection:
    if busy_timeout_ms is None:
        busy_timeout_ms = _WRITE_TIMEOUT_MS
    path = Path(_DB_PATH)
    path.parent.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(str(path), timeout=busy_timeout_ms / 1000.0, isolation_level=None)
    conn.row_factory = sqlite3.Row
    conn.execute(f"PRAGMA busy_timeout={int(busy_timeout_ms)}")
    if ensure_schema:
        conn.executescript(_SCHEMA)   # 幂等 DDL；仅后台写路径调用
    return conn
```

- **写路径**：`BEGIN IMMEDIATE` → 读写 → `commit`；异常 `rollback` + 返回 `{"error": "db_locked"}`，**不向上抛**（主链/主动线不因状态库故障中断）。
- **读路径**：`ensure_schema=False` + `busy_timeout_ms=50`；`sqlite3.OperationalError: no such table` / `database is locked` → 返回空快照 `degraded=True`，不建表、不等待。
- **DDL 只在写路径**：`update_after_turn` 第一次调用时建表；`get_topic_snapshot` 永不在用户等待路径上做 DDL。
- **时间**：统一 `utils.local_time.now_local()` 归一为 naive 北京墙钟，存 `"%Y-%m-%d %H:%M:%S"`；禁止混用 `chat_history.created_at` 的 UTC。

```python
def _normalize_now(now: datetime | None = None) -> datetime:
    from utils.local_time import _BEIJING, now_local
    dt = now or now_local()
    if getattr(dt, "tzinfo", None) is not None:
        dt = dt.astimezone(_BEIJING).replace(tzinfo=None)
    return dt.replace(microsecond=0)
```
- **坏 JSON**：`anchors` 解析失败 → `[]` + `logger.debug`，该行其余字段照常返回；不删行、不抛异常。
- **多 worker**：SQLite WAL（生产库已 WAL，2026-10-27 只读实测）+ `BEGIN IMMEDIATE` + busy_timeout：写事务在开始时就取写锁，同一会话的并发更新被串行化；`PRIMARY KEY` 保证同一 `topic_id` 不重复，`active_cap` 在同一事务内强制，不会并发产生第 4 个 active。

## 5. 状态机契约（②）

### 5.1 六类转换（确定性优先）

| 转换 | 触发条件（全部可测） | 结果 | `action` |
|---|---|---|---|
| **continue** | 当前用户消息与某 **active** 的 `title/anchors` 重叠 ≥ `switch_theta1` | 该 topic `mention_count+1`、`anchors` 追加本轮短句（去重保留≤3）、`summary=clip(本轮消息,60)`、`salience=min(1, s*0.9+0.2)`、`idle_turns=0`、`last_active_at=now`、`expires_at=now+retention_days（固定 7d）`；`turn_count` 由 §5.3 统一 +1（不在此重复） | `continue` |
| **switch** | 与所有 active 重叠 < θ1，且未命中任何 parked ≥ θ2 | 新建 active（`title`=当前用户短句≤20 字，`summary`≤60，`anchors=[当前短句≤40]`，`salience=0.5`） | `switch` |
| **resume** | 命中某 **parked** 的重叠 ≥ `switch_theta2` | 该 parked→active；原 active 保持（多 active 并行） | `resume` |
| **park** | 某 active **连续 3 个用户轮**未被提及（`idle_turns >= 3`） | active→parked；`expires_at=now+retention_days（固定 7d）` | `park` |
| **close** | 命中明确结束语 + 与某 active **或 parked** 的重叠 ≥ θ1 | 该行→closed；`expires_at=now+retention_days（固定 7d）` | `close` |
| **timeout** | 某 active 距 `last_active_at` ≥ `park_idle_hours`（6h） | active→parked；`expires_at=now+retention_days（固定 7d）` | `timeout` |

**动作优先级**（同轮多事件时，`action` 取最高优先级，其余作为 `transitions` 列表返回）：
`close` > `resume` > `switch` > `continue` > `timeout` > `park`。
例：用户说「那个面试弄完了」且命中 active A → close A；同时另一 active B 已 3 轮未提 → B 也 park，但 `action="close"`，`transitions=["close:A","park:B"]`。

### 5.2 判定算法

**重叠度（中文短文本，字符 bigram 包含度）**：

```python
_PUNCT_RE = re.compile(r"[\s，。！？、；：,.!?;:\"'“”‘’（）()\[\]【】~～…·]+")

def _norm(text: str) -> str:
    return _PUNCT_RE.sub("", str(text or "").lower())

def _bigrams(text: str) -> set[str]:
    t = _norm(text)
    if len(t) <= 2:
        return {t} if t else set()
    return {t[i:i + 2] for i in range(len(t) - 1)}

def text_overlap(a: str, b: str) -> float:
    """短边包含度：len(交集)/min(len(ga), len(gb))。
    为什么不用 Jaccard：消息长、标题短时 Jaccard 会被长边稀释
    （「我今天去面试了」vs「面试」= 1/9），短边包含度 = 1.0，符合「标题是话题名」的语义。
    """
    ga, gb = _bigrams(a), _bigrams(b)
    if not ga or not gb:
        return 0.0
    return len(ga & gb) / max(1, min(len(ga), len(gb)))

def topic_overlap(message: str, topic: dict[str, Any]) -> float:
    candidates = [topic.get("title") or ""] + list(topic.get("anchors") or [])
    return max((text_overlap(message, c) for c in candidates), default=0.0)
```

**结束语判定**：

```python
_CLOSE_RE = re.compile(r"(弄完了|解决了|搞定了|完事了|结束了|不聊这个了|别提了|翻篇了|处理完了|办完了)")
_CLOSE_QUESTION_RE = re.compile(r"[吗呢？?]\s*$")

def is_close_statement(text: str) -> bool:
    t = str(text or "").strip()
    if not t or _CLOSE_QUESTION_RE.search(t):
        return False          # 「结束了吗？」是提问，不是收尾
    return bool(_CLOSE_RE.search(t))
```

**新话题标题**：取用户消息按 `[。！？!?；;\n]` 切分后的第一个非寒暄短句，`clip(20)`；若为空则 `clip(user_message, 20)`；仍为空 → `"未命名话题"`。`summary` 取 `clip(user_message, 60)`。**不调用 LLM 起名**（确定性期）；LLM judge 可在高置信度时覆盖 title/summary。

**新话题创建门槛**：只有 `len(_norm(user_message)) >= 4` 且不是纯寒暄/空应答时才新建 active。短应答（「嗯」「好的」「哈哈」「在吗」）不建新话题，只推进现有 active 的 `idle_turns`/衰减；若因此触发 park/timeout，`action` 就是 `park`/`timeout`。这条门槛是「park 能成为主 action」与「不被寒暄刷出垃圾话题」的共同前提。

**`topic_id` 生成**：`sha1(f"{session_key}|{character_id}|{normalized_title}").hexdigest()[:12]`。同一会话/角色下同标题复用同一行（不重复建）；标题不同但语义相同仍由 `topic_overlap` 兜住（θ2 命中即 resume/park 原行）。**冲突处理**：若生成的 `topic_id` 已存在——parked → 复用并 `resume`；active → 复用并 `continue`；closed → 追加 `|now.strftime("%Y%m%d%H%M%S")` 再哈希生成新 id（保留旧 closed 行，避免主键冲突）。

**多 active 匹配**：按 `topic_overlap` 降序，取最高分；同分按 `salience` 降序、`last_active_at` 降序。

### 5.3 salience、多 active 与淘汰

- 新 topic：`salience = 0.5`。
- 被提及：`salience = min(1.0, salience * 0.9 + 0.2)`；未被提及：`salience = max(0.0, salience * 0.9)`。
- `mention_count` 只在被提及的轮次 +1；`turn_count` 对该 topic 处于 active 的每个用户轮 +1（含未提及轮，用于展示「已持续 N 轮」）。**continue/resume 不得再单独 +1**；每轮只由本规则加一次，避免同一被提及轮被加 2。
- 淘汰：`active` 数量 > `active_cap` 时，按 `(salience, last_active_at)` 升序排序，最低者 `status="parked"`；重复直到 ≤ cap。
- 淘汰不删除、不关闭；`parked` 仍可 `resume` / 被主动复提（受三重闸）。
- `salience` 只影响排序与淘汰，不影响「能否被想起」：只要 `expires_at > now` 且 `status != closed`，就仍可命中。

### 5.4 7 天 TTL

- 每次 `continue/resume/park/close/timeout` 都把该行 `expires_at = now + retention_days`。
- `purge_expired()` 删除 `expires_at < now` 的所有状态行（active/parked/closed 一视同仁）与过期计划。
- `get_topic_snapshot / select_proactive_recall` 的查询都带 `expires_at > now`，即使未跑 purge 也不会返回过期行。
- `purge_expired(force=True)` 挂 `ProactiveScheduler._run_daily_maintenance`（`proactive/scheduler.py:2150`），每日一次——即使 `topic_state.enabled=false` 也清理过期行，避免「启用过再关闭」留下永久残留；正常 `purge_expired()` 在关闭态仍返回 0（零 DB 契约）。同时 `update_after_turn` 在会话内顺手清理该会话过期行（小事务，避免表无界增长）。

### 5.5 边界与幂等

| 边界 | 行为 |
|---|---|
| `θ1`/`θ2` 相等 | 使用 `>=`（命中即算）；配置校验要求 `θ2 >= θ1` |
| 空 `anchors` / 坏 JSON | 只用 `title` 计算；坏 JSON 视为 `[]`，不抛 |
| 单话题、无 active | 第一条消息 → `switch` 新建；后续按继续/切换 |
| 同 `turn_id` 重放 | **仅当 `turn_id` 非空且** `topic_meta.last_turn_id == turn_id` → `action="replay"`，所有计数不变；`turn_id` 为空时一律正常更新（不判重放） |
| 同轮命中多个 active | 取最高重叠；其余 active 只做 `idle_turns+1`/衰减 |
| 同轮同时 close + park | `action="close"`；`transitions` 保留全部 |
| 用户消息为空 | 不更新（返回 `action="empty"`），避免空轮建话题 |
| `session_key` 为空 | 不读不写（返回 `action="empty"`），禁止产生无主行 |
| 库锁/超时 | 返回 `{"error": "db_locked"}`，不抛；下一轮再试（幂等） |
| 角色切换 | `character_id` 是主键一部分，绝不串角色 |

### 6.6 LLM judge 的输入/输出（Q1-B）

```python
TOPIC_JUDGE_SYSTEM = """你是话题状态判定器。只判断这一轮用户消息对现有话题做了什么，
不要改写对话，不要输出解释。只输出 JSON：
{"action":"continue|switch|park|resume|close","topic_title":"...","summary":"...","confidence":0.0}"""
```

- 触发：`turns_since_llm >= judge_every_turns`（固定 4）**且** `llm_judge_enabled=true`；`daily_llm_budget` 固定 0（Q5 不设上限，不做日预算限制）；当前没有任何 active/parked → 不调用（没有可判的状态，省一次调用）。
- 输入：当前用户消息 + 当前 assistant 回复（各 ≤300 字）+ active/parked 的 `title/anchors` 摘要（≤300 token）+ 当前时间；**不输入完整人设**。
- 输出：严格 JSON `{"action": "continue|switch|park|resume|close", "topic_title": "...", "summary": "...", "confidence": 0.0-1.0}`。
- 应用：`confidence < 0.6` / 解析失败 / 超时 / `action` 非法 → **原状态不变**；高置信度才允许改 `title/summary/status`；**永不删除行、永不跨越 session/character**。
- 应用映射：`continue` → 更新匹配 active 的 `summary`；`switch` → 用 LLM `topic_title/summary` 新建 active（受 `active_cap` 淘汰）；`park` → 按 `topic_title` 匹配 active；`close` → 按 `topic_title` 匹配 active 或 parked；`resume` → 按 `topic_title` 匹配 parked（无匹配则 no-op）。
- **不重复计数**：judge 只改 `status/title/summary`（以及新建行的初始计数），绝不再次递增确定性机已经计过的 `mention_count/turn_count/salience`。
- 计数：每次实际发起调用 `llm_calls += 1`（按本地日重置）；无论成败 `turns_since_llm = 0`，避免每轮重试风暴。

### 7.1 parked 复提三重闸

| 闸 | 实现位置 | 判据 |
|---|---|---|
| **① 距上次话题 ≥6h** | `topic_state.select_proactive_recall` | `last_active_at <= now - recall_after_hours`（默认 6h） |
| **② 非静默** | 同上 + `scheduler._is_quiet_hours()` 已前置 | 静默时段返回 `[]`；`scheduler.py:1419` 已在 LLM 决策前拦截 |

- **judge 关闭 = 第三闸不存在**：`llm_proactive.judge_enabled=false` 时 `topic_recall.build_topic_recall()` 直接返回空候选（没有 allow 就不允许 parked 复提）；手动/祝福线不受影响（仍走原 judge_disabled 放行语义）。

`proactive/topic_recall.py`（新文件，完整职责）：

```python
"""主动线 parked 话题复提候选 —— 三重闸的候选侧。

只读 topic_state.select_proactive_recall；不自己查库、不自己判静默。
"""
from __future__ import annotations

from dataclasses import dataclass
from typing import Any

from utils import topic_state
from proactive.post_draft_judge import read_judge_config


@dataclass(frozen=True)
class TopicRecall:
    items: tuple[dict[str, Any], ...] = ()
    keywords: tuple[str, ...] = ()
    judge_context: str = ""


def build_topic_recall(
    session_key: str,
    character_id: str = "default",
    *,
    quiet_hours: tuple[int, int] | None = None,
    now: Any | None = None,
    judge_available: bool = False,
) -> TopicRecall:
    judge_enabled, _timeout = read_judge_config()
    if not judge_enabled or not judge_available:
        return TopicRecall()   # 第三闸不存在/不可调用 → 不允许 parked 复提
    items = topic_state.select_proactive_recall(
        session_key, character_id, now=now, quiet_hours=quiet_hours,
    )
    if not items:
        return TopicRecall()
    judge: list[str] = []
    keywords: list[str] = []
    for item in items[:2]:
        title = str(item.get("title") or "").strip()
        anchors = [str(a).strip() for a in (item.get("anchors") or []) if str(a).strip()]
        anchor = anchors[0] if anchors else ""
        age = float(item.get("age_hours") or 0.0)
        judge.append(f"{title}（约 {age:.1f} 小时前）")
        keywords.extend([title, anchor])
    return TopicRecall(
        keywords=tuple(k for k in keywords if len(k) >= 2),
        items=tuple(items),
        judge_context="；".join(judge),
    )
```

### 7.4 `next_plan` 全周期（skip 存 → 重启读 → 到点注入 → 发送消费）

```
should_contact=false + wait=45
  └─ save_next_plan(topic, intent, wait_minutes=45)
       next_at = planned_at + 45min
       expires_at = next_at + 24h（上限 7 天）
       upsert 时 consumed_at = NULL（新计划必须可读）
       ↓ （进程重启：sqlite 行仍在）
下一次 tick
  └─ take_next_plan(consume=False)：仅当 next_at <= now 且 expires_at > now
       → next_plan 注入决策上下文（不依赖 _llm_proactive_next_ok 内存字典）
       ↓
decide_proactive 再次判断
  ├─ should=false → save_next_plan 覆盖旧计划（consumed_at 复位 NULL）
  └─ should=true → 投递成功
       ├─ take_next_plan(consume=True) 消费旧计划
       └─ save_next_plan(本次 next_topic/next_intent, wait_minutes=0)
投递失败 → 不消费、不覆盖旧计划（保留到 TTL）
window_expired → take_next_plan(consume=True) 丢弃过期计划（过期不补）
```

- `topic_plan` 主键 `(session_key, character_id)`，同一会话/角色只保留**一条**待执行计划；新计划覆盖旧计划。
- **`next_at` 是到点闸**：`take_next_plan` 只返回 `next_at <= now` 的计划；`_llm_proactive_next_ok` 丢失/重启也不会提前注入。
- **`consumed_at` 必须复位**：`save_next_plan` 的 upsert `DO UPDATE` 必须写 `consumed_at = NULL`；否则「消费旧计划 → 保存新计划」的新计划仍带旧 `consumed_at`，`take_next_plan` 永远读不到（只写不读）。
- `take_next_plan` 默认不消费；只有 `consume=True` 才写 `consumed_at`。这是「到点注入」与「发送成功才消费」同时成立的关键。
- 计划 TTL：`next_at + 24h`，上限 `retention_days`（7 天）。**Q4 的「全部状态保留 7 天」针对 `topic_state` 的 active/parked/closed 行**；`topic_plan` 是执行计划，用更短的 `next_at+24h` 防止陈旧计划复活，但跨进程重启仍在。
- 重启后计划仍在：不依赖 `_llm_proactive_next_ok` 内存字典，直接从 `topic_plan` 的 `next_at/expires_at` 读。

```python
def _call_llm(llm: Any, system: str, prompt: str, timeout: float) -> str:
    """8s 硬超时：daemon 线程 + join(timeout)，到点即返回空串。
    不用 `with ThreadPoolExecutor`：其 __exit__ 会 shutdown(wait=True)，
    LLM 不结束就永远不返回（实测 sleep(3) 在 3.03s 才抛 TimeoutError）。
    """
    if llm is None or not hasattr(llm, "chat_sync"):
        return ""
    kwargs = dict(query=prompt, system_prompt=system, max_tokens=200, temperature=0.1)
    try:
        params = inspect.signature(llm.chat_sync).parameters
        if "timeout" in params:
            kwargs["timeout"] = float(timeout)
    except (TypeError, ValueError):
        pass

    result: dict[str, Any] = {}
    def _worker():
        try:
            result["value"] = str(llm.chat_sync(**kwargs) or "")
        except Exception as e:  # noqa: BLE001
            result["error"] = e

    import threading
    t = threading.Thread(target=_worker, name="topic-judge", daemon=True)
    t.start()
    t.join(float(timeout))
    if t.is_alive():
        return ""          # 硬超时：放弃等待；daemon 线程不阻塞进程退出
    if "error" in result:
        return ""
    return result.get("value", "")
```

```python
def _attach_topic_state(memory_context: Any, snapshot: Any) -> Any:
    """把 topic snapshot 的 text 挂到 memory_context（不改变其他键）。"""
    text = str((snapshot or {}).get("text") or "").strip() if isinstance(snapshot, dict) else ""
    if not text:

    if isinstance(memory_context, dict):
        out = dict(memory_context)
        out["topic_state_text"] = text
        return out
    if not memory_context:
        return {"topic_state_text": text}
    return memory_context  # 非空字符串形态保持现状（persona_service 只吃 dict）
```

## 13. 风险与回滚（⑩）

| 风险 | 对策 |
|---|---|
| 状态漂移/误判 | 确定性优先；LLM 低置信度不改；active→parked 可逆；closed 保留 7 天可审计 |
| prompt 竞争复发 | 状态块是数据（≤160 字），指令只有 4 条软规则；旧硬规则只在关闭态使用；黄金集/A-B 断言 |
| 多 worker 并发 | SQLite WAL + `BEGIN IMMEDIATE` + busy_timeout + 主键幂等 + **非空** `turn_id` 重放保护 |
| 库锁/缺表拖慢主链 | pre-turn 读 50ms 超时 + `ensure_schema=False`；写 5s；异常降级为空，不抛 |
| 测试污染真实库 | conftest 重定向 `_DB_PATH/_CONFIG_PATH`；所有测试用 `tmp_path`；禁止直连宿主 `data/sqlite.db` |
| parked 复提被 judge 误杀 | `topic_context` 显式段 + 规则 3 例外；judge 仍可拒绝（三重闸不放水） |
| 计划陈旧/复活 | `topic_plan` 的 `next_at` 到点闸 + `next_at+24h` TTL；`window_expired` 消费；注入文案「语境变了不要硬套」 |
| 关闭态行为漂移 | 六 API 首行短路（每日 `purge_expired(force=True)` 例外）；prompt 逐字断言；`enabled=false` 不建表不读表 |
| 与 `user_facts` 双真源 | `topic_state` 只表达「对话进度」，不写事实；不合并注入；事实仍唯一记忆真源 |
| 隔离键写坏（R7 P0） | 管理端复用 `_resolve_admin_target_key`；纯数字无绑定 400；测试 full-key roundtrip |
| 账号删除后的残留 | `topic_state` 只存摘要/≤3 短锚点，随 7 天 TTL 自然过期；若要**立即**清除，需在账号生命周期 purge 增加内部清理（不在本批六 API 契约内，另行裁决，不静默扩权） |

**回滚步骤**：

1. `data/scheduler_config.json` → `topic_state.enabled=false`：主链无状态块、主动线无复提、六 API 零 DB、prompt 逐字旧文本。
2. `topic_state.llm_judge_enabled=false`：保留确定性状态，停止一切 judge LLM 调用。
3. 代码级：本批不部署、不提交 git；如需彻底撤回，按文件清单反向修订（`git diff` 审查，禁止 `reset --hard`）。

### 18.4 主动线等待窗审计（用户本轮提供，三件事分开说）

1. **等待窗计时真跑过**：生产 **8,914 条** `llm_wait_window` 账本记录（**8,704 条 wait>0**），15 条「上一次决策 wait>0 → 紧接着投递」全部落在 **wait−1～wait+10 分钟**内。
2. **LLM 选的时间被持久化且到点会重新决策**：`scheduler_config.json` 的 `throttle.llm_proactive_next_ok` 保存绝对 epoch（如 `2:…=21:22:27+45min→22:07:20`），每 5 分钟 tick 到点后走**全新** `decide_proactive`。
3. **但「下一次对话要说什么」的内容计划不存在**：只存一个 float 时间戳，到点后重新组装当前上下文再判一次，不携带上次的 `reason/草稿/目标`。因此机制在跑，产品上却可表现为「一直在等、始终没开口」：生产 `user=2` 今天 **17:57–21:22 连续 5 次 wait=45/45/45/60/45（合计 240 分钟）零投递**，这正是用户质疑「从来没真正实现过一次」的直接来源。

> 本批的 `topic_plan` 即针对第③点的补强：持久化 `topic/intent/next_at`，skip 也保存、重启可读、到点注入、发送成功才消费；但**不折叠 `should=false` 的重复唤醒**（T-5 不在本批，见 §15.2 第 11 条）。
