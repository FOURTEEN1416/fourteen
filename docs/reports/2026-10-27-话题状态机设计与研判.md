# 话题状态机（架构级）设计与研判

> **日期**：2026-10-27（2026-10-28 实施收口更新）  
> **状态**：**已裁决并实施**（Q1–Q6 已拍板；实施结果见 `docs/reports/2026-10-27-话题状态机实施计划.md` §18）  
> **范围**：主链「跨轮话题推进/收尾/复提」的状态化；不含剧情线、不含第二套记忆库  
> **结论先行**：按 **两阶段 B→C** 落地——**确定性话题状态**（零 LLM 成本）+ **稀疏 LLM 判定**（每 4 轮、后台异步、8s 硬超时）；状态以**短数据块**注入，替代「至少 2~3 轮守住同一话题」这类硬指令；主动线用 `active/parked` 状态提供「由头」。**不做**图数据库、不做每轮 LLM、不存用户原文全文。  
> **口径注记**：本文 §4 的方案参数（单 active / parked ≤5 / closed 30 天 / 日预算 20 等）是**裁决前设计稿**，已被 §5 的 Q1–Q6 最终裁决覆盖；最终落地参数以 §5 与实施计划 §8（11 键）为准。

## 1. 现状取证（代码实况 + 生产证据）

### 1.1 现有机制只有「锚点注入」，没有状态

| 环节 | 现状坐标 | 行为 |
|---|---|---|
| 锚点提取 | `utils/prompt_sanitize.py:308` `_extract_user_anchor_sentences` | 取 **24h 内 user 行**的完整短句 ≤3 条；过滤寒暄/空应答；只取用户原话 |
| 关键词袋 | `utils/prompt_sanitize.py:382` `extract_current_topics` | 规则切词（已被锚点句取代为主路径，仍保留） |
| 计算与下传 | `orchestrator/optimized_orchestrator.py:1311-1321, 1350-1358` | 每轮重算 → `memory_context["current_topics"]` |
| 注入 | `shisi/application/persona_service.py:209-218` | 「## 对方最近在说（对方原话，先接住具体内容）」+ 一句「仅有可指认未完成点才追问」 |
| 硬指令 | `utils/prompt_sanitize.py:545` `TOPIC_CONTINUITY_RULE` | 「**至少 2~3 轮内守住同一话题**」等 4 条规则 |
| 主动线 | `proactive/llm_proactive.py:707` `build_proactive_context` | 只带最近消息/最后一句，无跨轮话题记忆 |

### 1.2 结构性缺口

1. **无话题身份**：每轮从滑动窗口重算锚点，没有 topic_id / 生命周期；窗口滑出即「失忆」。
2. **无状态转换**：不知道「在聊 A → 用户换到 B → A 被搁置 → 三天后想接回 A」；`parked/closed` 概念不存在。
3. **无收尾语义**：用户说「弄完了/解决了」后，模型没有「这件事已结束」的状态，容易继续追问旧事。
4. **注入是「规则」不是「状态」**：v1.54/1.55 已实证——把「像真人」拆成互相竞争的硬指令会恶化输出；`TOPIC_CONTINUITY_RULE` 的「至少 2~3 轮」正是这类硬指令。
5. **主动线无由头**：只能在「最近消息」里找钩子，无法「想起上周没聊完的事」——而这正是「像人」的高价值时刻。

### 1.3 生产证据（既有批次留痕）

- 2026-10-16：`「吃饭」`在 10-19 仍被注入「当前话题」→ 时间窗修复（`extract_current_topics` 24h 窗，v1.53/10-19 批）。
- 2026-10-20：话题包实测只有 `['的话','哈喽']` 噪声 → 换用户原话锚点（v1.54 批）。
- 2026-10-20/21：v1.54/v1.55 结论「硬指令互相竞争会恶化」；v1.55 真根因是修复被降级路径抵消。
- 用户多轮报障「没有话题意识」「聊着聊着就另起炉灶」——锚点修了「取材」，没修「跨轮状态」。

> 结论：**问题不在锚点质量，而在缺少「话题作为对象」的持久状态与生命周期。**

## 2. 行业研判（带来源）

| 来源 | 机制 | 我们借什么 | 我们不借什么 |
|---|---|---|---|
| **DSH Tavern**（`github.com/flizzywine/dsh-tavern`，1324★，README 2026-10） | **前台模型只写正文，变量结算交后台模型**；状态栏由固定模板按变量显示，不再让正文模型每轮输出格式；「哪步出错重来哪步」 | **状态与正文分离结算**；状态用固定模板渲染，不占正文注意力；后台逐轮可重试 | 酒馆玩法/变量体系；其许可与玩法不适合直接引入 |
| **Letta（MemGPT）memory blocks**（`docs.letta.com/guides/agents/memory-blocks`） | 持久化**带标签的结构化块**（label/description/value/limit），**常驻上下文、无需检索**，agent 通过工具自编辑 | **状态=结构化块注入**（数据不是命令）；块带 description 约束读写语义 | agent 自编辑（我们要后台结算，更可控、可审计） |
| **Graphiti / Zep 时序知识图谱**（`github.com/getzep/graphiti` README） | 实体/关系带**时间有效性窗口**；信息变化时旧事实失效不删除；增量摄入 | **状态带时间戳与失效语义**（parked/closed 而非删行）；可追溯 | 图数据库 + 额外 LLM 抽取管线（重、需运维、与现有记忆双真源风险） |
| **TextTiling**（Hearst 1997, *Computational Linguistics* 23(1):33–64，`aclanthology.org/J97-1003/`） | 相邻文本块**词汇相似度骤降**处 = 话题边界 | **确定性切换检测**（锚点/标题词重叠度），零 LLM 成本 | 全文分段/重型算法 |
| **DST 对话状态跟踪**（`arxiv.org/html/2405.13037v1`；`github.com/yukyunglee/Awesome-Dialogue-State-Tracking`） | 用**结构化槽位**维护跨轮用户意图/约束，而非自由文本 | **状态 = 结构化字段**（topic_id/status/turn_count/anchors） | 任务型槽位体系（订餐/订票语义） |
| **EvolvConv**（Virginia Tech 学位论文，动态话题跟踪与演化） | 长对话中**实时话题跟踪与演化** | 话题生命周期（active → parked → closed）的存在性依据 | 其模型训练/数据集方案（成本不匹配） |
| **爱语 2.8.8 逆向**（本地：`D:\Desktop\爱语逆向\工作区\03-动态脱壳与反编译\交付\04-对标深度分析-爱语为何更好与资产利用方案.md`） | 160 个可调参数、4 档记忆、注入槽含「最近话题」；**但没有话题状态机** | 「话题是注入槽」+ 可配置思路 | 参数堆叠；它也没解决跨轮推进（我们的机会点） |

**研判结论**：行业里真正有效的不是「再写一条 prompt」，而是 **①状态与正文分离结算（DSH Tavern）、②结构化状态常驻注入（Letta）、③状态带生命周期/时间语义（Graphiti）**。这与 v1.54/v1.55 的教训一致：**数据进上下文，规则退场**。

## 3. 方案对比

| 方案 | 机制 | 成本/延迟 | 风险 | 判定 |
|---|---|---|---|---|
| **A 仅强化 prompt** | 再加「守话题/别跳题」规则 | 零成本 | 已有实证：硬指令互相竞争、越加越差 | ❌ 拒绝 |
| **B 确定性话题状态** | 规则更新状态表 + 短块注入；零 LLM | 零 token；后处理异步 | 语义判断有限（换题靠词重叠） | ✅ **一期**（1 批可上） |
| **C B + 稀疏 LLM 判定** | 每 N 轮/切换候选时后台小模型判定 `continue/switch/park/close/resume` | ≤1 次/4 轮/会话，日预算封顶；后台 8s，不影响首字 | judge 误判、成本漂移 | ✅ **二期（目标态）** |
| **D 图数据库/第二记忆库** | Graphiti/Neo4j 存话题图 | 高（运维+LLM 抽取） | 双真源（`memory_ext` 删除教训）、复杂度失控 | ❌ 本期拒绝 |

## 4. 推荐架构（C，分两期落地）

### 4.1 数据模型（`data/sqlite.db` 新表，幂等迁移）

```sql
CREATE TABLE IF NOT EXISTS topic_state (
    session_key   TEXT NOT NULL,
    character_id  TEXT NOT NULL,
    topic_id      TEXT NOT NULL,            -- 8~12 位随机/哈希，不用标题当键
    title         TEXT NOT NULL,            -- ≤40 字，话题名（可 LLM 起名，确定性期用首锚点）
    summary       TEXT NOT NULL DEFAULT '', -- ≤80 字，仅摘要，不存原文
    status        TEXT NOT NULL CHECK(status IN ('active','parked','closed')),
    turn_count    INTEGER NOT NULL DEFAULT 0,
    anchors       TEXT NOT NULL DEFAULT '[]', -- JSON：用户原话短句 ≤3（隐私边界内）
    last_active_at TEXT NOT NULL,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    PRIMARY KEY (session_key, character_id, topic_id)
);
CREATE INDEX IF NOT EXISTS idx_topic_state_active
  ON topic_state(session_key, character_id, status, last_active_at);
```

约束：
- 每会话**至多 1 个 active**；`parked` ≤5（超出按 `last_active_at` 淘汰最旧）；`closed` 保留 30 天后删除（与记忆 prune 对齐，可配）。
- **只存摘要与用户原话短句（≤3 条/话题）**，不存整段对话；日志不落原文。
- 隔离键 = `session_key + character_id`（D15/D16 语义，绝不跨用户/角色）。

### 4.2 状态机

```
                 switch / timeout(6h)
   active ───────────────────────────────▶ parked
      ▲                                      │
      │            resume（用户提起/主动复提） │
      └──────────────────────────────────────┘
      │
      │ close（明确结束：弄完了/解决了/不聊这个了 + 判定）
      ▼
   closed（30 天 TTL 后删除）
```

**确定性信号（一期，全部可测）**
- `continue`：当前用户消息与 active 的 `title/anchors` 词重叠 ≥ θ1（默认 0.2，可调）。
- `switch`：与 active 重叠 < θ1，且与某个 parked 重叠 ≥ θ2（默认 0.35）→ 该 parked 变 active、原 active 变 parked；否则原 active 变 parked、新建 active。
- `park`：active 连续 6h 无用户输入（且非静默时段外的主动线）→ parked。
- `close`：命中确定性结束语（`弄完了/解决了/搞定了/不聊这个了/结束了`）+ 同一话题锚点；或（二期）LLM 判定 close。
- `resume`：用户消息命中 parked 的 anchors（≥ θ2）→ 恢复 active。

**LLM 判定（二期，稀疏）**
- 触发：每 `judge_every_turns`（默认 4）轮；或确定性信号落在灰区（θ2 > overlap ≥ θ1）；或 close 候选。
- 输入：当前消息 + active/parked 的 title/anchors **摘要**（≤300 token）+ 时间；**不输入完整人设**。
- 输出：严格 JSON `{action: continue|switch|park|close|resume, topic_title?, summary?, confidence}`；解析失败/超时 → **保留原状态**（fail-open for state）。
- 日预算：每用户 ≤20 次（可配）；超预算只走确定性。

### 4.3 更新流程（**零新增首字延迟**）

```
本轮生成/发送（现状，不动）
  → _after_process → 后台线程池 _safe_after_chat（现有，optimized_orchestrator.py:1681-1692）
      → memory.after_chat（现状）
      → topic_state.update_after_turn(...)   ← 新：确定性更新；二期可在此 enqueue sparse judge
本轮注入使用**上一轮结束时的状态**（pre-turn snapshot）→ 状态更新下一轮生效
```

- 关键纪律：**话题状态更新绝不进入用户等待路径**；judge 与 after_chat 同线程池，独立 8s 超时，不重试。
- 首轮/无状态：注入回落现状锚点（兼容旧行为）。

### 4.4 注入（用「状态块」替代硬指令）

现有 `TOPIC_CONTINUITY_RULE`（至少 2~3 轮）**退役**，替换为 ≤120 字状态块：

```
## 当前话题状态（这是你自己在追的事，不是任务清单）
- 正在聊：{title}（已持续 {turn_count} 轮）
- 你记得的细节：{anchors ≤3}
- 之前没聊完：{parked titles ≤2}（只有对方主动提起或自然衔接时才接回）
```

- **不写**「至少 N 轮」「必须追问」等硬指令；只保留一句「接住具体内容，不另起炉灶」。
- 状态是**数据**（Letta 式块），不是命令（避免 v1.54 指令竞争）。
- 未启用时：prompt 与现状**逐字一致**（A/B 可断言）。

### 4.5 主动线集成

- `build_proactive_context` 增加状态块（active + parked 标题/锚点）。
- 主动 `post-draft judge` 不变；「复提 parked」只在满足「距上次话题 ≥ 6h + judge allow + 非静默」时允许；`closed` 永不主动复提。
- 由头优先级：active 未完成点 > parked 自然衔接 > 用户最近消息。

### 4.6 配置与回滚（`data/scheduler_config.json`，热读，跨 worker）

```json
"topic_state": {
  "enabled": false,
  "llm_judge_enabled": false,
  "judge_every_turns": 4,
  "daily_llm_budget": 20,
  "parked_ttl_hours": 72,
  "closed_ttl_days": 30,
  "switch_theta1": 0.2,
  "switch_theta2": 0.35
}
```

- `enabled=false` → 行为与现状**完全一致**（不建表不读表、注入回落锚点）。
- 任一异常（库锁/解析/超时）→ 保留旧状态，主链不受影响；日志 `[topic_state][step=…]`，不落原文。

### 4.7 测试计划（新功能必须附测试）

1. **状态机表驱动**：continue/switch/park/resume/close/timeout 六类转换 × 边界（θ 等值、空锚点、单话题、超 5 parked）。
2. **隔离**：A 用户/A 角色的状态绝不泄漏给 B；`user_key` 形态与运行时读取键一致（R7 教训）。
3. **容错**：坏 JSON/坏行 → 回落旧状态；表缺失 → 自动建表；DB 锁 → 不阻断。
4. **注入 A/B**：`enabled=false` 时 prompt 与现状逐字一致（diff 断言）；启用时块 ≤120 字且不含硬指令。
5. **judge（二期）**：不可用/超时/坏 JSON → 保留状态；预算耗尽只走确定性；不修改正文。
6. **主动线**：parked 复提受 6h+judge+静默三重闸；closed 不复提。
7. **黄金集**：新增 6~8 条「话题连续性」用例（跨轮锚点、换题、收尾、复提），确定性判定。
8. **突变验红**：禁用 continue/switch/park 任一条 → 对应用例必须变红。

## 5. 用户裁决（2026-10-27 已拍板）

| 裁决 | 用户选择 | 最终落地口径 |
|---|---|---|
| **Q1 状态更新方式** | **B：确定性状态机 + 稀疏 LLM** | 每轮先跑确定性转换；LLM 每 **4 轮**一次、后台、**8s 硬超时**、失败保留原状态；`judge_every_turns` 固定 4 |
| **Q2 注入强度** | **B+C 融合** | 注入状态块 + 明确接续指令 + **保留但软化**「同一话题通常自然聊 2~3 轮」；有明确新信息/用户换题时自然跟过去 |
| **Q3 主动复提** | **A：允许 parked 复提** | 三重闸：距上次话题 **≥6h** + 主动 **judge allow** + **非静默**；`closed` 永不主动复提；`recall_max=2` |
| **Q4 保留期** | **B：全部状态保留 7 天** | `topic_state` 的 active/parked/closed 全部 7 天 TTL；`topic_plan` 用 `next_at+24h` 短 TTL 防陈旧复活 |
| **Q5 成本** | **免费 API，不设每日 LLM 次数上限** | `daily_llm_budget=0`（不限）；保留每 4 轮稀疏触发，目的是控制质量而非成本 |
| **Q6 话题粒度** | **B：多 active 并行，上限 3** | `active_cap` 默认 3、允许 1..3；超限按 `(salience, last_active_at)` 低者淘汰到 `parked` |

> 实施结果见 `docs/reports/2026-10-27-话题状态机实施计划.md` §18（2026-10-28 收口）：4,180 收集 / 4,174 通过 / 4 失败 / 2 跳过；前端 251/251；ruff 0；**未部署**（**默认开启**，回滚走管理端显式 `topic_state.enabled=false` / `llm_judge_enabled=false`）。实际裁决 **Q1-B、Q2 B+C、Q3-A、Q4-B、Q5 不限、Q6-B**；原始选择题与推荐见 git 历史。

## 6. 负面边界（明确不做）

1. **不**引入图数据库/第二套记忆库（`memory_ext` 删除教训）。
2. **不**每轮调用 LLM；judge 只在灰区/每 N 轮/close 候选触发。
3. **不**增加用户可见延迟（更新走后台线程池，注入用 pre-turn 状态）。
4. **不**存用户原文全文；只存摘要 + ≤3 条短句锚点。
5. **不**复活追问链/焦虑驱动 follow-up（v1.44 D14 裁决）。
6. **不**替代现有出站守卫、去重、主动 judge、humanize 节奏机制。
7. **不**与 `reply_mode`/时间锚点竞争：状态块是数据段，不是又一段规则。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 状态漂移/误判 | active→parked 可逆、closed 也保留 30 天；judge 低置信度不改状态；确定性优先 |
| 双真源（与 `user_facts`/记忆层） | `topic_state` 只表达「当前对话进度」，不写事实；事实仍唯一记忆真源；不合并注入 |
| 用户隔离 | `session_key+character_id` 主键；跨用户/角色测试；日志不含原文 |
| 成本漂移 | 每 4 轮 + 日预算 20；预算耗尽只走确定性；观测降级计数 |
| prompt 竞争复发 | 状态块 ≤120 字；删除「至少 2~3 轮」硬指令；黄金集 + A/B |
| 并发写 | 单会话后台串行（after_chat 已有会话语义）；SQLite 事务 + 幂等 upsert |
