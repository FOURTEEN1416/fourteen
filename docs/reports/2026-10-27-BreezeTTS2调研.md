# BreezeTTS2 调研报告（Breeze TTS 2 · 集成设计事实底稿）

- **调研日期**：2026-10-27
- **调研目标**：查清 BreezeTTS2 的本体、能力、部署、资源、延迟、许可与托管 API 事实，为「是否/如何引入本项目」提供事实依据
- **结论置信度**：本体/许可/部署形态 **高**；中文音质与生产网络时延 **中低**（未实测）；宿主可行性中的性能判断凡未实测者均标注「推断」
- **一句话结论**：Breeze TTS 2 是 BreezeBlue 的 3B 英中双语 open-weight TTS，能力与延迟数据亮眼，但**权重许可为非商用**、自托管需要 12–24GB NVIDIA GPU、官方仓库只面向单请求推理；对本项目而言，**生产最现实的路径是托管 API，自托管必须同时解决 GPU 与商业许可两道门**。

## 一、它是什么

### 1.1 正身

**BreezeTTS2 = BreezeBlue（RESONIA, INC.）的 Breeze TTS 2**，一个面向实时交互的 **3B 参数、英中双语 open-weight TTS 模型**。

- 官方代码仓库：[`breezeblue-ai/breeze-tts`](https://github.com/breezeblue-ai/breeze-tts)（GitHub API：Apache-2.0，创建于 2026-08-25，截至 2026-10-27 约 963 stars / 129 forks）
- 官方模型页：[`BreezeBlue/Breeze-TTS-2`](https://huggingface.co/BreezeBlue/Breeze-TTS-2)（模型卡：3B params；Downloads last month 15,525）
- 官方发布页：[`breezeblue.ai/breeze-tts-2`](https://breezeblue.ai/breeze-tts-2)（博客标注 2026-08-07；模型卡 News 记 2026-08-25 发布权重与 PyTorch 推理代码）
- 官方产品站：[`breezeblue.ai`](https://breezeblue.ai/)
- 许可见下方 §2.4；**「open-weight」不等于开源许可**，权重是 BreezeBlue Research and Non-Commercial License v1.1。

| **B. 官方 `--fast-all`** | Linux + NVIDIA GPU | 24GB VRAM（14.4 GiB 占用） | RTF 0.32（H100） | 高 | 同上 | 质量/延迟最佳，成本最高 |
| **C. 社区 8GB recipe** | Windows / Linux + 8GB NVIDIA | 8GB VRAM；约 6.3 GiB reserved / 7.2 GiB peak | RTX 4060 Laptop：0.55–0.61s TTFA（Windows 原生）、0.21s（WSL2+FA） | 中高（triton-windows、MSVC、Inductor cache） | 同上 | 开发机可试；非官方、未验证 RTX 50 系 |
| **D. C++/GGUF 移植** | Windows/Linux x64（Vulkan GPU 或 CPU） | Q8_0 3.3GB / ~4GB VRAM；Q4_K 2.4GB / ~3GB VRAM | RTX 3060 Q8_0 ~1.5× 实时；带 guidance ~1.3× | 中（预编译包） | 代码 Apache；权重非商用 | Windows 最稳；生产仍需 GPU |
| **E. CPU-only** | Linux CPU | AVX2；Q4_K 权重 2.4GB（运行时内存未给） | **无公开 RTF**；按 3B 自回归 + 15 步深度解码推断，2–4 vCPU 远低于实时 | 中 | 同上 | 现生产服务器不可行 |
| **F. 托管 API** | 任意 | 无 | 官方 benchmark p50 127.2ms TTFA；实际含网络，需实测 | 低 | 付费计划商用；免费非商用 | **生产最现实** |

### 3.2 对两种宿主的初判（按本项目实况）

#### ① 生产 = Linux 云服务器（nginx + systemd + FastAPI 多 worker，无 GPU 记录）

**结论：现有生产服务器跑不动 Breeze TTS 2 自托管；不建议尝试。**

依据：
- 部署文档的硬件要求是 **RAM ≥4GB（推荐 8GB）、CPU ≥2 核（推荐 4 核）、磁盘 ≥20GB**（`deploy/README.deploy.md:14-16`）；没有 GPU 项。
- 生产安装记录明确使用 **`.venv-cpu`**（`docs/HANDOFF_REPORT.md:9`），即 CPU 环境。
- 官方 Breeze 要求 **CUDA NVIDIA GPU**，eager 显存约 **7.7 GiB**、`--fast-all` 约 **14.4 GiB**；官方 README 没有 CPU 支持承诺（[README](https://github.com/breezeblue-ai/breeze-tts#requirements)）。
- 即使改用 Q4_K GGUF（2.4GB 权重）走 CPU，3B 模型 + 每帧 15 步 depth decoder 的自回归解码，在 2–4 vCPU 上达到实时语音（RTF<1）的可能性很低；**这是推断，不是实测**，但足以判定「不能作为默认方案」。
- 官方仓库 issue #15 明确：**open-source repo 目前只面向单请求推理，不含生产级并发优化**；高并发/低延迟生产请用官方托管服务（[issue #15](https://github.com/breezeblue-ai/breeze-tts/issues/15)）。

> 若坚持生产自托管：需要新增一台 **12GB（eager）或 24GB（fast path）NVIDIA GPU** 的 Linux 机器，并接受**单请求推理 + 应用层队列**；多 worker FastAPI 不会自动提升吞吐，因为每个 worker 都要占一份 GPU 显存。商用还需 BreezeBlue 商业许可。

#### ② 开发机 = Windows（项目 Windows-first）

**本机实测（2026-10-27，`nvidia-smi`）**：`NVIDIA GeForce RTX 5060 Laptop GPU`，**8151 MiB 显存**（查询时空闲 4608 MiB），驱动 573.24，CUDA 12.8；系统内存 16GB，24 逻辑核。

**结论：可以用于「跑通/试听」级实验，但不能当作生产宿主；优先走社区 8GB recipe 或 GGUF Q8，不建议直接上官方 eager。**

依据：
- 官方 eager 需约 **7.7 GiB**，而本机总显存 8GB，查询时已有 3.2GB 被桌面/其他程序占用；直接跑官方 eager 很可能 OOM。
- 社区 8GB recipe 在 **RTX 4060 Laptop 8GB** 上实测约 **6.3 GiB reserved / 7.2 GiB peak**，说明「8GB 卡 + 关闭其他 GPU 应用」存在可行性（[RACErace](https://github.com/RACErace/breeze-tts-8g#windows-setup)）。
- 更稳的是 **HoppouAI C++/GGUF Q8_0**：约 4GB VRAM、RTX 3060 约 1.5× 实时；Windows/Linux x64 有预编译 Vulkan 包，CPU 也可 fallback（[HoppouAI](https://github.com/HoppouAI/Breeze-TTS-2.cpp#readme)）。
- ⚠️ 本机是 **RTX 5060 Laptop（Blackwell，sm120）**，上述社区实测是 RTX 4060（Ada）；**没有任何来源验证过 50 系**。另外 Windows 上 `flash-attn` 没有可靠 wheel，官方/社区都回退 SDPA，速度会低于 H100 数据。
- 官方 README 只写 Linux；Windows 是社区 fork 补的，**不是官方支持**。

#### ③ 托管 API 是否更现实？

**结论：是。对本项目当前「无 GPU Linux 生产 + Windows 开发机」的组合，托管 API 是唯一不需要新增硬件的生产路径。**

但需要先确认三件事：
1. **从生产服务器（中国大陆）到 `api.breeze.blue` 的实际网络延迟/可达性**——公开文档没有区域说明，必须实测；
2. **数据出境合规**：参考音频/文本发往美国公司 BreezeBlue，需评估 PIPL、用户同意、隐私政策；
3. **成本**：按 §2.5 的 $60/1M 汉字估算，先算清每月语音字数与并发峰值。

## 四、对集成的影响因素

### 4.1 P0：许可与宿主

1. **许可门（P0）**：Breeze 权重是 **非商用**；项目愿景包含 B 端 API/托管服务的商业化（`docs/VISION.md:29`）。因此「自托管 Breeze 权重用于 B 端产品」必须先拿商业许可，不能只看代码 Apache-2.0。托管 API 的付费计划输出可商用，但免费计划按 FAQ 不可商用（[Pricing](https://breezeblue.ai/pricing)）。
2. **宿主门（P0）**：现生产是 CPU-only、4–8GB RAM 的 Linux 服务器（`deploy/README.deploy.md:14-16`、`docs/HANDOFF_REPORT.md:9`），无法承载 3B TTS；自托管必须新增 12–24GB GPU 机器，托管 API 则不需要。

### 4.2 P1：工程接入面

3. **接入面很小（托管 API）**：项目已有 `TTSProviderBase.synthesize(text, **kwargs) -> SynthesizedAudio | None` 契约（`voice/tts_provider_base.py:30-31`），云端产 MP3、SAPI 产 WAV，格式必须如实标注（`voice/tts_provider_base.py:6-8`）。Breeze 托管 API 默认输出 **mp3**，可直接塞进现有 `SynthesizedAudio(fmt="mp3")`；`voice/audio_converter.py` 已有 MP3/WAV→SILK 的 ffmpeg 转换链（`voice/audio_converter.py:1-20`）。**首版适配器可以不改 orchestrator。**
4. **现有语音链路是「非流式、整段回复后合成」**：orchestrator 只在用户明确要求语音时触发（`_detect_voice_request`），取 `reply[:200]`，`await voice_mgr.synthesize(...)`（`orchestrator/optimized_orchestrator.py:2078-2080`）。Breeze 的流式优势要真正发挥，需要改成「LLM 边生成、按句送 TTS、边下发音频」；项目已有 `utils.stream_guard.IncrementalReplyGuard` 的句界能力，可作为二期。
5. **并发/队列**：Breeze 托管 Free 2 / Starter 4 / Creator 8 并发，超限 429（[Rate limits](https://docs.breezeblue.ai/reference/rate-limits)）；自托管官方 API 是单并发，batch 与流式共享单槽，冲突 409（[README](https://github.com/breezeblue-ai/breeze-tts#readme)）。`tts_manager.synthesize` 明确注释「无全局锁，支持并发合成」（`voice/tts_manager.py:128`），即没有对上游 TTS 并发做限流；多用户同时要语音时需要应用层 semaphore/队列，否则 429/409 会直接表现为「没声音」。
6. **音色策略与 voice slots**：项目现役 **42 张角色卡**（`AGENTS.md` §4.3）。Breeze 托管 voice slots：Free 5、Starter 20、Creator 50（[Pricing](https://breezeblue.ai/pricing)）。
   - 若「每个角色一个设计音色」→ 42 个，**Starter 20 不够，Creator 50 才够**；
   - 若「每个用户克隆自己的音色」→ 42 角色 × 用户数，很快超过任何个人套餐，需要 B 端/Enterprise 或改用「固定角色音色 + 不做用户克隆」。
7. **克隆前置条件**：Breeze 自托管克隆要求**参考音频 + 精确文本稿**；项目 ASR 当前是关闭的（`config/system.yaml:134-135` `asr.enabled: false`）。托管 Breeze 的克隆会自动转写（3 秒起、5MB 上限、只取前 60 秒/最多 30 秒），自托管则要自己补 ASR 或让用户提供文本。用户音色还涉及**声音同意/授权**，Breeze 许可也要求对参考音频拥有全部权利（[HF LICENSE §5(c)(d)](https://huggingface.co/BreezeBlue/Breeze-TTS-2/blob/main/LICENSE)）。
8. **格式与微信通道**：Breeze 托管 mp3 → 现有 ffmpeg→silk 链路可用；若走自托管官方 API，输出是 **24kHz s16le PCM**，需要先封装 WAV/MP3 再转 silk，不能直接当 mp3 用。
9. **失败模式与降级**：Breeze 的 429/503/402 需要有明确降级（文本回复、预生成音频、或另一个 TTS）；项目现有 MiMo 的降级链在 Linux 上是**断的**——SAPI 只在 Windows 可用，非 Windows 直接 `return None`（`voice/mimo_tts_provider.py:320-322`），`tts_manager` 随后报「所有TTS引擎均失败」。任何云端 TTS 方案都不应把「本地 SAPI」当作 Linux 生产的兜底。
10. **数据合规**：BreezeBlue 是美国公司（特拉华州法），公开文档未给中国大陆区域/数据驻留承诺；参考音频属于敏感生物特征数据，跨境传输需法务确认。MiMo 是小米国内平台，这是现状方案的一个隐性优势。

### 4.3 与 MiMo 的迁移/并存判断

- **质量**：独立 Artificial Analysis（2026-10-27）Provider Voice Arena：Breeze TTS 2 **总榜 #11、Elo 1227**；开源权重榜 **#2、Elo 1227**（落后 Fish Audio Drama 3 Preview 1245）；MiMo-V2.5-TTS **#64、Elo 1054**（[Provider Voice](https://artificialanalysis.ai/text-to-speech/leaderboard/provider-voice)、[Open Weights](https://artificialanalysis.ai/text-to-speech/leaderboard/provider-voice/open-weights)）。
- **克隆质量**：AA Controlled Voice（8 个英文克隆音色）：Breeze **#25、Elo 1022**；MiMo 未上榜（[Controlled Voice](https://artificialanalysis.ai/text-to-speech/leaderboard/controlled-voice)）。这说明 Breeze 的强项更偏「原生音色/音色设计/导演」，**不是英文克隆绝对第一**；中文克隆没有独立数据。
- **克隆鲁棒性**：官方仓库 issue #14 记录跨语言克隆的输出崩塌/发音不稳，官方归因于 RTX 2080 Ti（Turing，无原生 BF16）与参考音频/文本不匹配；说明克隆链路对输入质量和 GPU 代际敏感，生产需做参考音频质检与种子复测（[issue #14](https://github.com/breezeblue-ai/breeze-tts/issues/14)）。
- **功能**：Breeze 有 51 语言托管版、8 种中文口音（含粤语）、34 种音频事件、音色设计/导演；MiMo 有中文原生音色、方言、导演模式、唱歌，但内置音色只有 4 中文 + 4 英文，克隆/设计的「流式」是兼容模式（全量推理后一次返回）（[MiMo 文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/audio/speech-synthesis-v2.5)、[MiMo 模型页](https://mimo.mi.com/models/en-US/mimo-v2.5-tts)）。
- **成本**：MiMo TTS 目前**限时免费**（官方定价页 2026-10-20 更新仍写 Free for a limited time）；Breeze 是 $30/1M 计费字符、中文约 $60/1M 汉字。**免费期结束后 MiMo 的价格未知**，这是现状方案最大的成本不确定性。
- **可用性**：MiMo 模型页标称 `mimo-v2.5-tts` **RPM 100 / TPM 10M**、8K context / 8K max output；Breeze 托管按并发套餐限流、无公开 RPM。两者都需要应用层限流/重试，但 Breeze 的 429/503 语义更明确。
- **接入**：MiMo 是 OpenAI 兼容的 `chat/completions` + `audio` 参数；Breeze 是自定义 REST（`/v1/text-to-speech/{voice_id}`）+ 官方 SDK。项目现有 MiMo provider 走 `/audio/speech` JSON（`voice/mimo_tts_provider.py:42-46,172-178`），而当前官方 MiMo TTS 文档示例走 `/chat/completions`（[MiMo API](https://mimo.mi.com/docs/en-US/api/audio/tts)）——**两条口径是否完全等价，需要实测确认**。

## 六、未确认事项（集成设计前必须先确认）

1. **商业用途边界**：本项目是否会把 TTS 用于 B 端 API/托管服务（`docs/VISION.md:29` 已写「增值层商业化」）？若会，**自托管 Breeze 权重必须先取得 BreezeBlue 商业许可**；请确认是「只做 C 端免费」还是「B 端也会用」。
2. **生产算力预算**：是否允许新增 **12GB（eager）/ 24GB（fast path）NVIDIA GPU** 的 Linux 机器？还是只接受托管 API？这决定方案 A/B/C/E 是否进入候选。
3. **语音策略**：42 个角色是「每个角色固定一个设计音色」（Creator 50 slots 可覆盖）还是「每个用户克隆自己的音色」（voice slots 会爆炸）？这直接决定套餐与成本。
4. **是否需要真流式**：产品是否要求「LLM 边说边出音频」？还是「整段回复后合成」可接受？若要真流式，需要改 orchestrator 的句级管线；若不需要，首版适配器可以极简。
5. **月语音量与并发峰值**：每月大约多少汉字/多少并发用户？用于计算 Breeze credits、套餐和 429 风险；目前项目没有 TTS 用量统计。
6. **跨境数据合规**：用户参考音频/聊天文本发送到美国 BreezeBlue 是否满足 PIPL、隐私政策与用户同意？需要法务确认；若不允许，托管 API 直接出局，只能自托管（且仍需商业许可）。
7. **Breeze 托管 API 从生产服务器（中国大陆）的实际可达性与延迟**：公开文档没有区域承诺；需要拿试用 key 从生产机实测 TTFA/失败率，不能只看 H100 数据。
8. **MiMo TTS 的后续价格与生命周期**：当前「限时免费」；页面顶部又有 MiMo-V2.5 语言模型 2026-10-21 退役公告（TTS 系列未在名单，但版本生命周期需确认）。同时确认项目使用的 `/audio/speech` 与官方文档 `/chat/completions` 是否仍等价。
9. **RTX 5060 Laptop 8GB（Blackwell sm120）兼容性**：社区 8GB recipe/GGUF 的实测都是 RTX 4060/3060；需要在本机做一次 Q8_0 GGUF 或 8GB recipe 的 RTF/显存实测，才能判断开发机能否承担试听/批量预生成。
10. **中文女声/角色音色克隆的验收标准**：目前没有独立中文克隆评测；需要定义听评人、样本集、MOS/偏好阈值，否则「Breeze 比 MiMo 好」无法验收。

## 七、结论与建议（供集成设计，非事实）

1. **短期（不新增硬件）**：用 Breeze **托管 API** 做 POC，只替换 `TTSProviderBase` 的 `synthesize` 实现，输出 mp3 走现有 `SynthesizedAudio` + ffmpeg→silk 链路；先选 1–2 个角色、固定 2 个设计音色，验证中文女声主观质量、从生产机到 `api.breeze.blue` 的延迟、429 频率和成本。
2. **中期（如果质量/成本过关）**：再评估「42 角色固定音色」的 Creator 套餐（50 slots），或 B 端商业许可 + 自托管 GPU；不要在没有商业许可的情况下把 Breeze 权重接进 B 端托管服务。
3. **Windows 开发机**：优先用 **HoppouAI C++/GGUF Q8_0** 做本地试听/批量预生成（约 4GB VRAM），不要直接上官方 eager（7.7GiB，8GB 卡太紧）；RTX 5060 需要先实测。
4. **不建议**：在当前 CPU-only、4–8GB RAM 的生产服务器上尝试 Breeze 自托管；也不要把 Windows SAPI 当作 Linux 生产的兜底。
