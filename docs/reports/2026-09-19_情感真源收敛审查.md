# 情感真源收敛审查（经历因果升级机制 P0 前置审计）

> **状态卡**：`derived` · 只读代码审计报告 · 2026-09-19
> **性质**：纯审查，零代码改动。本报告是「经历因果升级机制研究」P0 批次的前置阻塞项：**先收敛真源，再上新机制**。
> **审计方法**：逐文件实读 + 全仓 grep 接线追踪（调用点/持久化点/实例化点三向交叉），证据全部给出 file:line。
> **对照基线**：CODE_GRAPH v3.8.3（204 端点/1082+87 测试口径）；2026-09-15 体检记忆中"四套情感/好感度真源并存"的模糊判断在本报告中精确化。

## 〇、一句话结论

表面上的"四套情感真源并存"实为 **「1 主 3 仆 + 大量孤儿状态副本 + 全族无持久化闭环」**：`EmotionEngine.affection_points` 是事实上的唯一主源，`shisi affinity`/`emotion_stage` 由它派生，`vital_signs` 是热路径零调用的幽灵系统；而**整个情感状态族没有任何组件在重启后恢复状态**——亲密度与情绪在进程重启时一致地归零。

## 一、真源族盘点（五个系统逐一）

### 1.1 EmotionEngine（`my_character/emotion_engine.py`，849 行）—— 事实主源

| 项 | 实况 |
|---|---|
| 状态载体 | `CompoundEmotionalState`（emotion/intensity/energy/affection/affection_points），`self._state` + `self._emotion_history`（:498/:556-568/:817） |
| 持久化 | **零**。无 sqlite/json.dump/文件落盘（全文件 grep 证实）；`get_history()` 返回内存 deque 快照 |
| 主导数值 | `affection_points`（0~500 刻度，满级 = `AffinityLevel.BOND.threshold`，见 `shisi/affinity/mapper.py` 头注释） |
| 实例化点 | **4 处**：① `orchestrator/_init_mixin.py:135`（`components["emotion"]` 模板）；② `user_scheduler.py:108`（由模板派生配置，`_get_character_engine()` 每"用户×角色"一个，LRU 上限 8，永不淘汰活跃——2026-09-17 修复注释）；③ `orchestrator/optimized_orchestrator.py:578`（请求级 `_request_emotion_engines`，TTL 淘汰）；④ `my_character/persona_engine.py:185`（PersonaEngine **自带**一个） |
| 判定 | **主源但多实例**：调度器的 per-user 引擎、请求级引擎、persona_engine 内嵌引擎是三个互不同步的状态空间 |

### 1.2 AffinityEnhancer + AffinityMapper（`shisi/affinity/`，298 行）—— 派生源（带审计写）

| 项 | 实况 |
|---|---|
| 状态载体 | `self._values: dict[str, float]` 内存字典，**播种恒 0.0**（`enhancer.py:36-42`），无任何启动回读 |
| 持久化 | 写 SQLite `data/sqlite.db` 的 `affinity_records`（old/new/delta/reason/source）+ `affinity_audit` 两表（`enhancer.py:83-103`）；**全仓 grep：这两表只有 INSERT，零 SELECT**——append-only 审计，不是真源回读 |
| 派生关系 | `AffinityMapper.sync()`（`mapper.py:92-117`）：`target = affection_points / BOND_THRESHOLD × max_value`，与上次同步值求差分（clamp ±3）→ `enhancer.update()`。**shisi affinity 是 EmotionEngine 的投影** |
| mapper 自身状态 | `self._last_shisi` 内存字典（`mapper.py:31`）——同样重启归零 |
| 装配单点 | `shisi/api/registry.py:80`（`reg.affinity_mapper`）；热路径消费点 `optimized_orchestrator.py:885-900`（`_after_process` 中经 `api.deps.shisi_reg.affinity_mapper.sync(...)`）——**热路径与 API 共用同一 registry 单例**（本次审查澄清了"两套实例"的疑点：不成立） |

## 二、风险清单（按严重度）

| # | 风险 | 证据 | 严重度 |
|---|---|---|---|
| R1 | **重启全归零**：EmotionEngine（内存态）+ AffinityEnhancer._values（播种 0）+ mapper._last_shisi 全部不持久；`affinity_records` 只写不读。用户长期养成的亲密度在服务重启/部署后清零（两侧一起归零所以"看起来一致"，掩盖了问题） | enhancer.py:36-42/:83-103；全仓零 SELECT | **高** |
| R2 | **多 worker 状态分叉**：uvicorn 4 worker 各自持有独立的 EmotionEngine 族与 AffinityEnhancer._values（内存 per-process）；微信消息与 API 读写落在不同 worker 时数值互不相见。与 2026-07-28 已修的"4 倍主动消息"同构，但情感状态域**没有**等价的 flock 单写者保护 | user_scheduler.py:95-135；CODE_GRAPH §14 flock 先例 | **高** |
| R3 | **VitalSigns 幽灵端点**：`GET /api/shisi/vital-signs/{id}` 返回恒 default 的假状态 | registry.py:92；热路径零调用 | 中 |

## 三、收敛方案建议（P0 成文草案，**不实施**）

> 原则：不新开第五套真源；让现有写入路径收敛到一个账本式 owner；派生量保持派生。

| # | 建议 | 说明 | 对应风险 |
|---|---|---|---|
| S1 | **定主源**：`affection_points`（per 用户×角色）为唯一权威数值，EmotionEngine 为其唯一持有者 | 现状事实上已如此（mapper 单向派生），只需成文确认 + 消灭 1.1-④ 的孤儿实例 | R4 |
| S2 | **账本化持久**：把 `affinity_records` 升格为事件账本的雏形——补**启动回读种子**（SELECT 每 character 最后 new_value 灌回 `_values`），并为 emotion 转移/energy 变更补同构事件表 | 不新表也行：先给 affinity_records 加回读，是最小闭环 | R1 |
| S3 | **单例装配**：情感引擎族唯一 owner = `shisi_reg`（registry），`persona_engine` 的内嵌 EmotionEngine 改为注入共享；请求级引擎（optimized_orchestrator:578）确认其状态是否需要合并回主链 | 热路径已经走 shisi_reg（optimized_orchestrator.py:893 实证），顺势收拢 | R2/R4 |
| S4 | **多 worker 防线**：情感状态写沿用 flock 单写者先例（scheduler 域已验证的模式），或账本写统一走 master worker | 参照 CODE_GRAPH §14 `_ensure_scheduler_singleton` | R2 |
| S5 | **vital_signs 二选一**：接线（`update_on_emotion` 挂进 `_after_process`，与 emotion 转移同帧）或封存（下架端点 + 前端入口，入 DELETION_LOG，参照 09-18 死模块先例） | 不允许继续"有端点、无驱动"的中间态 | R3 |
| S6 | **快照写回核实**：排查 `PersonaBank.update_persona_with_snapshot` 与 aggregate.emotional_state 的同步点，要么接通要么在文档标注"快照仅为导入时初始值" | 先核实再定级 R5 | R5 |

**收敛后再上事件账本（机制研究 P0 主项）**：账本 schema（事件类型/时间/主体/对象/变更量/溯源）以 `affinity_records` 的五元组为起点扩展，避免 schema 推倒重来。
