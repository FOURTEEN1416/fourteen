## 0. 结论摘要

1. **本仓不是「拟人化空白」，而是「工程层已有骨架、节奏层缺两块、状态层偏薄」**。已覆盖的包括：真流式增量守卫、终审守卫、时间锚点 + 6 小时会话分段、主动 60/15/4 三道闸 + 23–7 静默、沉浸式/小说式按用户覆盖、称呼白名单、拆条 + 段间打字延时（《测绘》§2.1–§2.6）。
2. **最值得补的两块都在工程层，且都必须是工程机制、默认关闭、可灰度**：① 生成前的「阅读延迟 + typing 输入状态 + 活跃响应曲线 + supersede 显式契约」；② 拟人度配置的声明式 schema 与按用户覆盖（防 v1.56 R7 那类「写入键与运行时读取键不一致」的键漂移）。
3. **历史教训是硬约束**：v1.54/v1.55 的结论是「把像真人拆成互相竞争的硬指令」会恶化质量（AGENTS v1.54/v1.55、`docs/verification/2026-10-20-chat-quality-fullchain-diagnosis.md:65-78`）。因此本方案把所有「再加 prompt 规则」的建议降级为 P2 或直接判「不适合」，优先调度/工程/数据层。
4. **不建议做的事**：引入 DSH 运行时、直接安装 ★4 的 `dsh-im-humanize`、默认开启阅读延迟、完整打字时长模拟、故意打错字、把 `humanizer`/`lieflat` 清单塞进聊天主 prompt、复活已退役的追问链、把群聊注意力/疲劳/沉默状态机搬到一对一陪伴。
5. **实施按 5 批推进（0–4），每批独立可回滚**：批次 0 观测基线 → 批次 1 humanize schema/按用户覆盖 → 批次 2 阅读延迟 + typing + supersede（opt-in 灰度）→ 批次 3 主动增强 → 批次 4 P2 只读评估。每批均要求新增测试并通过 AGENTS §4.3 全量基线（当前口径 3900 收集 / 3898 通过 + 2 跳过 / 250 测试文件 / 42 卡；vitest 217/217、33 文件；ruff 0）。

## 1. 判定骨架与口径

### 1.1 七层模型（《生态调研》§2.0）

| 层 | 回答的问题 | 本仓总体判断 |
|---|---|---|
| **R 节奏层** | 怎么发？发几条？隔多久？ | 拆条/段间延时已覆盖；**阅读延迟、typing、活跃响应曲线缺失** |
| **T 时机层** | 什么时候说？要不要主动说？ | 主动三闸/静默/日上限已覆盖；jitter、静默退出墓碑缺失；群聊注意力类不适用 |
| **L 语言层** | 说什么样的话？ | 回复模式/角色卡已覆盖；表达库可长期借鉴；纯 prompt 加规则一律高风险 |
| **E 状态层** | 带着什么心情/关系说？ | 情绪引擎/连续性已覆盖；per-emotion 衰减、bond/trust 双刻度需改造借鉴 |
| **M 记忆层** | 凭什么记得？记得多牢？ | 三层记忆/检索/遗忘/记忆工具已覆盖；类型化 TTL、剧情分支 WAL 可改造借鉴 |
| **A 抑制层** | 什么不该发？ | 终审/增量/系统标记/复述/元解释/称呼守卫已覆盖；post-draft judge 可借鉴 |
| **I 临场层** | 在什么界面/身体里说？ | 角色卡/语音已覆盖；手机 UI、Live2D、语音打断属产品形态，当前不适用 |

### 1.2 判定四分类与优先级

- **已覆盖**：本仓已有实现且经《测绘》坐标核对；标注「**勿重复引入**」，只允许做参数级/可观测性增强。
- **可直接借鉴**：外部机制可 1:1 映射到本仓既有模块，工程量小、语义清晰。
- **需改造借鉴**：机制方向对，但必须适配本仓的数据模型/许可/产品形态，不能照搬。
- **不适合本项目**：与产品形态、用户裁决、许可证或历史教训冲突，明确不做。
- **优先级**：P0 = 不做会阻塞后续或已有明确缺陷风险；P1 = 高 ROI、可在 1–2 批内落地；P2 = 长期/需产品裁决。**已覆盖/不适合项不进入排期，优先级列记「—（已覆盖）」或「—（不做）」**；其余可执行项均给 P0/P1/P2。
- **Owner 口径**：下表「Owner」均按 AGENTS §2 Owner Map 的模块归属（编排开发/集成开发/语音开发/主动开发/工具开发/后端开发/前端开发/角色开发/记忆开发/知识开发/QA/运维开发/部署开发），不另立新 owner。

### 1.3 历史教训红线（本方案的最高约束）

> v1.54/v1.55 的生产结论：模型不是缺规则，而是**规则太多、互相竞争**；爱语 2.8.8 的 43 条提示词里「反问/追问/话题/复述/确认一下/你呢」全部为 0（《测绘》§5；AGENTS v1.54）。因此：
>
> 1. 任何「往 system prompt 再加一条」的建议，优先级自动降为 P2，并在风险栏标注「**高风险：可能重复 v1.54/v1.55 质量悬崖**」。
> 2. 能放到调度器、传输层、状态机、数据层的，不放到 prompt。
> 3. prompt 只保留「声音」和「边界」；「何时说、说几条、隔多久、记住什么、什么不该发」全部工程化。

## 3. P0/P1 机制详情卡

### 3.1 P0-A：拟人度声明式 schema + 按用户覆盖（G-1/G-2）

**做什么**
- 把 `utils/humanize_config.py` 现有 `DEFAULTS`/`INT_BOUNDS`/`WRITABLE_FIELDS` 收敛成一张 `HUMANIZE_FIELDS` 表：字段名、类型、默认值、边界、是否可写、是否 per-user、UI 标签。
- 增加 `user_humanize` 覆盖表（SQLite，键 `user_key`），读取顺序：用户覆盖 → 全局 `humanize` 块 → 默认值。**「键缺失 = 继承」**，不是「缺失 = 钉死默认」。建表用 `CREATE TABLE IF NOT EXISTS` 幂等迁移，不删旧键、不改旧行。
- API 写入严格校验（非法值 400），磁盘手改宽松修复（坏值回落默认并记 warning）。

**为什么**
- v1.56 R7 的 P0 是「admin 指定用户写入键形态与运行时读取键不一致，功能无效却回执成功」（AGENTS v1.56）。DSH `humanize-schema.mjs` 的「缺失=继承 + 严格/宽松双校验」正是防这类键漂移的工程答案（《DSH 专项》§2.2.9）。

### 3.2 P0-B：阅读延迟 + typing + 活跃响应曲线 + supersede（R-3/R-4/R-5/G-3，一体上线）

**做什么**
- 新增 `utils/humanize_read_delay.py`：
  - `compute_read_delay(idle_ms, text, cfg) -> int`，公式对齐《DSH 专项》§2.2.3/§2.2.4：`base = activity_boost(idle) or uniform(min,max)`；`reading = visible_len / chars_per_second * 1000`；`result = min(base + reading, max_total, channel_cap)`。
  - 默认 `min=1000ms`、`max=6000ms`、`chars_per_second=0`（长度项关闭）、`max_total=30000ms`；无 typing 能力的渠道 `channel_cap=5000ms`。
  - `idle_ms is None`（首条消息）→ 完整 `uniform(min,max)`，不加速。
- orchestrator 在 `process_message` 调 LLM 前 `await apply_read_delay(...)`；延迟结束启动 typing 会话；生成/发送结束 `finally stop()`。**覆盖范围（首版声明，自独立复验低severity意见补）：仅接入非流式主链 `orchestrator/optimized_orchestrator.py` 的 `process_message`（微信等通道）；`chat.stream_mode: true` 的流式路径 `orchestrator/_stream_mixin.py:216-245`（`process_message_stream`，Web/SSE/WS）首版不应用延迟与 typing，扩展列入后续批次（P1）。**
- `wechat_direct` 增加 `sendtyping status=1/2` 的薄封装；失败只记 debug，不影响发送。
- supersede：延迟期收到同一会话新消息 → 旧回合标记 `superseded`，静默取消（无生成、无发送、无失败提示）；实现放在 orchestrator 回合状态机，复用 `ProcessSessionLock` 的会话键。

**为什么**
- 当前「段间延时」只发生在生成之后；用户感知的「秒回」主要来自生成前零延迟（《DSH 专项》§4.1/§4.2）。
- typing 能显著缓解长延迟负效应，但「完整打字时长模拟」反而有害（Schanke 2021，见《DSH 专项》§2.2.11/§4.4）。

**落点 / Owner**
- `utils/humanize_read_delay.py`（新，Owner：工具开发）
- `orchestrator/optimized_orchestrator.py`（Owner：编排开发）
- `wechat_direct/wechat_connector.py`（Owner：集成开发）
- `config/system.yaml` / `utils/humanize_config.py`（Owner：工具开发）

**默认与灰度**
- `read_delay.enabled=false` 默认关闭；admin 打开后按 `user_key` 灰度（1%→10%→50%→100%）。
- 灰度指标必须按通道拆分（微信/非流式 vs 流式 Web）：流式路径首版未生效（见上「覆盖范围」），混入会稀释 A/B 结论。
- 先只对「非语音、非主动、非提醒」的普通文本回合生效；主动/提醒链不启用（避免延迟叠加）。
- 无 typing 能力时 `channel_cap=5000ms`；iLink `sendtyping` 未验证前不上 typing。

**测试**
- `tests/test_humanize_read_delay.py`（新）：`compute_read_delay` 边界（idle None/0/60/120/300s）、封顶、无 typing 5s cap、非法配置回落。
- `tests/test_humanize_supersede.py`（新）：延迟期新消息→旧回合取消、无发送、无双回复；不同会话互不影响。
- `tests/test_wechat_typing.py`（新，若有 iLink mock）：start/stop 恰好一次、失败 no-op、无接口不抛错。
- 现有 `tests/test_true_streaming.py`、`test_main_stream.py` 回归。

**回滚**：`read_delay.enabled=false` + `typing.enabled=false`；无需迁移；重启生效（TTS/编排配置非热重载，《测绘》§2.8）。

**验收指标**
- P50 首字延迟 2–6s、P90 ≤12s（无 typing 时 ≤5s）；`superseded` 回合零发送、零双回复；typing 成功率 ≥99%；用户负反馈率不高于基线。

### 3.3 P1-A：主动 jitter + 静默退出墓碑（T-4/T-5）

**做什么**
- 在 `proactive/scheduler.py` 计算下一次触发时间时加 `uniform(0, jitter_seconds)`；`jitter_seconds=0` 时行为不变。
- 决策 `should=False` 且无等待语义时，写一条可折叠的 `proactive_reclaim` 墓碑（只记原因/时间/会话键，不写正文），避免下一轮重复唤醒同一话题。
- 不动 T-1/T-2/T-3 的 60/15/4、23–7、日上限。

**落点 / Owner**：`proactive/scheduler.py`、`proactive/llm_proactive.py`（Owner：主动开发）。

**测试**：jitter 分布边界（0/上限/负值回落）；墓碑键形/清理；现有 `tests/test_proactive_window_expiry.py` 回归。

**回滚**：`proactive.jitter_seconds=0`、`proactive.tombstone_enabled=false`。

### 3.4 P1-B：主动消息 post-draft judge（A-4，成本待裁决）

**做什么**
- 在主动消息正文已 sealed、投递前，调用一次独立小模型 judge，只输出 `allow/drop`，**不允许改写正文**；judge 不可用/超时/解析失败 = **drop（fail-closed）**。
- judge 输入：候选正文 + 最近 5 条对话摘要 + 当前时间/静默状态；不输入完整人设（避免 judge 变成第二作者）。
- 记录 `proactive_judge` 账本：`allow/drop/reason/model/latency`。

**为什么**：主动消息错误成本远高于被动回复；`private_companion` 的 persona judge 是 fail-closed（《生态调研》§3.1.4）；「post-draft judge 只判发/不发」的建议来自**《生态调研》§4.2 P0-4**（DSH 报告 §4.2 的 P0-1～P2 清单没有这一项，不能记到 DSH 账上）。`private_companion` 无 LICENSE（默认版权保留，《生态调研》§3.5/§5.1），只可机制借鉴、不可抄代码；实现须独立重写。

**落点 / Owner**：`proactive/` 新模块（Owner：主动开发）+ `api/byok` 模型调用（复用 `utils.llm_bridge.request_llm`）。

**成本/风险**：每条主动消息多一次小模型调用；可能误杀好消息；judge 与主模型同源会同错。**列为 Q3 待用户裁决**。

**测试**：judge 不可用→drop；allow→投递；drop→不投递且账本；不修改正文；超时；现有主动链测试回归。

**回滚**：`proactive.judge_enabled=false`。

### 3.5 P0-C：观测与灰度底座（G-5）

**做什么**
- 在 orchestrator/wechat/主动链增加结构化日志字段：`read_delay_ms`、`idle_ms`、`typing_started/stopped`、`superseded`、`segment_count`、`segment_delay_ms`、`proactive_jitter_ms`、`reply_guard_hit`（已有）。
- 复用 `quality_degraded` 类日志惯例（AGENTS v1.55）：降级/跳过必须带 `engine/fallback/reason`，不落用户原文。
- 所有新机制一个总开关 `humanize.experimental_enabled`，默认 false。

**测试**：日志字段断言（caplog）；开关关闭时行为与基线完全一致（A/B 对照）。

## 6. 待用户裁决

> 编号与汇总索引统一。产品形态/花钱/换供应商类问题一律不越权自决。

- **Q1 阅读延迟 + typing 是否上线？**
  - A. 上线，默认关闭 + 灰度（推荐）：收益是消除秒回机器感；代价是首字变慢，需 1–2 周灰度。
  - B. 只上 typing，不上延迟：风险最低，但「秒回」仍在。
  - C. 都不上：保持现状，接受机器感。
- **Q2 humanize 是否做按用户覆盖？**
  - A. 做（推荐）：不同用户不同节奏；代价是多一张表 + 管理端复杂度。
  - B. 保持全局：简单，但无法兼顾「喜欢快」与「喜欢慢」的用户。
- **Q3 主动消息是否加 post-draft judge（多一次小模型调用）？**
  - A. 加，fail-closed（推荐）：主动消息错误成本高；代价是每条多一次调用/延迟。
  - B. 不加：只用现有确定性守卫；代价是错误主动消息仍可能发出。
  - C. 只对高价值主动类型加：折中，但规则复杂。
- **Q4 是否接受 1–2% 错别字/口语瑕疵？**
  - A. 不接受（推荐）：信任风险；B. 仅沉浸模式可选；C. 接受。
- **Q5 是否进行情绪/关系 schema 改造（per-emotion half-life、bond/trust 双刻度）？**
  - A. 暂不做，先观测（推荐）；B. 做 P2 改造；C. 只做只读评估。
- **Q6 是否放宽拆条 2 段上限/引入 `message_break`？**
  - A. 保持 2 段（推荐，现行用户裁决）；B. 放宽到 3–4 段并做模型断点；C. 仅实验环境评估。
