# 单一个体 Agent 架构：调研与设计

> 日期：2026-11-10
> 触发：用户裁决——「向着一个完整的独立的个体去发展，并且向着 agent 化执行……现在的各种能力，升级为真正的 tools 调用……核心的角色扮演能力不能丢，角色和人设相当于它的灵魂，设计出能够将其中的灵魂进行替换，但是外部各部分都能正常运行的一套架构」。
> 前置：`docs/reports/2026-11-10-出站发声架构现状与统一方案.md`（现状审计）。
> 状态：**调研 + 设计，零代码变更**。

---

## 1. 目标（把用户的话翻译成架构约束）

| 用户表述 | 架构约束 |
|---|---|
| 一个完整的独立的个体 | 同一时刻只有一个发声者；所有输出都出自同一个 agent 实例 |
| 各种能力升级为真正的 tools | 发消息、语音、记忆、提醒、日程、知识检索都是工具调用，不是并列的代码管线 |
| 不像一个人 = 解离 | 不允许"调度器生成文案"；调度器只能投递**事件** |
| 角色扮演是灵魂 | 人设/口吻/边界是**一等状态块**，由它决定一切表达的形态 |
| 灵魂可替换、外部照常运行 | Soul 与 Capabilities/Transport/State 解耦；换 Soul 不改任何外部代码 |

## 2. 外部调研（GitHub-First，逐项验证）

### 2.1 主动型 agent：调度器只"唤醒"，不"生成"

- **LangChain《Why aren't you building proactive agents yet?》**：主动 agent 由两部分构成——① 健壮的 cron server；② agent-friendly 的界面。关键表述：一次定时运行"**只是一个在计划时刻触发的 prompt，thread 与 memory 属于创建该计划的 principal**"。→ 调度器的职责是**唤醒 agent**，不是自己写文案。
- **OpenClaw `docs/automation`**：Automations = 内置调度器，"**wakes the agent at the right time**, and can deliver output to a chat channel"；另有 Heartbeat（周期性自检）与 Standing Orders（常驻授权，注入每个会话）。
- **OwnPilot `docs/TRIGGERS.md`**：触发器（schedule/event/condition/webhook）触发后执行 **action**，action 的一种就是"**sending a chat message through the agent**"或"calling a tool"。
- **PraisonAI issue #3058**：把"调度存储"做成协议、但"何时触发"焊死在轮询线程，被明确视为架构缺陷——**触发源应当可插拔**。

> 对本仓的意义：`scheduler` 现在同时承担"何时说"和"说什么"（`decide_proactive` + `_deliver`），这正是解离的根源。应降级为纯触发源。

### 2.2 状态化 agent：人格是"状态块"，可替换

- **Letta（MemGPT）memory blocks**：core memory 是"**persist across all interactions**、在上下文窗口里始终可见（无需检索）"的结构化块；`persona` 与 `human` 是约定俗成的两个 block label；persona 存"关于你当前人格的细节，指导你如何行为和回应"；block 可 attach/detach、可共享、可设只读，**更新 value 会整体替换内容**。
  → 这就是「灵魂可替换」的工程落点：**Soul = 一个可整体替换的 persona block**，其余能力不认识它的内容。

### 2.3 事件溯源：让"一个人说过什么"可回放、可投影

- **SageKit / BAML《Event-driven agentic loops》**：不要原地修改会话状态——**记录每一个用户输入、工具结果、LLM chunk**，再把事件流投影成 UI、prompt、持久化三个独立视图；线性 agent loop 在需要打断/排队/审批时会崩。
- **Daemora VISION**：有 **Shadow Mode**（agent 推理但不执行，产出"我本来会做什么"日报）与 **Brain export/import**（可分享的 agent 配置：memory + goals + watchers + cron + skills）。

> 对本仓的意义：`chat_history` 是"投影"，不是事件日志；它丢了工具调用、丢失原因、线程归属。需要一层 append-only 事件。

### 2.4 本地对照实现：爱语 2.8.8（逆向，`D:\Desktop\爱语逆向`）

`work/产物/aiyu_prompts_full.json`（43 条真实 prompt）暴露了它的架构：

- **一个 persona 管线**：`PersonaManager` →「📝 构建 System Prompt -> 当前人设」，主动消息按「**人设ID匹配**」进入同一条管线。
- **能力 = 内联标签工具**（同一条输出流里调用）：`<add:>`（写记忆）32 处、`<search:>` 11、`<voice:>` 6、`<post:>/<like_moment:>/<comment_moment:>/<get_my_moments>/<get_user_moments>`、`<note:>`、`<generate_image:>/<edit_image:>`、`<look_screen:>`、`<get_foreground_app>`、`<force_lock>/<force_vibrate>`、`<get_all_usage>`。
- **明确的"个体"指令**：`【思维链通用指令】`第一条——「你**不是在扮演**，你就是那个名字/物种/性格的个体」；第二条——「**所有系统功能（如存档、检索、发动态）直接视为自己的心理活动或本能动作，不是"外部指令"**」。
- **输出形态**：`【多段落输出规则】`要求每个段落回车分隔。

> 结论：参考产品的"像一个人"不是靠更多规则，而是靠**一个 prompt + 自己的输出里调自己的工具**。它没有"主动决策 prompt"和"聊天 prompt"两套人格。

### 2.5 范式收敛

四类来源指向同一个形状：

```
Trigger（何时） ──► Agent Core（唯一发声者） ──► Tool Calls（能力）
                        │
                        └── State（soul / memory / threads / commitments）
```

## 4. 目标架构

### 4.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ L4 Triggers（只投递事件，不生成任何文本）                       │
│  inbound_message │ proactive_tick │ reminder_due │ date_due   │
│  manual_command                                              │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ L3 Agent Core（唯一发声者，每个 user_key × character_id 一个） │
│  turn loop: assess → (optional tool calls) → speak/end_turn   │
└───────┬───────────────────────────────────┬──────────────────┘
        │                                   │
        ▼                                   ▼
┌─────────────────────────┐   ┌──────────────────────────────────┐
│ L2 Tools（能力）         │   │ L1 State（单一真源）             │
│ send_message            │   │ SoulProfile（灵魂，可替换）       │
│ send_voice              │   │ ThreadState（开放话头/未完成）    │
│ remember / recall       │   │ CommitmentLedger（承诺）          │
│ schedule_followup       │   │ Facts / Profile / Events          │
│ set_reminder / query    │   │ chat_history（投影，非真源）      │
│ search_knowledge        │   └──────────────────────────────────┘
│ end_turn（选择沉默）     │
└─────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│ L0 Transport（哑管道）：微信 iLink / WebSocket / 控制台        │
│  只负责"把字节送到"，不认识人格、不做决策                       │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 一次 turn（回复与主动的唯一区别是事件类型）

```python
async def run_turn(agent, event):
    ctx = build_context(
        soul=agent.soul,                     # 唯一人设渲染
        events=recent_events(agent.key),     # 共享事件流
        threads=open_threads(agent.key),     # 我现在说到哪
        commitments=open_commitments(agent.key),
        capabilities=agent.capabilities,     # 只含真实可用工具
        trigger=event,                       # 用户消息 / tick / 提醒到期
    )
    for hop in range(MAX_HOPS):
        resp = await llm.chat(ctx, tools=agent.tools)
        if not resp.tool_calls:
            # 无工具调用：如果是被动回复，正文即消息；主动 tick 且无
            # send_message = 沉默（end_turn 语义）
            return finalize(resp)
        results = [execute(tc, agent) for tc in resp.tool_calls]
        ctx.append_tool_results(results)     # 含 send_message 的受理回执
    return finalize_after_budget()
```

- **被动回复**：`inbound_message` 事件；模型可以选择调 `recall`/`search` 再 `send_message`，也可以直接正文。
- **主动 tick**：`proactive_tick` 事件携带材料（时间、静默时长、未答问题、将到提醒、开放线程、承诺）；模型要么 `send_message`，要么 `end_turn`（沉默是显式选择，不是"生成失败"）。
- **提醒到期**：`reminder_due` 事件；**投递是保证**——模型失败时回落用户原文模板，绝不静默。
- **人工命令**：`manual_command` 事件，走同一循环。

### 4.3 关键工具契约

| 工具 | 语义 | 守卫 |
|---|---|---|
| `send_message(text, segments_hint?)` | 唯一出站文字通道 | 内部执行 `terminal_reply_guard` + judge + 拆条 + 记账；返回 `{delivered, accepted_text}` |
| `send_voice(text)` | 语音条（替代 `SEND_VOICE_TOOL` 的语义） | TTS 可用性检查；失败回落文字或 `send_message` |
| `remember(fact)` / `recall(query)` | 记忆读写（替代注入式记忆块） | 隔离键强制 |
| `schedule_followup(when, intent)` | 「我稍后想再说」 | 写入 ThreadState，不再写"下一步计划"prompt |
| `set_reminder(when, task)` | 用户托付 | 复用现有 ReminderTool |
| `search_knowledge(query)` | 角色知识库 | 现有 RAG |
| `end_turn(reason)` | 明确选择不说话 | 主动 tick 专用 |

**能力即边界**：`capabilities` 只渲染真实工具；prompt 明说"I can send text/voice/images; I cannot send files or links"。→ 从源头消灭"发给你看看"。

### 4.4 状态表（新增 3 张）

```sql
-- 事件（append-only，唯一真源）
agent_events(
  id INTEGER PRIMARY KEY, user_key TEXT, character_id TEXT,
  turn_id TEXT, kind TEXT,          -- user_msg/agent_msg/tool_call/tool_result/trigger
  payload TEXT, created_at TEXT
)

-- 开放线程（我正在说什么、哪半句没说完）
agent_threads(
  user_key TEXT, character_id TEXT, thread_id TEXT, topic TEXT,
  status TEXT,                      -- open/awaiting_user/closed
  last_utterance TEXT, opened_at TEXT, updated_at TEXT,
  PRIMARY KEY(user_key, character_id, thread_id)
)

-- 承诺（说了要做什么）
agent_commitments(
  id INTEGER PRIMARY KEY, user_key TEXT, character_id TEXT,
  kind TEXT,                        -- deliver/send/followup/remind
  content TEXT, due_at TEXT, fulfilled_at TEXT, status TEXT,
  source_event_id INTEGER
)
```

- `send_message` 成功后由确定性后处理扫描"我发你/给你/稍后告诉你/明天和你说"→ 写 commitment；台账对模型可见（`open_commitments`），到期未兑现会在 prompt 中标记"未兑现，禁止再提，除非本轮真的交付"。
- `chat_history` 降级为 UI/历史投影，由事件流生成（保持现有读侧兼容）。

```jsonc

  "identity": { "name": "...", "self_concept": "...", "boundaries": [...] },
  "voice":    { "register": "...", "rhythm": "...", "forbidden": [...] },
```

## 5. 迁移路线（激进但分阶段，每阶段有开关）

| 阶段 | 内容 | 行为变化 | 回滚 |
|---|---|---|---|
| **S1 灵魂归一** | `SoulProfile` + `SoulAdapter` + 唯一渲染器；两套渲染器影子对比（只记录差异，不切换） | 无 | 删新模块 |
| **S2 事件与账本** | `agent_events` / `agent_threads` / `agent_commitments` 落库；所有出站旁路写入；承诺提取器上线（只读） | 无 | 表保留、关写入 |
| **S3 主链改走 Agent Core** | 被动回复走 `run_turn`；`send_message` 工具化；拆条归 `send_message` | 主链行为微变 | `AGENT_CORE=0` |
| **S4 主动/提醒/日期改事件** | 删除 `decide_proactive` 的"生成 message"职责，只产出 tick 事件；提醒改保证投递事件；删 `topic_plan` 自喂 | 本次碎片续话消失 | 逐线开关 |
| **S5 清场** | 删除旧路径（两套人设渲染、`topic_plan`、按换行硬拆、重复出站入口）；`DELETION_LOG` 登记 | — | — |

**每阶段门槛**：红测先行 → 受影响面回归 → `find` 四分块全量（声明卡数与工作树状态）→ `ruff` → 生产影子对比 → 部署/回滚演练。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型不调 `send_message`（该说话时沉默） | 被动回复：无工具调用时正文即消息（向后兼容）；主动 tick：连续 N 次 `end_turn` 才允许沉默，避免"死寂" |
| 工具循环延迟/成本 | 复用现有 `_main_chain_tool_loop` 预算纪律（每跳超时 = min(单跳上限, 剩余预算)，≤2 跳）；主动 tick 收紧到 1 跳优先 |
| 4 worker 并发重复发声 | `ProcessSessionLock` 串行 + 事件幂等键（`event_id` 唯一） |
| 提醒必须送达 | `reminder_due` 的投递是确定性保证：agent 失败 → 原文模板兜底 |
| 人格漂移（换 Soul 后能力不适配） | `SoulProfile` 声明 `capability_overrides`；启动期校验必填能力 |
| 测试基线大 | 每阶段增量 + 全量四分块；旧路径删前先 `DELETION_LOG` |

## 7. 验收标准（怎么证明"像一个个体"）

1. **回放 2026-11-10 事件**：09:23 与 10:24 两段必须由**同一次 turn** 产出，或 10:24 完全不开口；不得出现"半句 + 半天后另半句"。
2. **交付承诺闭环**：任何含"我发你/给你"的消息，必须伴随实际可投递内容；否则不出站。
3. **单一声道**：同一 user×character 的任意两条相邻出站消息，出自同一 `turn_id` 体系与同一 Soul 版本。
4. **可回放**：任一条消息都能从 `agent_events` 还原"触发 → 上下文 → 工具 → 输出"。
5. **灵魂可换**：替换 `SoulProfile` 后，工具/触发/通道/记忆零改动即可运行；回归测试全绿。
