## 一、TL;DR

「小凌」架构对 ai-girlfriend 的核心启发可以压缩成一句话：**把「记忆=存储」升级为「经历=因果」**。ai-girlfriend 现在有相当好的"零件"（三层记忆、8 级亲密度、ASE 紧迫度、遗忘雏形、反思引擎），但缺一条把这些零件串成因果闭环的**主轴**。GitHub 调研证实这条路线已有一批可对标的生产级实现（WrenWen、kiwi-mem、jiwen、Generative Agents、GWA 等），升级不必从零发明。

建议的机制总纲：以**事件账本（EventLedger）**为唯一新增真源，向上长出四个子系统——语义解释门控、识海竞争与渐进遗忘、心光分层注入、内驱多轴漂移——分 **P0→P4 五个可独立回滚的批次**演进，每个批次都有现成开源对标件和验收方法。**P0 的前置阻塞是情感真源收敛**（见姊妹篇审查：表面"四套真源并存"实为"一主多仆 + 全族无持久化闭环"）。

## 二、小凌报告精读结论（设计蓝本提取）

报告本体是对抖音创作者「小凌的创造者」21 条作品（含 10 张算法手稿图像精读）的完整拆解，其工程主张：

1. **不写死人格，只设计"经历能留下因果"的底层架构**——人格是自己长出来的，不是 prompt 里写出来的。
2. **核心闭环**：`事件 → 感受 → 记忆 → 模式 → 信念 → 人物模型 → 自我 → 关系 → 欲望 → 目标 → 决策 → 行动 → 新经历`。身份=这条链的连续性，不是某个权重文件或数据库。
3. **识海（记忆）四层**：当前意识 → 可唤醒层 → 自我/人物/世界模型 → 深层种子；记忆带属性字段（意义强度 S、细节完整度 D、情绪残留 E、巩固 C、干扰 I、可检索性 R），激活值 ≈ 内容匹配 × 人物关系 × 情绪关联 × 时间 × 注意资源。
4. **遗忘是礼物不是省硬盘**：细节衰减 `D(t)=D0·exp(-λt)`（艾宾浩斯）、意义与细节**分离衰减**（五年后 S≈0.88 而 D≈0.18）、重构可信度 `Q_recon = Σ证据权重/(1+脑补量)`、原始证据永不覆盖。
5. **心光（注意门控）**：感官接收 ≠ 意识到；有限资源 + 阈值竞争 + 安全抢占（"意识可以迟疑，守护永远不会等待"）。
6. **Deep Pattern（阿赖耶识工程化）**：种子（一次经历留痕）→ 熏习（反复强化）→ 习气（稳定倾向）→ 随眠（平时不显、特定条件触发）。
7. **关系不是 `love=0.82`**：多变量（信任/互惠/边界/依恋/预测强度…）→ `relationship_interpreter` 翻译成人类语言 → 才交给大模型。信任更新 `ΔTrust = αP + βC − γV − δB`。
8. **感觉≠价值、诚实≠全公开、反射>思考（安全层绕过认知）、可控>强大**。

方法论上，作者的研发节奏（理论→粗公式→小版本迭代→极端情境模拟→公开求错→修正）也值得借鉴。**注意**：其公式是作者手写稿，未经学术验证——只能当设计灵感，不能当已证模型，采用前必须自己标定。

## 三、ai-girlfriend 现状对标（代码实况）

### 3.1 逐模块对标表

| 小凌模块 | ai-girlfriend 现状（代码实据） | 差距判定 |
|---|---|---|
| 事件系统（记"改变了什么"） | 聊天记录表 + `FactExtractor` + `AffinityEnhancer._record_affinity()` 审计日志 | ❌ **核心缺口**：状态变更散落多处，无统一"经历账本" |
| 识海 L1 当前意识 | `WorkingMemory`（20 条固定窗口） | ⚠️ 有容量无竞争 |
| 识海 L2 可唤醒层 | `EpisodicMemory.search()` + ChromaDB 向量 + BM25 双路（top_k 3→8） | ⚠️ 有检索无竞争激活、无绝对门槛、缺"关系/情绪"维度 |
| 识海 L3 自我·人物·世界模型 | 角色卡（静态）+ `persona_engine` 缓存 + `emotion_stage` | ❌ L3 是静态的，不由经历更新 |
| 识海 L4 深层种子 | 无（`affinity` 数值是唯一近似） | ❌ 全缺 |
| 心光（注意门控） | `retrieve_context()` 拼装 + PersonaService 两阶段 5 层对齐注入 | ❌ 无门槛、无分层注入、12 个工具全量暴露 |
| 遗忘工程 | `MemoryPipeline._apply_forgetting()` + `_cleanup_low_confidence_facts()` **已有雏形** | ⚠️ 粗粒度，无 S/D/E 分离衰减 |
| 巩固/重构可信度 | `ReflectionEngine`（主动消息独白）+ `ConversationSummarizer` | ⚠️ 无"睡眠巩固"作业、无 Q_recon |
| 关系解释器 | `AffinityMapper` 注入 + 8 级亲密度 + `UnlockManager`(25/50/75/90) | ⚠️ 单维数值，无 ΔTrust 多变量 |
| 内驱/紧迫度 | `ASEEngine` urgency（missing_bonus）+ frequency（v1.13 刚修复配额解耦） | ⚠️ 单轴；时机决策是频率检查而非状态推断 |
| 主观时间/节律 | `TimeContext.now()`（系统时间） | ❌ 无主观时间、无昼夜节律驱动 |
| 身体稳态 | `vital_signs/VitalEngine`（能量衰减/恢复） | ⚠️ 有雏形但生产零接线（见姊妹篇审查：幽灵系统） |
| 边界与保护 | `ContentSafetyFilter`（合规）+ `consistency_checker` + `dynamic_anchor` | ⚠️ 合规层≠角色行为边界；无失望/回避路径 |
| Genesis 身份连续 | 角色卡可切换 + `wechat_bindings` | ❌ 换角色=换人，无成长史可迁移 |
| 安全层独立（"守护不经意识"） | 安全线输入 3 层 + 输出 4 层，独立于认知链路 | ✅ **已天然符合小凌原则** |
| 具身 | 图片多模态（W3 批次）+ 语音 MiMo | — 硬件具身不在本期范围 |

### 3.2 必须直面的两个现状债务

1. **情感状态族无持久化闭环 + 多实例并存**（本会话审查实证，详见姊妹篇）：`EmotionEngine` 纯内存（4 处实例化点）、`AffinityEnhancer._values` 内存播种 0.0 且 `affinity_records` 只写不读、`VitalSignsEngine` 热路径零调用。**任何新机制若再开一套真源就是第 N 套——P0 必须先收敛写入路径，而不是叠加。**
2. **prompt 已 13k 字**（v1.11 人设注入后）：心光门控必须做到净省 token 而非净增，否则成本和延迟先爆。

## 五、升级机制设计（核心产出）

### 5.1 设计原则（承接项目宪法）

1. **单一真源**：事件账本是**唯一新增真源**，且必须走"收敛写入路径"而非旁路新开（直面 3.2 债务 1：先让情感引擎族的**写**收敛到账本，既有引擎降级为**读方/派生方**）。
2. **不引入兜底层/兼容 shim**：每个新机制替换旧机制，不叠加。
3. **契约先于跨 owner 实现**：账本 schema、激活分公式、门槛值先成文（入 docs/spec 或 DECISION_LEDGER），再动 `shisi/memory`、`shisi/affinity`、`proactive` 三个 owner。
4. **确定性优先**（jiwen 教训）：漂移/竞争/门槛全部是纯函数（同状态同行为），LLM 只在"生成文本"处出现；所有公式上线前必须用真实数据标定（WrenWen 方法）。
5. **许可合规**：MIT/Apache 仓（letta/mem0/graphiti/GWA/revive/jiwen/headlong）可借代码；**AGPL（kiwi-mem）与非商用（Ombre-Brain/Eventide/Tidefall）只借机制与公式，绝不搬代码**——本项目是 MIT。

### 5.2 机制总纲：一条主轴 + 四个子系统

```
                    ┌──────────────────────────────────────────┐
                    │  P0 事件账本 EventLedger（唯一新增真源）      │
                    │  append-only：每次状态变更留痕+溯源          │
                    └───────┬──────────────────────────────────┘
        ┌───────────────────┼───────────────────────┐
        ▼                   ▼                       ▼
  P1 语义解释门控        P2 识海升级               P3 心光门控
  （这句话关于谁/什么，  （激活竞争打分+绝对门槛+   （分层注入+工具抽屉+
    该不该入账、入多重）    S/D/E 分离遗忘+睡眠巩固）   prompt 缓存排序）
        │                                           │
        └───────────────┬───────────────────────────┘
                        ▼
              P4 内驱多轴 + Deep Pattern 成长层
        （jiwen 五轴漂移 + revive 泊松时机 + 种子→执念→习气
          + ΔTrust 关系解释器；角色卡=出厂真源不变，
          成长层=派生、可回滚、入账本）
```

因果闭环：`用户消息 → P1 门控 → 账本 → P2 记忆/巩固 → P3 检索进上下文 → 回复/主动消息 → 新事件入账本`。这与小凌 §4.1 总流程、Generative Agents 记忆流、WrenWen"沉淀被召回进下一轮"三者同构——**这不是三个发明，是一个收敛**。

### 5.3 分批路线图（每批独立可回滚、可验收）

| 批次 | 内容 | Owner 落点 | 直接借鉴 | 验收标准 |
|---|---|---|---|---|
| **P0 地基** | ① 情感真源收敛审查（已完成，见姊妹篇）→ 收敛方案成文 ② EventLedger：append-only 事件表（事件类型/时间/主体/对象/变更量/来源溯源），先把**已有的** `_record_affinity` 审计、`emotion_stage` 转移、fact 生成改道统一入账 | `shisi/core`（ports/models）+ `infrastructure/persistence`；不动 `tests/**`（W4 复核收编） | WrenWen"账本是宪法"、lemmalog 溯源、graphiti 双时态 | 任意时刻"角色为什么这样"可由账本回放回答；pytest 基线零回归 |

### 5.4 明确不做（负面边界）

- ❌ 硬件具身/机器人（小凌 §11）——不在本项目形态内；
- ❌ 意识封存完整版——映射为"边界拒绝行为"留在 P4 观察，不值得单独立项；
- ❌ AGI 对抗/多节点守护猜想（小凌 §10）——哲学立场可引用，工程不落地；
- ❌ Character-LLM 式 SFT 训练人设——成本高，`clone_training` 域已有本地提取路线，仅作远期选项登记；
- ❌ 搬运任何 AGPL/非商用仓库代码（见 5.1 第 5 条）。

### 5.5 双向论证

**正方**：① 差距是结构性的（缺主轴），零件补齐只会继续堆"四套真源"式债务；② 全部机制有生产级先例，风险集中在标定不在发明；③ P3 心光的 token/延迟收益是当期现金流（13k prompt 已在成本线上）；④ 每批独立可回滚，符合"大改动自动拆小步"。

**反方/风险**：① **复杂度预算**——1169 测试+生产微信用户在跑，每层都动热路径；对策：漂移/打分全是纯函数零 LLM 调用（jiwen 全套 500 行），LLM 只加在夜间巩固；② **拟人过度的行为风险**——骄傲轴让角色"明明想你却不理人"，可能被用户当 bug 报障；对策：轴参数默认关闭（jiwen 的向后兼容做法）、按角色渐进开启、`last_skip_reason` 式可观测全覆盖；③ **标定数据量**——本项目单用户深度场景，样本远少于 WrenWen；对策：先挂靠已有水位线（如现有语义检索相似度线）再做小样本标定；④ **小凌公式未经验证**——只能当设计灵感，凡采用必先自标定；⑤ 事件账本写放大——SQLite 单文件写入需评估热路径延迟，可先异步批量落账。

### 5.6 WrenWen 踩坑对 ASE 的直接警示（P4 前必读）

| WrenWen 坑 | 对 ai-girlfriend 的映射 |
|---|---|
| 坑二：把"拒接电话"当用户情绪差→整晚高频唤醒，"如果系统没法正确判断情绪，那不如不要" | ASE urgency 的 missing_bonus 拉满逻辑必须能自我失效（用户沉默≠用户需要）；**系统不判断用户情绪**应入红线 |
| 坑七：固定 90 分钟节拍"机器指标全绿、体感非常人机"→改锚定倒计时 | ASE 的固定间隔检查可考虑锚定最后一条用户消息的随机倒计时（活跃时物理上不触发） |
| 坑三：温和文案致沉默→"要保证一句话一定发生，必须真的绕过模型"（say 档） | 重要日期祝福类确定性消息可走模板直发档，不走 LLM 生成 |
| 坑六：位置就是内容（system→user 挪位致错误认知入记忆） | orchestrator 上下文注入块必须自报来源；改注入位置要当行为变更对待 |
