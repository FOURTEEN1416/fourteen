## 0. 结论摘要（先看 6 条）

1. **DSH 不是插件，是插件宿主。** DSH = DeepSeek Harness，是 DeepSeek 官方开源的 Agent Harness（智能体运行环境/编码 agent），官方定义是 "an open-source agent harness developed by DeepSeek AI"，架构口号是 "Everything is a Plugin"。它可以跑 Web UI、桌面端、headless、SDK、ACP，不是「让 AI 仿真人化」的单一插件。  
2. **「让 AI 仿真人化」是 DSH 生态里的第三方插件品类，不是 DSH 本体。** 最贴近用户描述的是 `john-walks-slow/dsh-im-humanize`：它给 DSH 接入的 IM 机器人加「阅读延迟 + 输入状态 + 分步消息 + 状态表情 + 回复引用」，覆盖微信、企业微信、QQ、飞书、钉钉、Telegram、Discord、Slack、WhatsApp 九种渠道。  
3. **另有「文本层去 AI 味」插件家族**：`lynote-ai/dsh-humanizer`（8 个确定性工具、零模型调用、学你的写作指纹）、`DEEP-IOS/dsh-humanizer`（中文长文/小说润色 + SQLite 任务记忆）、`Nothing1024/dsh-humanizer`（本地 humanizer 模型改写，保留数字/人名/链接）、`liuwenji007/dsh-humanizer`（生成前注入「人味」约束 + 确定性 AI 味检测）。它们和 `dsh-im-humanize` 不是同一个东西：前者管「文字像不像人写的」，后者管「聊天节奏像不像人」。  
4. **生态规模很大，但成熟度参差。** 截至 2026-10-27：DSH 本体 ★262,767 / fork 31,768 / 30 个 release / npm 38 个版本 / 2026-10-01–26 npm 下载 1,191,936；GitHub `topic:dsh-plugin` 返回 23,308 个仓库（含噪声，仅作量级）；社区目录 `awesome-dsh-plugin` 收录 7,214 条条目。  
5. **本项目已经有「段间延时 + 拆条」骨架，不是从零开始。** `utils/humanize_config.py` 已有 dynamic/fixed/random/off 四档、`per_char_ms=45`、`delay_floor_ms=400`、`delay_ceil_ms=1600`、`max_segments=2`（用户裁决锁死）；`wechat_direct/wechat_connector.py::split_reply_for_wechat` + `send_reply_segments` 已按「换行/句末标点切块 + 段间 sleep」发送。DSH 插件真正值得补的是**前置阅读延迟、typing 输入状态、活跃响应曲线、按用户覆盖、声明式 schema**，不是重写现有拆条链。  
6. **不建议把 DSH 运行时嵌进主链。** DSH 是 Node.js/TypeScript 的 Agent Harness，当前是 developer preview 且明确会有 breaking changes；官方 Python SDK 也是启动 `dsh --profile sdk` 子进程，不是纯 Python 库。对本项目（Python/FastAPI + 微信 iLink）来说，**借机制、重写实现**的性价比远高于引入第二个 agent loop。

## 2. 机制级清单

### 2.1 DSH 本体：一切皆插件的运行机制

DSH 的「插件化」不是普通的插件市场，而是**连 agent loop、模型适配器、工具注册表、会话日志本身都是插件**。下面按「一个请求怎么跑起来」拆。

#### 2.1.1 Cordis：没有特权内核

- Cordis 是 DSH 底层框架：插件向共享上下文贡献**服务、类型化事件、可逆的副作用**。
- 产品的每一部分都是插件：模型适配器、工具注册表、会话日志、agent loop 本身；每个都可以从配置替换。
- **不存在需要打补丁的特权内核**：扩展 DSH 的方式是把插件挂载到其他插件旁边；注册是副作用，插件卸载时撤销。  
  来源：[docs/architecture.zh.md:9-11](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md#L9-L11)

#### 2.1.2 Profile、组合包、Patch：启动时叠一棵插件树

- 运行中的 `dsh` 是一棵插件树，由启动时按序叠加的各层组成。
- **profile**：Harness home 中的具名组装，列出自己叠放的组合包、树外插件、用户自己的 `cordis.patch.yml`。随发行版交付 `web`、`headless`、`sdk`、`sdk-minimal`、`acp` 五个模板。
- **组合包（bundle）**：Cordis 配置项 + 挂载代码的分发格式；在 `package.json` 里用 `dsh.bundle` 指向 patch 文件。
- **层序**：profile 中有序的组合包 → 其 `cordis.patch.yml` → home patch → `--patch` overlay。patch 按 `id` 定位条目，替换整个 `config` 或插入新条目。  
  来源：[docs/architecture.zh.md:15-25](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md#L15-L25)
- 调试命令：`dsh --profile web --dump-config` 打印本机启动的完整配置树；打印出来的任何条目都可以用自己的 patch 替换。  
  来源：[docs/architecture.zh.md:31-37](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md#L31-L37)

#### 2.1.3 插件的最小形态：一个导出 `apply(ctx)` 的 TypeScript 模块

- DSH 官方教程的定义：**插件就是一个 TypeScript 模块，导出 `apply` 函数**；框架加载时调用 `apply`，传入 `ctx`，插件通过 `ctx` 注册能力。
- `ctx` 上注册的监听器、工具、定时器会在插件卸载时自动清理；需要显式清理的资源用 `ctx.effect()` 返回 disposer。
- 插件可以声明 `inject = ['tools']` 之类的依赖，框架会等所需服务就绪再加载。  
  来源：[docs/user/develop/basic/index.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md)

这意味着：**「让 AI 像人」的插件可以注册自己的工具（如 `message_break`）、系统提示词段落、事件监听器，甚至替换消息投递管线**——不需要改 DSH 核心。

#### 2.1.4 Agent Loop：turn / step / 工具流水线

DSH 的 agent loop 不是「一次 LLM 调用」，而是：

```text
turn/start
  claim next-step input + queued message
  snapshot model selection; assemble prompt sections + tool schemas
  -> agent/pre-step（accept / rewrite / reject）
  step/start
  agent/request -> prepareCall
  stream the bound prepared call -> llm/stream
  assistant/message | assistant/attempt
  tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
  step/end
  如果工具还欠一次请求，或又有新输入 -> 下一个 step
turn/end
```

- **step** = 一次模型请求 + 它调用的工具；**turn** = 零个或多个 step，从领取首条输入开始，到不再欠工作结束。
- `agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 是 waterfall 事件，监听器必须调用 `next()` 才能继续；`agent/turn-stopping` 是 serial 事件。
- 这套事件模型是「拟人化插件」能挂进去的地方：例如 `dsh-im-humanize` 在 `tool/call` 事件里识别 `message_break`，把「工具调用」变成「发一条独立 IM 消息」。  
  来源：[docs/architecture.zh.md:83-124](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md#L83-L124)；`dsh-im-humanize` 的 `harness-client.mjs:636` 在 `tool/call` 分支处理 `message_break`（见 §2.2.7）。

#### 2.1.5 会话日志：模型可见即已记录

- 会话日志是**仅追加的 `SessionEvent` 日志**，`deriveMessages()` 从日志投影出模型历史。
- 每个 `assistant/message` 嵌入产生它的精确紧凑 stream；`assistant/attempt` 保留失败/重试/取消/stream error，但不进模型历史。
- **模型可见即已记录**：每个模型请求都必须能从日志重建；新增模型可见输入需要会话事件；修改消息内容的插件注册「纯消息投影」。
- 会话格式有 generation 与迁移链；已提交 generation 路径绝不重命名/替换/删除。  
  来源：[docs/architecture.zh.md:126-132](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md#L126-L132)

#### 2.1.6 系统提示词与人设：按 order 拼段落，persona 是其中一段

- `PromptSection` 是只读的同进程注册约定；各段按 `order` 升序排列，同 order 按名称代码单元顺序；`complete` 段会成为唯一提示词段落。
- `PERSONA_PREFIX_SECTION`（`deployment:persona-prefix`）与 `PERSONA_SUFFIX_SECTION`（`deployment:persona-suffix`）是全局配置与带作用域贡献共享的段落名。  
  来源：[docs/subsystems/system-prompt.zh.md:40-44](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/system-prompt.zh.md#L40-L44)
- `@deepseek-ai/dsh-persona` 让单个 agent 拥有自己的 system prompt 人设：preset 挂载它，注册前缀/后缀段落，遮蔽部署级默认值；`complete: true` 时前缀成为该会话唯一 system prompt；`includeRuntimeContext: false` 时抑制可选运行时上下文。  
  来源：[packages/preset/persona/README.zh.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/persona/README.zh.md)
- 对「仿真人化」的意义：**人设/口吻可以按 agent preset 隔离，不会和全局部署人设打架**；这比在单一 system prompt 里堆指令更干净。

#### 2.1.7 能力 seam：换一个 provider 就换掉一整条能力

- **seam** = 可替换能力，三角色：Service Definition（声明接口）、Service Provider（实现）、Consumer（通常是面向模型的工具）。
- 文件系统与进程提供方共享同一个执行世界：把 `ctx.fs` 指向远程沙箱，Bash、PTY、LSP 会一起搬过去，不需要 provider 专用 fork。
- 新行为的归属位置有明确映射：加模型提供方 → `ctx.llm`；加工具 → `ctx.tools`；加 shell → `ctx.shell`；加持久终端 → `ctx.terminals`；加用户命令 → `ctx.commands`；加后台任务 → `ctx.jobs`。

### 2.2 仿真人化插件：`dsh-im-humanize` 的机制级拆解

> 仓库：`john-walks-slow/dsh-im-humanize`（MIT，JavaScript，★4，创建 2026-09-07，最后 push 2026-10-26）。它是 `@xmanrui/dsh-im`（★2,627，9 渠道）的拟人化 fork，npm 包 `@johnnren/dsh-im-humanize@4.38.0-humanize.2`。  
> 安装：`dsh plugin --profile web add @johnnren/dsh-im-humanize`（README:55）或 `dsh plugin --profile web add github:john-walks-slow/dsh-im-humanize`（dsh-plugin.org）。

#### 2.2.1 它解决什么问题

不是「让模型写得像人」，而是「让机器人发消息的**时序**像人」：

- 机器人回复太快、太整、太连续 → 像客服/公告；
- 真人会「过一会儿才看到消息」→ **阅读延迟**；
- 真人会「打一段、停一下、再打一段」→ **输入状态 + 分段间隔**；
- 真人会把长回复拆成几条 → **message_break**；
- 真人会用表情/引用/「正在处理」等社交信号 → **statusReaction / replyQuote / progressStatus**。

官方插件目录页的定位原话：「为 DeepSeek Harness 的 IM 渠道加入拟人化回复：发送延迟、输入状态、分步消息与状态表情，让机器人聊天更像真人。」  
来源：[dsh-plugin.org/zh/plugins/john-walks-slow/dsh-im-humanize](https://dsh-plugin.org/zh/plugins/john-walks-slow/dsh-im-humanize)

#### 2.2.2 两阶段模型（核心语义）

| 阶段 | 时机 | 做什么 | 源码/文档 |
|---|---|---|---|
| **阶段① 阅读延迟** | 回合开头、`harness ask` 之前 | 静默等待，模拟「人过了一段时间才读到消息」；不发 typing、不发已读 | `src/channels/shared/send-delay.mjs:1-13`；summary:8-11 |
| **阶段② compose** | 延迟结束后 | 输入状态指示（off/continuous/burst）+ 分段间隔（「正在打下一条」） | `send-delay.mjs:9-13`；summary:8-11 |

阶段①的 `supersede` 语义：`pre-ask AbortController` 覆盖「延迟 + 图片 staging + 流打开」，无条件生效；被取代回合 `code='superseded'` → 静默（无生成、无发送、无失败提示、无双回复）。  
来源：`docs/features/260908-humanize-send-delay-typing/260908-humanize-send-delay-typing.summary.md:12`

#### 2.2.3 阅读延迟的精确公式

```text
baseMs    = activityBoost 基础值（有活跃记录且开启时；永不超过 readDelay.minMs）
           否则 uniform(minMs, maxMs)
readingMs = visibleLength(userText) / charsPerSecond * 1000（charsPerSecond=0 时关闭）
result    = min(baseMs + readingMs, maxTotalMs, channelCapMs?)
```

- `idleMs == null`（本会话还没有已完成回合，如首条消息）→ 用完整 `uniform(minMs, maxMs)`，不加速。
- 无输入状态接口的渠道 → `SHORT_DELAY_CAP_MS = 5_000`，因为「没有 typing 指示器解释这段沉默」。
- 默认值：`readDelay.minMs=1000`、`maxMs=6000`、`charsPerSecond=0`（长度项默认关）、`maxTotalMs=30_000`；`segmentGap.minMs=500`、`maxMs=2000`、`maxTotalMs=10_000`。  
  来源：[`src/channels/shared/send-delay.mjs:18-66, 331-366`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/send-delay.mjs#L18-L66)、[`447-467`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/send-delay.mjs#L447-L467)

#### 2.2.4 活跃响应曲线（activity boost）

- 替代旧的 `idleBoost`：**刚聊完天就「秒回」，闲置越久越接近完整区间**。
- 默认曲线：`fastReplyMs=1000`；`idle <= fastWindowMs(60s)` → 1s；`fastWindowMs..minWindowMs(120s)` → 从 1s 线性升到 `minMs`；`minWindowMs..fullWindowMs(300s)` → `minMs`；`>= fullWindowMs` → 完整 `uniform(minMs,maxMs)`。
- 不变量：**加成后的基础延迟永不高于 `minMs`**（只缩短，不拉长）；`fastReplyMs > minMs` 时截到 `minMs`；`idleMs == null` → 完整区间，不加速。  
  来源：[`send-delay.mjs:26-53, 380-391`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/send-delay.mjs#L26-L53)；summary:109-131

#### 2.2.5 输入状态（typing）三档 + burst 断续

- `typingIndicator`：`off` / `continuous` / `burst`；默认 **burst**。
- `continuous`：立即 `sendTyping`，之后每 `refreshMs` 重发（平台指示器寿命总是长于 refresh）。
- `burst`（residual-aware，余辉感知）：
  - 随机 ON 相位 `onMinMs..onMaxMs`（默认 3000–6000ms），内部按 `refreshMs` 续期；
  - 然后进入暗相位 `offMinMs..offMaxMs`（默认 1500–4000ms）；
  - 平台指示器在最后一次发送后有「余辉」（Telegram ~5s、Discord ~10s），所以：
    - **有显式取消接口**（如 WhatsApp `stopTyping` / `paused`）→ 暗相位开始时立即 `stopTyping`，暗相位可见（`darkResidualMs=0`）；
    - **无显式取消接口** → 在 ON→OFF 转换时补发一次最终 refresh，再按「可见暗时间 + 余辉」睡眠，保证用户看到的暗时间是诚实的。
- 生命周期绑在 bridge turn：`start()` 在阅读延迟后，`stop()` 在 turn 的 `finally`；`pause()/resume()` 用于等待用户交互（提问/审批）；`restartOn(action)` 用于 message-break 段间隔和 Telegram 附件动作。  
  来源：[`src/channels/shared/typing-session.mjs:1-42`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/typing-session.mjs#L1-L42)；summary:109-117

#### 2.2.6 分段间隔（segmentGap）

```text
baseMs = uniform(segmentGap.minMs, segmentGap.maxMs)
typingMs = segmentLength / charsPerSecond * 1000（默认关闭）
result = max(min(baseMs + typingMs, maxTotalMs), minSegmentGapMs)
```

- 默认 500–2000ms，封顶 10s；
- **平台频控优先**：钉钉 webhook 要求分段间隔 ≥ 3000ms（否则 48 条/分钟会触发 20 条/分钟频控，封禁 10 分钟），代码里 `DINGTALK_MIN_SEGMENT_GAP_MS=3000` 覆盖随机下限——**该常量定义在 `src/channels/dingtalk/dingtalk-bridge.mjs:539`、使用于 `:1520`**（2026-10-27 源码复核修正：原引用误写为 `send-delay.mjs`）。
- 纯文本段才有 gap；纯空白分段跳过。  
  来源：[`send-delay.mjs:398-415`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/send-delay.mjs#L398-L415)；[`src/channels/dingtalk/dingtalk-bridge.mjs:539,1520`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/dingtalk/dingtalk-bridge.mjs#L539)；summary:76-80

#### 2.2.7 `message_break`：一个「空操作工具」当分段定界符

这是整个插件最值得学的设计：**不靠 prompt 让模型「请分多条」，而是注册一个 no-op 工具，让模型在自然段落边界主动调用它。**

- 工具名 `message_break`，无参数，`execute` 返回 `{ ok: true }`；真正发送发生在 bridge 的 `onUpdate` 回调。
- **尾随定界符（trailing delimiter）**：调用时把「自上一个断点以来累积的文本」作为一条独立消息发出；模型必须先写这一段，再调用；**空断点是 no-op**，后面的文本会等到下一个断点或回合结束。
- 单回合最多 20 段（`MAX_MESSAGE_BREAKS_PER_TURN = 20`）；纯空白分段跳过。
- 只在 IM 会话生效：只有本回合有活跃 IM 投递消费者时才引导模型使用；Web/CLI 会话与 AI Office 任务调用会被拒绝。
- 与流式共存：**每段各自流式**（在各自的 carrier 里逐字输出），断点处定稿成一条真实消息，随后为下一段新开一条流；流式关闭时退化为每段整条发送（带分段间隔）。
- `segmentsCover(fullAnswer)` 只在「已发送段覆盖全文 + 尾部可证明为空」时抑制最后一条，避免重复；前缀失配（canonical 改写、段尾空白）一律照旧发送整条——**宁可重复也不丢内容**。  
  来源：[`src/channels/shared/message-break.mjs:1-26, 40-70, 91-100, 115-197`](https://github.com/john-walks-slow/dsh-im-humanize/blob/main/src/channels/shared/message-break.mjs#L1-L26)；`docs/features/261009-message-break-prompt/261009-message-break-prompt.plan.md`；`docs/features/261009-segmented-streaming/261009-segmented-streaming.summary.md`

#### 2.2.11 人类行为实证依据（为什么这些默认值不是拍脑袋）

`dsh-im-humanize` 的调研文档汇总了平台能力与人类行为证据，关键数字：

- 打字速度：桌面英文 **4.3 字符/s**、移动英文 **3.0**、中文拼音 **0.3–1+ 字/s**（多源 20–64 字/分）；自由撰写约为机械听打的 60%（Karat et al., CHI 1999）。
- IM 回复中位数 **15 秒**，92% 在 5 分钟内回复（Avrahami & Hudson 2006 等）。
- 人类交互间隔**重尾**（对数正态/幂律），不是均匀分布；工程上用 `uniform(min,max)` 是合理近似，v2 可升级对数正态。
- 感知最优延迟：短回复 **1–2s**、复杂回复 **~9s**；2s 偏肤浅，>8–10s 转负。
- **typing indicator 显著缓解长延迟负效应**（Kim et al. 2025, IJHCI）；但**完整打字时长模拟反而有害**（Schanke 2021 反例）。
- **42% 的真人消息序列拆成多条连发**，均值 1.7 条/序列，每条 ~5.4 词（Baron 2010）——这是 `message_break` 的实证依据。  
  来源：`docs/features/260908-humanize-send-delay-typing/260908-typing-and-delay.research.md:14, 225-289, 302-370`（原文附 DOI/PDF 链接）

### 4.2 最值得补的 5 个机制（按 ROI 排序）

#### P0-1：前置阅读延迟 + typing 输入状态（opt-in）

- **做什么**：在调用 LLM 之前，按 `uniform(1000, 6000)` 等待；等待期间不发 typing；等待结束后启动 typing 会话；LLM 生成期间保持 typing；发送前停止。
- **为什么**：项目现在的「段间延时」只发生在**生成之后**；用户感知的「秒回」主要来自**生成前零延迟**。DSH 的实证调研明确：typing indicator 能显著缓解长延迟负效应（Kim 2025），而「延迟 + typing」才是有效组合；只延迟不 typing 的渠道应把延迟压到 ≤5s。
- **怎么做**：新增 `utils/humanize_read_delay.py`（或扩展 `humanize_config`），字段：`read_delay_min_ms`、`read_delay_max_ms`、`read_delay_max_total_ms`、`activity_boost`；在 `orchestrator` 的 `prepare` 前调用 `apply_read_delay()`；在 `wechat_direct` 的发送链前后调用 `sendtyping status=1/2`。
- **风险**：增加首字延迟；默认必须关闭（DSH 的 `sendDelay.enabled` 默认 false，README:69/107）。建议先做 admin 开关 + 1% 灰度，不要默认全量。
- **验收**：P50 2–6s、P90 ≤12s；新消息在延迟期到达时旧回合静默取消（supersede），无双回复；无 typing 能力时延迟 ≤5s。

#### P0-2：活跃响应曲线

- **做什么**：用「上一回合结束时间」计算 idle：`idle <= 60s` → 1s；`60–120s` → 线性升到 `minMs`；`120–300s` → `minMs`；`>=300s` → 完整区间。
- **为什么**：固定延迟会让「刚聊完」也显得慢，也会让「隔很久」显得急；真人节奏是「刚聊完秒回，闲置越久越慢」。
- **怎么做**：在会话状态里记录 `last_turn_end_ts`（项目已有会话/回合概念，可复用）；`compute_read_delay(idle_ms)` 纯函数；单测覆盖 0/60/120/300/None 五个边界。
- **风险**：idle 语义要明确「上一回合结束」而不是「上一条用户消息」；否则长生成会把 idle 算错。

#### P1-1：burst 断续输入状态

- **做什么**：`typingIndicator` 三档 `off/continuous/burst`；burst 的 ON 3–6s / OFF 1.5–4s；有 `stopTyping` 的渠道暗相位立即生效，无 `stopTyping` 的渠道按「余辉」补偿。
- **为什么**：连续 typing 像「机器人一直按着键盘」；断续才像真人「打一段、想一下、再打」。
- **怎么做**：`typing-session` 状态机（start/pause/resume/restartOn/stop），绑定 turn 生命周期；微信 iLink 若只有 ticket 型 typing（status 1/2），先做 continuous-only，不要硬做 burst。
- **风险**：平台 typing 余辉不同（Telegram 5s、Discord 10s、WhatsApp 10s）；微信 iLink 需实测。

#### P1-2：按用户覆盖 + 声明式 schema

- **做什么**：把 `humanize` 从「全局 admin 配置」扩展为「全局默认 + 按用户覆盖」；用一张 `HUMANIZE_FIELDS` 表派生默认值、读写校验、前端控件、per-user 白名单。
- **为什么**：项目刚在 v1.56 R7 出过 P0——admin「指定用户」写入键形态与运行时读取键不一致，功能无效却回执成功。DSH 的 `humanize-schema` 用「缺失 = 继承，显式 = 覆盖」的语义 + 严格/宽松双校验，正是防这类键漂移的工程答案。
- **怎么做**：先给现有 `humanize_config` 字段表化（`DEFAULTS` / `INT_BOUNDS` / `WRITABLE_FIELDS` 已经接近）；再加 `user_humanize` 覆盖表（参考 `user_reply_mode`）；读写走同一个 `resolve_humanize(user_key)`，禁止 UI 自己拼键。
- **风险**：覆盖层级变多（全局 < 用户 < 会话？）要一次定清楚；不要又造一套「全局/用户/会话」三套键。

#### P2：`message_break` 语义（只在未来放宽段数时）

- **做什么**：注册一个 no-op 工具/标记，模型在自然段落边界调用；插件把「自上一个断点以来的文本」作为独立消息发出；空断点 no-op；尾部去重。
- **为什么**：项目当前 2 段是用户裁决，不需要 20 段；但「模型主动断点」比「按标点贪心切」更懂语义。未来若用户愿意放宽到 3–4 段，这是最干净的扩展方式。
- **风险**：模型可能滥用断点；需要单回合上限、空断点 no-op、尾部 `segmentsCover` 防重复；prompt 必须写「先写后断」，否则会出现「断点落空、文本迟到」（DSH 自己就踩过这个坑，见 `261009-message-break-prompt.plan.md`）。

### 4.3 次优先/观察项

1. **supersede 显式契约**：阅读延迟期间用户再发消息 → 旧回合 `code='superseded'` → 静默取消，无生成/无发送/无失败提示/无双回复。项目现在有 `ProcessSessionLock` 保证串行，但没有「延迟期取消」的显式语义；如果加阅读延迟，这是必做前置。
2. **平台能力矩阵**：如果未来接第二个 IM 渠道，先建一张「渠道 × typing/流式/引用/频控」表；无 typing 的渠道延迟封顶 5s，钉钉分段 ≥3s。不要用一套参数打所有渠道。
3. **状态表情/回复引用**：微信 iLink 没有对应能力，不适用；但「过程进度可关闭、不污染最终回复」的原则可以用于现有状态提示。
4. **情绪状态机**：`Fyue7/dsh-emotion` 的「会话投影情绪状态机 + 三段提示词注入（声线/状态/本轮实况）+ 情绪条」值得对照项目的 emotion engine；重点不是再加一套情绪，而是**把情绪投影成一小段紧凑上下文**，不要让整套规则进 system prompt。
5. **模拟生活/身体时钟**：`dsh-simulated-life` 的「每轮注入过去 24h 生活事件」和 `dsh-mate-companion` 的「身体时钟/离线睡眠」是「有自己生活」的工程化；但 token 成本和一致性风险高，建议先做「轻量版」：每天 3–5 条生活事件，按衰减注入。
6. **主动唤醒**：`dsh-proactive` 的 jitter + quiet hours + daily budget + min_idle + `proactive_reclaim` 墓碑，与项目现有 `commit_sent`「投递成功才记账」哲学一致；可对照补 jitter/预算/静默退出。
7. **文本去 AI 味三层**：
   - 生成前：system prompt 风格约束（`liuwenji007` 的做法）；
   - 生成中/后：确定性扫描评分（`lynote-ai` / `liuwenji007`，零 token、可复现）；
   - 必要时：本地小模型改写（`Nothing1024`，成本/延迟高，不建议主链）。
   项目已有 `terminal_reply_guard`；建议加「确定性 AI 味评分」做观测与回归，不要在主链做 LLM 重写。

### 4.4 不建议做的事

1. **不要把 DSH 本体嵌进主链**。理由：Node 24 + TypeScript + developer preview + 38 个 npm 版本 + breaking changes；官方 Python SDK 是子进程，不是库；引入后会多一个 agent loop，与项目 `orchestrator` 的 owner 体系冲突。
2. **不要直接安装 ★4 的 `dsh-im-humanize` 到生产**。它是 fork，上游 `dsh-im` ★2,627 才是成熟底座；且微信/QQ/飞书/钉钉实机未验证。正确做法：读它的 `send-delay.mjs` / `typing-session.mjs` / `message-break.mjs`，在本项目用 Python 重写。
3. **不要默认开启阅读延迟**。DSH 自己 `sendDelay.enabled=false` 默认关闭；项目的用户已经习惯当前响应速度，突然加 1–6s 会被感知为「变卡」。先 admin 开关 + 小流量。
4. **不要做「完整打字时长」模拟**。DSH 调研明确：完整打字时长模拟反而有害（Schanke 2021 反例）；只做「段间停顿 + typing 指示」即可。
5. **不要为了「像人」故意打错字/加错别字**。DSH 调研的结论是禁止故意打错字、禁止占位消息；错别字在高信任陪伴场景可能损害信任（项目已有 v1.55 质量悬崖教训）。
6. **不要直接并 GPL/AGPL 代码**。本项目 MIT；MaiBot GPL、AstrBot 插件 AGPL、dsh-tavern AGPL 等都只能借机制。

## 8. 附：一句话回答「DSH 是什么」

> **DSH = DeepSeek Harness = DeepSeek 官方开源的 Agent Harness（智能体运行环境），不是「让 AI 仿真人化的插件」。**  
> 「让 AI 仿真人化」的是跑在它上面的第三方插件：聊天节奏看 `dsh-im-humanize`，文本去 AI 味看 `dsh-humanizer` 家族，人格/情绪/主动看 `dsh-persona` / `dsh-emotion` / `dsh-proactive` 等。  
> 对本项目：**借它的机制（阅读延迟、typing、活跃响应、message_break、声明式 schema），不要借它的运行时。**
