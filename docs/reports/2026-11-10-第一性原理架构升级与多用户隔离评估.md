## 0. 结论先行（三句话）

1. **"像一个个体"与"多用户隔离"是同一条约束的两面**：一个 Identity 只能有一个 Soul、一份 Memory、一套 Credentials、一条时序；任何共享都会同时破坏"像人"与"隔离"。
2. **DeepSeek Harness 是单 home、会话级、host 级凭据的运行时**，没有 user 维度；它**不适配**我们现有多用户隔离体系，除非"一 bot 一 runtime"（成本高）或自建租户层（风险高）。
3. **架构升级应发生在 Python 侧**：借用 Harness 的五个形状（事件日志 / loop 解耦 / schedule 投消息 / capability seam / model-visible means logged），而不是替换运行时。

## 1. 第一性原理：什么是一个"个体"

把"角色"拆到不可再分，只有六个要素：

| 要素 | 回答的问题 | 本仓对应 |
|---|---|---|
| **Identity** | 我是谁、对谁说话 | `user_key`（owner:peer）+ `character_id` |
| **Soul** | 我怎么说、边界在哪 | 角色卡 + 回复模式 + 人设渲染 |
| **Memory** | 我记得什么 | 三层记忆 / facts / 画像 / 知识库 |
| **State** | 我上一句说到哪、承诺了什么 | `chat_history` + `topic_state` +（缺）承诺账本 |
| **Capabilities** | 我能做什么 | 工具注册表（17 项） |
| **Transport** | 我怎么把话送出去 | 微信 iLink / WS / 控制台 |

**"像一个个体"的判据（可机器检验）**：

> 对任意两个相邻出站消息 m1、m2，若它们属于同一 Identity，则必须满足：
> ① 同一 Soul 版本；② 共享同一 State（无"半句话"跨生产者）；③ 只使用该 Identity 的 Memory 与 Credentials；④ 时序上属于同一决策序列。

本仓 11-10 事故违反的是 ②（半句跨线）与 ③（承诺了不存在的能力）——不是文风问题。

## 2. 第一性原理：什么是"隔离"

隔离不是"分表"，而是**六个面同时成立**：

| 面 | 定义 | 失效后果 |
|---|---|---|
| **读隔离** | A 的会话不能读到 B 的记忆/画像/历史 | 串台、隐私泄露 |
| **写隔离** | A 的写入不能落到 B 的键 | 污染、误归属 |
| **凭据隔离** | A 的 LLM Key/通道凭证不能用于 B；失败不得回落平台 | 费用串账、越权 |
| **时序隔离** | A 的静默窗/节奏/冷却不影响 B | A 的暂停导致 B 静默 |
| **能力隔离** | A 的角色设置/工具权限不泄漏给 B | 越权调用、角色漂移 |
| **删除隔离** | 删 A 不波及 B；A 的派生召回必须失效 | 幽灵记忆、合规风险 |

**隔离的三条铁律**：

1. **键必须显式**：任何存储/缓存/调度都必须带 `(user_key, character_id)`，禁止"默认全局"。
2. **默认必须 fail-closed**：拿不到键时拒绝，而不是回落全局。
3. **跨边界即新增泄漏面**：每引入一个运行时/语言/进程，就多一个需要证明隔离的边界。

## 3. 本仓隔离体系（代码实况）

### 3.1 身份与键

- `utils/session_key.py` 是会话键唯一真源：微信 `N:wxid@im.wechat`、web `N:web:hex`、WS `N:N:web:hex`；判据无启发式。
- `user_key` = 会话归属账号；`character_id` = 该用户当前角色。
- D15 身份组（`user_identity_map` + `identity_keys()`）：**显式声明**才共享事实，未声明行为 100% 不变。

### 3.2 数据

- `user_facts` 主键 `(user_key, fact)`；`get_facts_by_ids` 带组隔离；检索水位/删除水位按 key 持久化。
- `chat_history` 带 `session_id + user_key + character_id + channel`。
- `user_character_settings` 主键 `(user_key, character_id)`（全量快照）。

### 3.3 凭据

- `api/byok.py`：按 `user_id` 读取 `users.llm_config`；**数据库失败/停用账号一律拒绝，绝不回落平台 key**。
- 后台任务（调度器/主动线）通过 `session_llm(session_key)` 走同一账号策略。

### 3.4 时序与并发

- 主动线**按 user_key 逐个 tick**；每用户独立引擎状态（ASEHub）、独立静默窗、独立 token 窗口、独立节奏双闸与连击闸。
- `ProcessSessionLock`：按 `session_id` 哈希的 **OS 文件锁**，4 worker 同会话串行。

### 3.5 删除

- `api/lifecycle.py` 五阶段作业（preview→冻结→purge→验证→回执）+ 八 owner purge 接口 + `deletion_guard` 丢弃迟到写入。

### 3.6 现有证明

- 事实相关 27 个测试文件 / 501 例（跨通道组隔离、删除水位、越权拒删）。
- `test_shisi_migration_isolation.py` 钉住测试沙箱不写真实库。

> 结论：**本仓的隔离是"数据层显式键 + fail-closed + OS 锁"三件套**，所有不变量都活在 Python 代码里。

### 3.7 N 用户规模下的共享面（不是双用户问题）

隔离在 N 个用户下不是"两两不串"就够，而是**所有共享结构都必须在 N 下保持有界、公平、可归属**。当前共享面：

| 共享面 | 现状 | N 下的风险 |
|---|---|---|
| **调度 tick** | `_check_ase_per_user` **串行 for 循环**遍历所有 user_key（每 5 分钟） | 单用户决策 LLM 15–20s ⇒ 30 用户 ≈ 450–600s > tick 周期：**队头阻塞、尾部用户饿死** |
| **每用户内存字典** | `_deliver_fail_counts` / `_disabled_event_day` / `_quiet_event_day` / `_judge_recent` 均为无界 dict | N 增长时内存与键空间无界（量小但无上限） |
| **ASE 引擎注册表** | `ASEHub` 是 **LRU 有界**（好），状态按用户分文件 | 高 N + 淘汰抖动 ⇒ 反复落盘/重载 |
| **向量检索** | 依赖每次查询显式 `where={"user_key": …}`（`vector_memory._search` / `semantic_memory`） | **任何一条遗漏 filter 的查询 = 跨用户召回**；N 越大代码路径越多，风险越高 |
| **平台网关熔断** | breaker key = provider（平台网关共享实例） | 供应商抖动会让**全体用户**同时进入 `model_degraded`，主动线集体静默（共享命运，需产品级策略） |
| **SQLite** | 单库 + 4 worker；部分路径 `busy_timeout=50ms` | N 用户写竞争 ⇒ 超时 ⇒ 各路径 fail-open 行为放大 |
| **会话锁** | `ProcessSessionLock` 每会话一个锁文件 | N 会话 = N 锁文件；需清理与上限 |
| **删除** | lifecycle 八 owner purge | N 下删除必须**不阻塞其他用户**，且派生召回必须失效 |
| **限速/配额** | 入站按 owner、出站按账号节奏 | N 下需确认桶按 owner 而非全局 |

**N 不是"双用户的放大版"**：双用户能过，N 用户仍可能因为队头阻塞、无界字典、漏 filter、写竞争而违规。

## 4. DeepSeek Harness 的隔离模型（逐项取证）

| 维度 | Harness 的事实 | 证据 |
|---|---|---|
| 身份 | `identity` 包只提供**anonymous install id**（一个 home 一个匿名 id），**没有用户身份** | `packages/identity/README.md` |
| 租户 | 无 tenant/user 概念；运行单元是 **session**（append-only 日志） | `docs/architecture.md`、`docs/subsystems/session.md` |
| 凭据 | `credentials` seam 是**host 级引用**（env/file/project-env/user-env），按操作解析；**无 per-session/per-user 凭据模型** | `docs/subsystems/credentials.md` |
| 存储 | 会话落 `$DSH_HOME/sessions`（JSONL），一个 home 一套 | `packages/bundle/sdk-minimal/README.md` |
| 作用域 | `scope` 是**插件可见性/生命周期**的 per-agent 作用域，不是数据隔离 | `docs/subsystems/scope.md` |
| 访问控制 | `remoteAccess` 是**API peer** 的访问策略（客户端连会话），不是终端用户数据隔离 | `docs/api-gateway.md` |
| 模型/人格 | 会话级 `modelSelection`；system prompt 可由插件组装；`sdk-minimal` 用 `DSH_SYSTEM_PROMPT`（runtime 级） | `docs/architecture.md`、sdk-minimal README |
| 调度 | `dsh-tool-schedule` 把 prompt 作为"用户消息"投进目标 session | `docs/tool-catalog.md` |

**判定：Harness 是"单 home ≈ 单租户"的运行时；它的隔离粒度是 session，不是 user。**

## 5. 适配性评估（把六面逐条对撞）

| 隔离面 | 本仓现状 | 换成 Harness（共享 runtime） | 换成 Harness（一 bot 一 runtime） |
|---|---|---|---|
| 读隔离 | SQL 按 user_key | ❌ 需自建 session↔user 映射 + MCP 侧二次校验 | ✅ 进程级天然隔离 |
| 写隔离 | 主键带 key | ❌ 同上 | ✅ |
| 凭据隔离 | per-user BYOK，禁止回落 | ❌ **host 级凭据**，需自定义 provider 或每用户 runtime | ✅（每 runtime 一个 key） |
| 时序隔离 | 每用户 tick/静默/节奏 | ❌ 调度在 dsh 是 per-session，闸门仍在 Python，跨语言 | ✅（各自 runtime） |
| 能力隔离 | 角色快照 | ⚠️ 需 per-session preset/插件作用域 | ✅ |
| 删除隔离 | lifecycle 八 owner | ❌ dsh session 是**第二个真源**，删除要双清 | ⚠️ 删目录 + 删 Python 数据 |

**额外的新增泄漏面**（换 runtime 才有）：

1. **跨语言边界**：MCP 调用必须携带 `user_key`，且 Python 侧要**再校验一次**（不能信 dsh 传来的身份）。
2. **第二个真源**：dsh 的 SessionEvent 日志 vs 我们的 `chat_history`——谁是唯一真源必须重新裁决，否则"删除必须失效派生召回"会被绕过。
3. **凭据层**：BYOK 的 per-user key 在 host 级 credentials 里无法自然表达。
4. **并发模型**：我们靠 `ProcessSessionLock` 跨 4 worker；dsh 有自己的会话串行，但两者不共享锁语义。
5. **运维**：Node ≥ 24.9 + v0.1 preview，breaking changes 会传导到隔离层。

### 5.1 成本量级（估，需实测）

- 一 bot 一 runtime：N 个 Node 24 进程；Node 基线 + agent 依赖估计 **100–200MB/进程**（**待 spike 实测**）。10 用户 ≈ 1–2GB，50 用户 ≈ 5–10GB，200 用户 ≈ 20–40GB。
- 共享 runtime + 租户层：等于把本仓隔离层（身份/凭据/删除/审计）在 TS 侧重写一遍，并维护两套真源；且**N 用户下的公平性/有界性仍要自己解决**（Harness 的调度也是按 session，不保证多租户公平）。
- 参考：本仓现状在 N=200 时的瓶颈是**调度串行 tick**与**SQLite 写竞争**，不是内存——这两个在 A1/A2 里都仍然存在（甚至在 A2 多一层）。

## 6. 结论

### 6.1 判定

**DeepSeek Harness 不适配我们现有多用户隔离体系。**

不是"跑不起来"，而是**隔离模型不对等**：它是 session 级、单 home、host 级凭据；我们需要 user 级、多 home 语义、per-user 凭据。

### 6.2 三条路线与取舍

| 路线 | 隔离 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| **A1 一 bot 一 dsh runtime** | ✅ 强 | 高（N×Node） | preview 升级传导 | 仅当用户数小且愿意换部署形态 |
| **A2 共享 dsh + 自建租户层** | ❌ 需重写隔离 | 最高 | 双真源 + 跨语言泄漏面 | **否决** |
| **B Python 侧 Agent Core（推荐）** | ✅ 沿用现有 | 中（600–1000 行） | 无新边界 | **推荐** |

### 6.3 路线 B 要借的五个形状（来自 Harness，已验证）

1. **append-only 事件日志**（替代"只存文本历史"）：模型可见即已记录。
2. **loop / prompt / tools / model 解耦**（插件化的思路，不必用 Cordis）。
3. **schedule 把 prompt 作为"用户消息"投进同一 session**（替代独立主动决策器写文案）。
4. **capability seam**（Service Definition / Provider / Consumer）——我们的 MCP/工具也按这个三分法组织。
5. **单一出口**：`send_message` 工具是唯一文字通道（对应 Harness 的 turn/step 语义）。

### 6.4 若坚持 Harness：必须先满足的硬条件

1. 一 bot 一 `DSH_HOME`（禁止共享 home）。
2. 每个 MCP 调用携带 `user_key`，Python 侧**双重校验**。
3. 自定义 credentials provider 实现 per-user key（或一 runtime 一 key）。
4. 删除链路双清（dsh session + Python 数据），并证明派生召回失效。
5. 明确 `SessionEvent` 与 `chat_history` 的唯一真源关系。
6. 通过下节隔离矩阵。

## 7. N 用户隔离验证矩阵（任何运行时变更的上线门槛）

### 7.1 三类证明

1. **结构性证明（静态）**：键完整性——所有存储/缓存/检索/调度入口必须显式带 `(user_key, character_id)`；用 AST/文本守卫枚举"无 key 的查询/写入"，命中即红。
2. **性质性证明（运行时）**：给每个用户的事实/消息打**唯一 nonce**，抓取该用户实际发给模型的 prompt，断言**不包含任何其他用户的 nonce**。这比两两对拍更强，且天然覆盖 N。
3. **规模性证明（压测）**：N=50 / N=200 合成租户并发跑入站 + 主动 + 提醒，测公平性、有界性、内存、写竞争、删除不阻塞。

### 7.2 矩阵

| # | 用例（N 用户） | 期望 |
|---|---|---|
| N1 | N=50 每户注入唯一 nonce 事实，抓全量 prompt | 任意 prompt 中**零**出现他人 nonce |
| N2 | N 户 BYOK 各自不同假 key，mock 供应商记录请求 | 每请求只用本户 key；未配置户**不得回落平台** |
| N3 | N 户各自静默窗/暂停/节奏 | 任一户暂停不影响他人 tick 与投递 |
| N4 | N 户各自角色/设置切换 | 他人 Soul/设置零变化 |
| N5 | 压测中删除第 k 户 | 其他户零影响；k 的 facts/向量/session 目录零命中 |
| N6 | 4 worker × N 会话同会话并发 | 串行、幂等、无重复出站 |
| N7 | 注入 1 个慢用户（决策 60s） | 其他户 tick 仍在周期内完成（**公平性**） |
| N8 | N=200 会话长跑 | 内存有界（LRU/字典有上限）；无 O(N) 无界增长 |
| N9 | 随机查询 fuzz（含缺 filter 的调用） | 结构性守卫拦截；不存在无 key 的向量检索 |
| N10 | D15 显式组 | 仅组内共享；未声明户零变化 |
| N11 | SQLite 写竞争压测 | 超时率在阈值内；fail-open 行为有日志与上限 |
| N12 | 供应商熔断 | 全户降级可见、可解释；主动线静默策略符合裁决 |

> N1（nonce 扫描）、N2（凭据矩阵）、N5（删除隔离）必须**红测先行**：先构造能泄漏的代码路径并证明测试会红，再修到绿。
> N7（公平性）与 N8（有界性）是"双用户测不出来"的两类——必须在 N=50/200 下跑。
