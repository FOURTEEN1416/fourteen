## 0. 结论摘要（先看这 10 条）

1. **「暂不引入」的裁决不需要改任何代码或配置**。现行 `voice.engine: "mimo-tts"`（`config/system.yaml:141`）、`TTSManager` 只注册 MiMo（`voice/tts_manager.py:60-74`）、API 只允许 `mimo-tts`（`api/routers/voice_routes.py:118-123`）都与「暂不引入」一致。本文只是候选设计，不构成对 AGENTS L6「MiMo 唯一引擎」（`AGENTS.md:226`）的覆盖。
2. **BreezeTTS2 的能力与许可必须分开看**：代码/音频 tokenizer 是 Apache-2.0；**模型权重、checkpoint、adapter、衍生模型、自托管输出是 BreezeBlue Research and Non-Commercial License v1.1（2026-09-01）**，仅研究/非商用，**不是开源许可**，商用要 BreezeBlue 单独书面许可。**本地部署省的是 API 费，不省许可费**。
3. **对「公开产品」而言，许可门比硬件门更硬**。许可把 Commercial Purpose 定义为包括「production use or use in a product, service, or business operation」「hosting or making ... available through an API, SaaS offering, application, plug-in, website, or other service」。一个面向用户的 AI 陪伴产品即使不向 C 端收费，也很难被解释成「个人/教育/爱好」；**先法务确认，再谈买卡**。
4. **现生产服务器跑不了本地 Breeze**：部署文档的硬件下限是 RAM ≥4GB（推荐 8GB）、CPU ≥2 核（推荐 4 核）、磁盘 ≥20GB，**没有 GPU 行**（`deploy/README.deploy.md:13-16`）；生产是 `.venv-cpu`、4 worker（`deploy/ai-girlfriend.service:21`）。本地 Breeze 必须新增一台 **NVIDIA GPU 推理机**，不能和现有 API 服务挤在一台 CPU 机上。
5. **官方硬件门槛**：Linux + Python 3.10+ + CUDA NVIDIA GPU；eager 约 **7.7 GiB** 显存，建议 **12GB** 卡；`--fast-all` 约 **14.4 GiB**，建议 **24GB** 卡；官方只面向**单请求推理**，并发请求返回 **409**（GitHub README；issue #15）。CPU-only 官方不支持。
6. **8GB 开发机只能「试听」，不能当生产**：本机实测 `NVIDIA GeForce RTX 5060 Laptop GPU, 8151 MiB`，当前空闲 `4953 MiB`（2026-10-28 `nvidia-smi`）。官方 eager 7.7GiB 在桌面占用后很可能 OOM；社区 8GB recipe 在 RTX 4060 Laptop 上实测 6.3GiB reserved / 7.2GiB peak；GGUF Q8_0 约 4GB 显存。RTX 50 系（Blackwell）**没有被任何社区实测验证**。
7. **推荐拓扑不是「在 API 进程里 import 模型」，而是「GPU 推理机 + 本地串行网关 + 仓内 Provider」**：GPU 机跑官方 `breeze_infer.api`（单槽），前面加一个单进程队列网关（串行、鉴权、PCM→WAV、voice profile 解析、健康检查）；现有 API 的 4 个 worker 只通过内网 HTTP 调网关。这样既避开官方单槽 409，也不让 4 个 worker 各占一份显存。
8. **接口契约的关键是「引擎域隔离」**：新增 `BreezeLocalTTSProvider`（`name="breeze-local"`，`supports_streaming=False` 首版），返回 `SynthesizedAudio(fmt="wav")`；`CharacterVoiceSpec` 增加 `breeze_voice`/`breeze_instruction`；`TTSManager` 改为按调用路由、失败回落 MiMo 但**不永久改写 `_current_engine`**；Breeze 的 voice profile 不放 `VoiceCatalog`（避免与 MiMo 的 `voice_id` 字符串撞车），由 GPU 网关持有、API 侧只缓存 id/展示名。
9. **MiMo-only 铁律下的灰度只有一条安全路径**：默认 `breeze-local.enabled=false`、全局 `voice.engine` 仍是 `mimo-tts`，只允许**按角色 opt-in**；Breeze 失败回落 MiMo，**MiMo 失败绝不自动回落 Breeze**（否则一次 MiMo 抖动会把流量全打到 GPU/许可风险上）；回滚只需关开关 + 解绑试点角色 + 停 GPU 服务，**不需要数据迁移**。
10. **成本结论与直觉相反**：MiMo 当前「限时免费」，Breeze 托管约 **$60/1M 汉字**；本地 Breeze 没有按字费，但有 GPU 资本/租赁、电费、运维和**未公开的商业许可费**。按自有 24GB 卡约 ¥650–800/月估算，对托管 Breeze 的盈亏平衡约 **1.5–1.9M 汉字/月**；对「MiMo 免费」则永远不划算。**如果只是为了省钱，本地 Breeze 在低用量下并不成立；它成立的理由是质量/隐私/可控，而不是单价。**

### 3.6 容量与延迟估算（🧠 工程推断，需实测）

本仓主链取 `voice_text = reply[:200]`（`orchestrator/optimized_orchestrator.py:2286`），微信语音建议 ≤60 字但代码上限是 200。按中文 4–5 字/秒估算：

| 文本长度 | 音频时长（估） | H100 RTF 0.32 生成时长 | RTX 3060 Q8（「1.5× 实时」=**快于实时**，RTF≈0.67——方向由社区 README 原文钉死，见 §3.2 与 §10.3#9） | 结论 |
|---:|---:|---:|---:|---|
| 40 字 | 8–10s | 2.6–3.2s | 5.3–6.7s | 舒适 |
| 80 字 | 16–20s | 5.1–6.4s | 10.7–13.3s | 可接受 |
| 120 字 | 24–30s | 7.7–9.6s | 16–20s | 偏长 |
| 200 字 | 40–50s | 12.8–16s | 26.7–33.3s | **接近/超过当前 30s 超时**；微信语音过长 |

> **「1.5× 实时」方向声明（2026-10-28 复核钉死）**：社区 GGUF README 原文为 *"roughly 1.5x realtime at Q8_0 on an RTX 3060, 1.3x with guidance"*，且其 Demo 段明写 *"faster than realtime"*——即 1.5 秒音频/1 秒墙钟（RTF≈0.67，**快于实时**）。本表按此方向换算；若未来该仓库改口径或换卡，以 M3 实测为准。这是 Ampere（RTX 3060）实测，RTX 50 系/24GB 生产卡仍需 M3 自测。

**设计结论**：

- Breeze 本地首版 `voice_text` 上限建议 **80 字**（按完整句截取，不硬切），provider 硬上限 200 字但记 warning；不要把 200 字直接送本地 8GB/12GB 卡。**实施位置 = `BreezeLocalTTSProvider` 内部（见 §4.4），orchestrator 的 `reply[:200]` 截取点（`orchestrator/optimized_orchestrator.py:2286`）不改**。
- provider 超时建议 **60s**（含冷启动/队列等待），不要沿用 MiMo 的 30s（`config/system.yaml:154`；`voice/mimo_tts_provider.py:75`）。
- 现有 `voice_duration_ms = len(reply) * 180`（`orchestrator/optimized_orchestrator.py:2326`）是估算，不是真实音频时长；Breeze 本地可以解析 WAV 头得到真实时长，但需要扩展 `SynthesizedAudio` 或 orchestrator，列为 P2，不阻塞首版。

### 3.8 GPU 宿主物理位置与组网（未决，买/租拍板的前置问题）

**矛盾陈述**：§3.5 H1 与 §6.1 的「自有卡 + 电费 + UPS」口径隐含 GPU 机在**本地机房**；但本节与 §3.7 同时要求「私网 1Gbps、API→GPU 延迟 <1ms、不跨公网」，而**生产 API 是公网云服务器**（`deploy/ai-girlfriend.service:21` 绑 `127.0.0.1:8000` + nginx）。两件事不能同时成立——本文没有回答「自有卡和云上 API 怎么连」，这是 §9#4（买卡还是租卡）**之前**必须先答的问题。

| 路径 | 拓扑 | <1ms 私网 | 成本口径变化 | 隐私口径变化 | 判定 |
|---|---|---|---|---|---|
| **N1 云租 GPU**（与 API 同 VPC/同可用区） | GPU 机 = 云上另一台实例，与 API 走 VPC 内网 | ✅ 满足 | §6.1 电费/UPS/资本摊销**不适用**，读「云租」行（¥2.5–4/h）；「买卡」不发生 | 「本地」实为「自管云 VPC」：文本不出该云、但仍过第三方机房 | **推荐默认**；唯一不违反 §3.5/§3.7 组网约束的现成路径 |
| **N2 本地自有卡**（家宽/办公网 ↔ 公网云 API） | 跨公网（VPN/frp/反连） | ❌ 违反 <1ms 与「不跨公网」；模型服务暴露面增大 | 按 §6.1 自有卡行 | 数据真的在本地 | 仅当用户接受降级口径（放宽延迟/安全约束）才可选 |

### 4.2 总体拓扑（推荐）

```text
微信/iLink
  └─ wechat_connector（to_silk/to_amr → send_voice）
          └─ orchestrator.process_message（want_voice → reply[:200]，不改）
          └─ CharacterVoiceSpec.synth_kwargs()（engine / breeze_voice / instruction）
              └─ TTSManager.synthesize（按调用路由 + 回退链）
                  ├─ MiMoTTSProvider（默认，云端）
                  └─ BreezeLocalTTSProvider（opt-in，内网 HTTP）
                      └─ Breeze 本地网关（单进程队列、鉴权、profile 解析、PCM→WAV）
                          └─ 官方 breeze_infer.api（单槽，127.0.0.1:7860）
                              └─ Breeze TTS 2 权重（24GB GPU）
```

**职责边界**：

- `TTSManager`：注册、路由、降级、冷却、健康；不做音色解析。
- `BreezeLocalTTSProvider`：一次内网 HTTP 合成 + 结果归一；不读写全局状态、不做跨引擎回退。
- `Breeze 本地网关`：串行队列、鉴权、profile 解析、调用官方 API、PCM→WAV、健康/指标；**这是新增组件，不属于现有 `voice/` 包**（部署在 GPU 机）。
- `orchestrator`：只决定「要不要语音、用哪段文本」，不拼 provider 参数。
- `CharacterVoiceManager`：角色 → 不可变快照；不决定引擎默认。

### 4.3 Breeze 本地网关契约（新增，部署在 GPU 机）

> 为什么需要网关：官方 `breeze_infer.api` 是**单并发**，4 个 API worker 直接打会 409；官方响应是 **PCM**，而本仓 `SynthesizedAudio` 只认 mp3/wav；官方 README **未提供** profile/鉴权/队列/健康端点。网关把这三件事收口（官方源码是否另有隐藏端点，本次未读，属 ❓）。

**内部 HTTP（仅私网）**

| 方法/路径 | 请求 | 响应 | 说明 |
|---|---|---|---|
| `GET /health` | 无 | `{"available": bool, "model": "...", "gpu": "...", "queue_depth": int, "vram_used_mb": int}` | 不做合成；不占推理槽 |
| `GET /profiles` | 无 | `{"profiles": [{"id": "breeze:lin-wanxia", "name": "林挽夏", "kind": "design", "description": "...", "owner": ""}]}` | **不返回** `ref_audio_path`/`ref_text`；避免音频资产泄露。**`owner` 必填**（空串=平台共享）：§4.8 的绑定校验「普通用户只能绑平台共享或自己的 profile」以此字段为准，两处契约同源，缺 owner 即无法支撑校验 |
| `POST /synthesize` | JSON：`{"text": "...", "profile_id": "breeze:lin-wanxia", "instruction": "...", "cfg_scale": 4, "seed": 42}` | `audio/wav`（24kHz mono s16le）或 JSON 错误 | 网关内部串行；调用官方 API 的 multipart；PCM 加 RIFF 头 |
| `POST /reload` | 无/管理员 token | `{"ok": true}` | 热加载 profiles（可选） |

**错误码**：

| HTTP | 含义 | Provider 行为 |
|---|---|---|
| 400 | 参数/文本/profile 非法 | 不重试；`last_error`；回退 MiMo |
| 401/403 | 网关 token 错 | 不重试；告警；回退 MiMo |
| 409 | 网关队列满/官方单槽冲突 | 网关应内部排队；若仍返回，provider 最多重试 1 次，再回退 |
| 413 | 文本超长 | 不重试；记 `text_too_long` |
| 500/503 | 推理服务不可用/OOM | 回退 MiMo；告警 |
| 504 | 超时 | 回退 MiMo；告警 |

**网关内部调用官方 API**（官方 README 命令/字段）：

```bash
curl -X POST http://127.0.0.1:7860/v1/audio/speech \
  -F "cfg_scale=4" \
  -F "ref_audio=@reference.wav" \
  -F "ref_text=这是参考音频的准确文字稿。" \
  -F "text=[笑] 欢迎回来，今天想聊点什么？" \
  -F "instruction=一位温柔自信的年轻女性，声音清晰，语气亲切。" \
  -F "seed=42" \
  --output output.pcm
```

- 返回 **streaming mono 24kHz s16le PCM**；网关按 `Content-Length`/流式读完，补 44 字节 WAV 头。
- **Voice Design** 不需要 `ref_audio/ref_text`，只传 `text + instruction + cfg_scale=4`（官方 CLI 示例如此；HTTP 是否允许省略 `ref_audio` 待实测，见 §9 #8）。
- **Voice Direction** 需要 `ref_audio + ref_text + instruction`。
- **Voice Clone** 需要 `ref_audio + ref_text`；首版不做（见 §4.9 非目标）。
- 官方 API 的单槽意味着网关必须**串行**；不要用多线程并发打官方 API。

**文件（未来实施）**：`voice/breeze_local_tts_provider.py`（本文不创建）。

**文本长度两级口径（实施位置都在本 provider 内）**：`max_chars` 构造参数是 provider 的**硬上限**（默认 200，超过直接拒绝，防滥用）；`voice.breeze-local.max_chars` 是 provider 在**调用网关前**实施的**软上限**（默认 80，按完整句截取）。软上限解决「200 字在 8GB/12GB 卡上超时」。**明确不改**：主链截取点 `orchestrator/optimized_orchestrator.py:2286`（`voice_text = reply[:200]`）与 `TTSManager` 都不感知 80 字口径——截断只发生在 Breeze provider 内部，**Breeze 失败回退 MiMo 时 MiMo 仍拿原始全文（200 字口径）**，回退音质不受软上限影响。`TTSManager`/orchestrator 不在任何改造清单里为 80 字负责（§7.5 白名单据此不含 orchestrator）。

**输入契约**（kwargs，全部来自调用快照，不写实例状态）：

| key | 类型 | 必填 | 说明 |
|---|---|---|---|
| `engine` | str | 否 | `"breeze-local"`；manager 路由时**必然**剥离（`kwargs.pop("engine", None)`，见 §4.5）——本 provider 收到的 kwargs **永不含 `engine` 键**，fallback 链上直调其它 provider 时同样不带 |
| `breeze_voice` | str | 否 | profile id（如 `breeze:lin-wanxia`）；空则用 `default_profile` |
| `breeze_instruction` | str | 否 | 角色级导演指令；与 `emotion` 合并 |
| `emotion` | str | 否 | 9 个中文情感标签；映射成短指令（见下） |
| `speed` | float\|None | 否 | Breeze 本地 API 没有数值 speed 字段；映射成「语速稍快/稍慢」指令；越界钳制 0.5–2.0 并 warning |
| `pitch` | float\|None | 否 | 同上，映射成「音调略高/略低」；无法映射时记 `tts_param_unsupported`，不静默丢弃 |
| `model` | str | 否 | 仅用于本仓侧权重版本标注；❓官方本地 API 是否接受/需要 `model_id` 字段**未确认**（§9#8，官方源码本次未读）——M2 实测后决定是否透传，**默认不传**；在实测确认前，本表不对其字段形状下任何断言 |

**输出契约**：

- 成功：`SynthesizedAudio(data=wav_bytes, fmt="wav")`；`mime` 由 `voice/audio_result.py:16-19` 映射为 `audio/wav`。
- 失败：`None`，`_last_error` 记录原因；由 `TTSManager` 回退 MiMo。
- 空音频：按失败处理，不返回空 `SynthesizedAudio`（对齐 MiMo `_last_error="API 返回空音频"` 的惯例）。

**为什么返回 WAV 而不是 PCM/MP3**：

1. `SynthesizedAudio` 的 MIME 映射只有 `mp3`/`wav`（`voice/audio_result.py:16-19`）；返回 PCM 需要扩展 MIME 和下游 `coerce_voice_payload`。
2. 微信链 `to_silk`/`to_amr` 用 ffmpeg 按 `source_format` 转码（`voice/audio_converter.py:19-26`、`:81-85`）；WAV 是最稳的输入，不需要在 provider 里引入 mp3 编码器。
3. 官方 API 原生就是 PCM；网关加 WAV 头是零依赖、无损、可校验的封装。

**emotion → instruction 映射（建议）**：

| emotion | instruction 片段 |
|---|---|
| 开心 | 语气轻快，带笑意 |
| 撒娇 | 语气软一点，尾音稍拖 |
| 温柔 | 语气温柔，语速稍慢 |
| 伤心 | 语气低落，语速放慢 |
| 生气 | 语气偏硬，语速稍快 |
| 害怕 | 语气发紧，略带迟疑 |
| 害羞 | 语气轻，略带停顿 |
| 傲娇 | 语气上扬，带一点别扭 |
| 平常 | 自然、平稳 |

> 这些是「导演指令」，不是 MiMo 的 `emotion` 参数；不要原样把 MiMo 的 `emotion`/`pitch` 数值塞给 Breeze。角色级 `breeze_instruction` 优先，情感片段追加，总长度限制 300 字。

**超时/重试/并发**：

- 超时 60s（含网关队列 + 官方冷启动）；连接超时 5s，读超时 60s。
- 409/503：最多重试 1 次（指数退避 0.5s），仍失败回退 MiMo。
- 400/401/403/413：不重试。
- **并发**：provider 内 `asyncio.Semaphore(1)` 只保证单进程；生产 4 worker 必须由网关串行（或跨进程锁）。不要用 provider 内信号量假装解决了账号级并发。

**健康检查（防事件循环阻塞是硬要求）**：

- `TTSProviderBase.health_check()` 是**同步**方法（`voice/tts_provider_base.py:56-63`），而 `TTSManager.health_check()` 也是同步调用（`voice/tts_manager.py:170-182`）。**纠正常见错误**：在同步方法里做「2s 超时的 urllib/socket 探测」**并不能避免阻塞事件循环**——同步 socket 等 2s 就把所在 worker 的循环冻结 2s；`/api/voice/status` 每进程调一次即全进程请求冻结 2s，这是不能接受的线上卡顿面。
- 契约按此设计：① `health_check()` **默认只返回缓存状态**（TTL 60s；每次 `synthesize` 成功/失败刷新 `_last_ok`/`_last_error`/延迟样本；TTL 内不发任何网络请求，零阻塞）；② 缓存过期且调用方明确要实时探测时（管理端/诊断入口），用 `asyncio.to_thread` 包裹网络探测且超时 **≤500ms**，绝不在事件循环里裸调同步 socket；③ provider 内不 `await`（保持基类同步签名）。
- 实时探测目标：`GET {gateway_url}/health`，不合成、不占推理槽。
- 返回：`{"available": bool, "engine": "breeze-local", "endpoint": ..., "model": ..., "queue_depth": ..., "last_error": ..., "stale": bool}`（`stale`=缓存是否过期，供诊断判断可信度）。
- 网关不可达时 `available=False`，但不要抛异常；manager 的 `health_check` 汇总时展示。

### 4.5 `TTSManager` 改造契约

| 能力 | 现状 | 改造后 |
|---|---|---|
| 注册 | 只注册 MiMo；无 key 整个 manager 禁用（`voice/tts_manager.py:60-85`） | 注册 `mimo-tts` + `breeze-local`（仅当 `enabled`）；缺 Breeze 只 warning；**MiMo key 仍必须保留**，否则无回退 |
| 默认引擎 | `voice.engine`（`config/system.yaml:141`） | 不变，仍 `mimo-tts` |
| 按调用路由 | 无（`synthesize` 不接受 engine） | `synthesize(..., engine="breeze-local")`；`requested = kwargs.pop("engine", None)`；`primary = requested or _current_engine` |
| 回退链 | 失败遍历所有 provider，成功即永久切 `_current_engine`（`:141-151`） | `chain = [primary] + routing[primary].fallback`；逐 provider 尝试；**链上每次调用前移除 `engine` 键**（provider 收到的 kwargs 永不含 engine，与 §4.4 输入契约一致）；**不回写 `_current_engine`**；记录 `last_engine_used`；失败引擎冷却 60s |
| 跨引擎参数 | 无 | Breeze→MiMo 丢弃 `breeze_voice`/`breeze_instruction`；MiMo→Breeze 丢弃 `model`/`voice_id`/`speaker_name`；`emotion/speed/pitch` 由各 provider 自己翻译，不原样透传 |
| 健康 | `enabled/current_engine/available_engines/providers/synthesize_count/last_error`（`:170-182`） | 增加 `routing`、`last_engine_used`、`degraded`、每引擎 success/fail/degraded 计数 |

**关键修正**：旧语义「一次瞬时失败永久切到 MiMo」会让 Breeze 永不恢复（`voice/tts_manager.py:148`）。新语义必须是「本次调用回退，主引擎不变，冷却后重试」。现有测试 `tests/test_voice_manager.py` 钉了旧语义，实施时要改为「`last_engine_used=="mimo-tts"` 且 `current_engine=="breeze-local"`」并新增「冷却后恢复」用例（《Breeze 引入设计》§3.3）。

**问题**：`engine` 字段存在，但 `synth_kwargs()` 不输出；`voice_id` 是 MiMo 域，不能给 Breeze 用；`speaker_name` 是 MiMo 预设/SAPI 发音人，不能冒充 Breeze profile。

**改造草案**：

```python
@dataclass(frozen=True)
class CharacterVoiceSpec:
    engine: str = "mimo-tts"
    mimo_model: str = ""
    voice_id: str = ""
    speaker_name: str = ""
    breeze_voice: str = ""          # 新增：Breeze profile id（engine 域内唯一）
    breeze_instruction: str = ""    # 新增：角色级导演指令
    speed: float | None = None
    pitch: float | None = None

    def synth_kwargs(self):
        kwargs = {"engine": self.engine or "mimo-tts"}
        if self.engine == "breeze-local":
            if self.breeze_voice: kwargs["breeze_voice"] = self.breeze_voice
            if self.breeze_instruction: kwargs["breeze_instruction"] = self.breeze_instruction
        else:  # mimo-tts / 旧契约
            if self.mimo_model: kwargs["model"] = self.mimo_model
            voice = self.voice_id or self.speaker_name
            if voice: kwargs["voice_id"] = voice
        if self.speed is not None: kwargs["speed"] = self.speed
        if self.pitch is not None: kwargs["pitch"] = self.pitch
        return kwargs
```

- `resolve_voice_spec()` 从绑定 JSON 读 `breeze_voice`/`breeze_instruction`；旧 JSON 无字段 → 空串 → 用网关默认 profile；**零迁移**。
- `bind_voice()` 继续展平落盘，不需要改 `data/character_voices.json` 格式。
- `engine` 校验放在 API 层（`_validate_contract`），`CharacterVoiceManager` 保持纯存储，避免两处白名单。
- **绑定作用域 = 角色维度（灰度粒度的硬约束）**：`resolve_voice_spec(character_id, user_id)`（`shisi/voice/character_voice.py:134`）按 `character_id` 读绑定；`user_id` 只用于 W14 好感门禁（`affinity.unlocks type=voice` 阈值 75，未达标返回 None 回落引擎默认音色），**不是绑定维度**。把一个角色的 `engine` 绑成 `breeze-local`，影响的是该角色**全部 W14 达标用户**；现契约下不存在「只对某几个用户启用 Breeze」的按用户粒度（要做须新增作用域字段/表，属独立批次，首版不做）。§5.2 的灰度扩量与 §5.3 的回滚粒度均按角色口径表述。

### 4.7 `VoiceCatalog` / Breeze profile 归属

**现状问题**：

- `VoiceCatalog._entries` 以 `voice_id` 单键存储（`voice/voice_catalog.py:108`），`is_known(voice_id)` 全局（`:130-134`）；没有 engine 维度。
- 如果直接把 Breeze profile id 塞进同一个 catalog，MiMo 与 Breeze 同名字符串会互相覆盖/误通过。
- `VoiceCatalog` 是进程级单例 + 整文件写回，多 worker 不保证即时可见（`:137-144`）。

**推荐方案（首版）**：

- **Breeze 的 voice profile 不放进 `VoiceCatalog`**。profile 是 GPU 网关的资产（可能含 `ref_audio_path`/`ref_text`），由网关 `GET /profiles` 暴露 id/展示名/kind/description；API 主机只缓存这份列表。
- `breeze_voice` 使用 **`breeze:` 前缀**（如 `breeze:lin-wanxia`），从命名上就与 MiMo 的 `voice_id` 隔离。
- `VoiceCatalog` 继续只服务 MiMo（clone/design 产物），不迁移、不改键形；避免一次多引擎改造牵动 MiMo 克隆/设计全链。
- API `_validate_contract` 按 engine 分支：
  - `engine=="mimo-tts"`：走 `get_voice_catalog().is_known(voice_id)`（现状）。
  - `engine=="breeze-local"`：走网关 profile 列表校验（缓存 + TTL），**不查 `VoiceCatalog`**。
- `/api/voice/speakers?engine=breeze-local`：合并网关 profile 列表；不返回文件路径/参考文本。
- 若未来要做「统一音色目录」，再引入 `(engine, voice_id)` 复合键；那是独立批次，不在首版。

**备选方案（不推荐首版）**：`VoiceCatalog` 改 `(engine, voice_id)` 复合键，旧条目默认 `mimo-tts`。优点是统一；缺点是所有 MiMo 调用点（`api/routers/voice_routes.py:129`、`api/routers/mimo_voice_routes.py` 多处）都要补 engine，且触碰现有克隆/设计链路，回归面大。

## 5. MiMo-only 铁律下的灰度与回滚

### 5.1 铁律解释（本文的最高约束）

1. **默认引擎永远是 `mimo-tts`**：`config/system.yaml:141` 不改；`voice.engine` 不改。
2. **`breeze-local.enabled` 默认 `false`**：代码可以合入，但不注册/不使用；关闭时行为与现状完全一致。
3. **只允许按角色 opt-in**：`CharacterVoiceSpec.engine="breeze-local"` 的角色才走本地 Breeze；未绑定的会话走 MiMo。
4. **只允许 Breeze → MiMo 回退**：`routing.breeze-local.fallback=["mimo-tts"]`；`routing.mimo-tts.fallback=[]`，**MiMo 失败绝不自动切 Breeze**（避免一次 MiMo 抖动把流量打到 GPU/许可风险）。
5. **不伪装模型**：日志/health 必须显示实际 `engine`/`last_engine_used`；禁止把 Breeze 音频标成 MiMo 或反向。
6. **AGENTS L6 不提前改**：`AGENTS.md:226` 仍为「MiMo Cloud TTS 为唯一引擎」；只有用户正式修订后，才同步改 `voice/__init__.py:2`、`voice/tts_manager.py:60-62`、`config/system.yaml:141`。本文是预研，不是修订。
7. **SAPI 语义不变**：Windows 本地兜底仍在 MiMo provider 内部（`voice/mimo_tts_provider.py:306-365`）；Breeze 本地不是 SAPI 的替代，Linux 生产仍无 SAPI。

### 5.2 灰度阶段（G0–G4）

| 阶段 | 流量 | 入口 | 前置条件 | 观察指标 | 退出/回滚 |
|---|---|---|---|---|---|
| **G0 离线试听** | 0（不接生产） | 开发机/独立 GPU 机 CLI | 权重下载、官方 API 跑通 | TTFA、RTF、VRAM、音质主观 | 不通过即停，不影响生产 |
| **G1 离线回放**（原「影子」重设计） | 0（**生产零参与**） | 在 GPU 机/开发机用网关或 CLI 直接回放采样文本（样本来源：生产语音请求的文本抽样、脱敏后导出；**不经生产进程、不注册 provider、不占用 MiMo 流量**） | G0 通过；网关/Provider 单测通过；样本集准备 | 生成成功率、延迟、显存、音质抽听 | 不通过即停——回放本身不接生产，无需任何开关 |
| **G2 单角色** | 1 个测试角色（=其**全部 W14 达标用户**，绑定是角色维度，无法只圈单个用户，见 §4.6） | 角色绑定 `engine="breeze-local"` | G1 通过；`breeze-local.enabled=true`；MiMo key 在位 | 成功率、回落率、P95 延迟、用户反馈 | 解绑角色 + 关开关 |
| **G3 小灰度** | 5%–10% **试点角色**（按角色数扩量；每绑一个角色即覆盖其全部达标用户） | 管理端逐个绑定 | G2 稳定 7 天 | 同上 + 成本/GPU 利用率 | 批量解绑 + 关开关 |

> **为什么 G1 不做「生产内影子流量」**：影子流量必须在 `breeze-local.enabled=false` 时就把 provider 注册进生产 `TTSManager` 并旁路采样——这直接违反 §5.1 规则 2（关闭态行为与现状完全一致），还需要新增影子/采样开关（§4.9）与影子组件（§7.5 白名单），三者都要为首版不背的复杂度买单。重设计后的 G1 用**离线回放**拿到同等信息（成功率/延迟/显存/音质），生产侧零改动、零开关、零风险；若未来确需真影子（观测生产实时文本的在线表现），再立项做 `breeze-local.shadow` 配置位 + 独立旁路组件，不在本文契约内。
| **G4 扩大** | 25%→50%→全量 opt-in | 管理端 | G3 稳定 7 天；盲评通过 | 同上 + 30 天复盘 | 回 G2/G3 或全关 |

**准入/退出阈值（建议，非事实）**：

- 生成成功率 ≥99%（网关 200 + 非空 WAV）。
- 回退率 ≤5%；409 = 0；OOM = 0。
- P95 总延迟（含队列）≤10s（80 字文本）；TTFA ≤3s（如启用流式则另算）。
- 盲评：同一文本/角色，Breeze 偏好率 ≥60%，且无人耳可辨的断字/吞字/音色崩坏。
- 用户负反馈率不高于 MiMo 基线。
- GPU 显存峰值 ≤85%；队列深度 ≤5。

### 5.3 回滚 Runbook（按顺序）

1. **停止新增流量**：管理端把所有试点角色的 `engine` 改回 `mimo-tts`；或直接 `POST/PUT` 解绑 Breeze profile。**回滚粒度 = 角色**（绑定是角色维度，见 §4.6；解绑一个角色即恢复该角色全部用户走 MiMo，不存在按用户回滚）。
2. **关开关**：`voice.breeze-local.enabled=false`；重启 API 服务（配置非热重载，`orchestrator/_init_mixin.py` 只在初始化读）。
3. **停 GPU 服务**：先停网关，再停 `breeze_infer.api`；确认 GPU 显存释放。
4. **核验**：`GET /api/voice/status` 显示 `breeze-local` 不可用/未启用；发一条语音请求，确认走 MiMo；文本回复正常。
5. **数据**：首版无 DB 迁移；`data/character_voices.json` 中 Breeze 字段保留不读即可；GPU 网关侧 profile 资产不删，便于复盘；API 侧只缓存 profile 列表（内存），无需落盘回滚。
6. **记录**：`LOG.md` 记回滚原因、时间、指标；保留网关日志/GPU 日志 7 天。

**回滚触发条件**（任一）：

- 许可/法务判定不可用。
- GPU 机不可用/OOM/驱动故障 >5 分钟。
- Breeze 回退率 >20% 持续 10 分钟。
- P95 延迟 >15s 或用户投诉明显增加。
- 音质出现系统性断字/吞字/音色崩坏。
- 成本/运维超出预算。

### 5.4 失败矩阵

| 失败 | 现象 | 处理 | 用户感知 |
|---|---|---|---|
| 网关不可达 | provider 连接失败 | 回退 MiMo；告警 | 仍有语音（MiMo） |
| 官方 API 409 | 并发冲突 | 网关排队；provider 重试 1 次；再回退 | 可能延迟，最终有语音 |
| OOM | 500/503 | 回退 MiMo；自动关 Breeze；告警 | 仍有语音（MiMo） |
| 超时 | 504 | 回退 MiMo；告警 | 可能延迟，最终有语音 |
| 空音频 | 200 但 0 字节 | 按失败；回退 MiMo | 仍有语音（MiMo） |
| 文本过长 | 413 | 不重试；回退 MiMo；记 `text_too_long` | 有语音（MiMo，可能更长） |
| MiMo 也失败 | 两端都不可用 | `TTSManager` 返回 None；orchestrator 捕获异常（`optimized_orchestrator.py:2311-2312`） | **只有文字，没有语音**；消息不失败 |
| SAPI（仅 Windows） | 本地兜底 | MiMo 内部 `fallback_local` | Windows 开发机有兜底；Linux 生产无 |

| **只为省钱，月语音 >5M 汉字** | 本地可能比托管便宜；但先过许可/运维/质量三关 |
| **要质量提升（中文女声/角色音色）** | 先做盲评；AA 排名不等于中文角色音色；不通过不引入 |
| **要隐私/数据不出境** | 本地是唯一路径；但许可仍是硬门 |
| **要避免 MiMo 免费期结束风险** | 本地可作为备选，但固定成本高；建议先谈 MiMo 商业价/备选云 TTS |
| **不想增加运维** | 不引入；本地需要 GPU 机、驱动、队列、监控、on-call |

### 6.5 什么会改变结论

- MiMo 开始收费且价格 > 本地摊销 → 本地更有吸引力。
- BreezeBlue 商业许可报价可接受/可谈 → 许可门打开。
- 24GB GPU 价格下降/云租降价 → 平衡点下移。
- 盲评证明 Breeze 中文女声显著优于 MiMo → 质量理由成立。
- Breeze 官方发布生产级并发服务/多卡批处理 → 运维/吞吐改善。
- 许可条款更新（例如允许商用/放宽非商用） → 需重新法务评估。
