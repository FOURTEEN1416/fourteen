# 设计原则（≤7 条）

> 原则是"不应期"——无论多紧急都不能违反的底线。
> 违反一条原则 =  需要一个新的 ADR 来允许它。

## 原则 1：API 全集，不重不漏

整个项目只对外暴露一套 API 路由。内部可以有多个实现，但对外接口必须统一。新增功能只需要改一个入口。

## 原则 2：状态边界清晰

UI 状态（弹窗/表单输入）→ Zustand store。服务端数据（角色/聊天/配置）→ React Query。两者混用时，拆成两个独立状态管理，绝不混在一个 store 里。

## 原则 3：一个配置源

同一个配置项只能在一个地方定义。如果两个配置文件都有同一个字段，必须定义优先级规则（当前 system.yaml 优先）。

## 原则 4：层间单向依赖

```
前端 API 层 → 前端页面层 → 前端组件层
                 ↓
           前端 Store 层
```
禁止：页面直接 import 旧 API 文件（shisiClient/characterApi/memoryApi）绕过 client.ts 体系。
禁止：Store 层直接调用 API。

## 原则 5：测试覆盖核心路径

后端核心流程（聊天/情感/记忆/角色 CRUD）必须有测试覆盖。管理台 UI 的测试优先级低于后端。

## 原则 6：决策需记录

任何影响项目结构的决策必须在 `docs/adr/` 留下记录。没有 ADR 的架构变更视为"临时方案"，下个迭代必须补 ADR 或回滚。

## 原则 7：CI 门禁

每次提交必须通过自动化检查（测试 + 构建 + ADR 完整性）。CI 红了不合并。紧急情况下可走豁免流程（需在 48 小时内修复或回滚）。
