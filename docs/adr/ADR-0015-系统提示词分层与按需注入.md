# ADR-0015：系统提示词分层与按需注入

**状态**：提议（设计已定，分阶段落地中；第 1、2 项已实现，见「落地状态」）
**日期**：2026-09-19
**关联**：`orchestrator/optimized_orchestrator.py`（`_prepare_context` / `_persona`）、
`utils/reply_mode.py`、`proactive/ase_engine.py`、`wechat_direct/wechat_connector.py`、
`docs/FUNCTION_INVENTORY.md`（MESSAGE 区）

## 背景：一次线上体验复盘暴露的系统性问题

2026-09-19 的连续排查（微信端真实对话 + 生产日志）暴露出**同一类病根在不同层反复出现**。
按层归类如下（均已定位，标 ✅ 者已修）：

### 投递层（✅ 已修）

| # | 问题 | 实证 |
|---|------|------|
| 1 | 投递结果**五层谎报成功** | 底层返回 `{"ret": -2, "errmsg": "prepare failed"}`，而 `_post_api`（不看业务码）→ `send_text`（丢返回值）→ `run_api._send`（丢 bool）→ `_send_to_all`（不抛异常即成功）→ console（日志兜底必"成功"）全部报成功。用户零接收，日志连续多日显示「已投递」 |
| 2 | 静默时段**生成即扣配额**，投递层再丢弃 | 23–7 点 8 条全丢却全计数 → 配额凌晨满额 → 白天全天零投递，每日重演 |
| 3 | websocket **零客户端也算送达** | 广播对空客户端集合静默返回 → 记「已送达: websocket」并提交配额 |
| 4 | 通道未就绪**静默跳过** | `instance=None` 时 `continue` 无日志 → 「为什么微信一条都没发」无线索 |

### 上下文层（本 ADR 主题；#5–#7 已部分缓解）

| # | 问题 | 实证 |
|---|------|------|
| 5 | `scenario` 被当作**永久事实**而非开场情境 | 角色卡写「你刚从公交车上下来…手里拿着一个白色的小风扇…说了句『来了啊』」，被逐轮注入 → 机器人反复追问「路上堵不堵/热不热/慢慢走/要不要来家里坐坐」；用户明确否认也纠正不过来 ✅ |
| 6 | 角色卡内**互相冲突的格式要求**，无二选一 | 同一段对话里 14:17「（她捏着白色小风扇的手指轻轻收紧了一下，耳尖泛起…）」vs 14:52「嗯，下了一下午了／雨声还挺舒服的」——小说式与口语式随机跳 ✅ |
| 7 | **设定权重压过对话内容**（"设定驱动"而非"对话驱动"） | 用户观察「似乎纯靠系统提示词加角色设定生出回复逻辑，而不是根据聊天内容真正仿真人回复」。**注意：归因经过实测修正**——见下节「实测数据（含一次自我纠正）」 |
| 8 | 追问**无上下文**，硬插通用催促语 | 生成 prompt 只含上一句 AI 回复 → 只能产出「在吗」「人呢」「再不理我我就撤了哦」✅ |

### 稳定性层

| # | 问题 | 实证 |
|---|------|------|
| 9 | `chat_sync` 每次 `asyncio.run` 新建事件循环 → httpx 连接池失效、`aclose()` 在死循环上抛异常 | 生产日志持续刷 `Task exception was never retrieved ... Event loop is closed` ✅ |
| 10 | **超时被当成"检测到攻击"**（fail-closed 用反了） | 3s 预算 vs provider 9~33s → 每次都超时 → 用户正常消息「怎么已读不回？」被判 Prompt 注入并拒绝 ✅ |
| 11 | 会话锁 + 慢 provider → 罐头语 | 用户连发两条即得「处理中, 请稍候...」；超 30s 得「抱歉，处理超时」 |

**共同病根**：**把「不确定」当成「确定」，把「静态设定」当成「动态事实」**。
投递层的 `ret<0` 是"未知→却报成功"；注入检测的超时是"未知→却报攻击"；
`scenario` 是"开场情境→却当当前事实"。

## 实测数据（含一次自我纠正）

**本文档初稿曾断言"system prompt 约 1.3 万字，历史仅数百字"——这是错的。**
实测推翻了它，记录于此以免后续决策建立在错误前提上：

在 25 个角色的角色卡上实测 `_load_character_persona_segment()` 输出（即 L1 常驻段）：

| 指标 | 实测值 |
|------|--------|
| 最大 | **1843 字符** |
| 中位 | **1415 字符** |
| 最小 | 364 字符 |
| 超过 2500 字符的角色 | **0 / 25** |
| 当前生效角色 62105bca | **1210 字符** |

**结论修正**：角色常驻段**不是**数量级问题（与"一万三千字"的直觉差一个数量级）。
那么"设定驱动"的真实成因是：

1. **`scenario` 被永久锚定**（#5）—— 这是最强的牵引力，且**与字数无关**：
   短短一句"你刚从公交车上下来"逐轮重复，就足以把对话拉回开场画面
2. **角色卡内互相冲突的指令**（#6）—— 模型无法二选一，只能随机挑
3. **动态块未受控**——`rag_context` / `memory_context` / `chat_summary` / `world_info`
   与 50 条历史的实际占比**此前完全不可观测**（本轮已加埋点，见「落地状态」）
4. 基座模型能力（agnes / glm-4-flash 档位）

**方法论教训**：没有埋点就只能靠直觉论证架构，而直觉可能差一个数量级。
因此本 ADR 把「注入可观测」列为**与分层同等重要的交付项**——先度量，再优化。

## 调研：行业标准怎么做

### 1. Anthropic — 上下文工程的四个模式

来自 Anthropic 官方文档与 Claude Code 团队实践：

- **Just-in-time context**：不要一次全塞进去，按需让 agent 用工具取（"不会把整本建筑规范塞进 system prompt，而是需要时调用 `lookup_building_code`"）
- **Compaction**：长对话把旧轮次摘要成结构化块
- **Prompt caching**：把稳定部分标记为可缓存，跨请求复用
- **Memory tool**：跨会话记忆通过工具读写

**Claude Code 的关键工程结论（与本文最相关）**：

> 「The best way to do this is **static content first, dynamic content last**.」
>
> 其排序为：`Static system prompt & Tools（全局缓存）→ CLAUDE.md（项目级缓存）→
> Session context（会话级缓存）→ Conversation messages`

并明确：**按稳定性排序**；任何上游块变动会使下游全部缓存失效
（"Cache hits drop from 70%+ to 7% on any incautious edit"）；
**更新信息要走 messages 而不是改 system prompt**，否则缓存全废；
**不要在会话中途换模型**。

成本量级（Anthropic 定价）：缓存**读 0.1×**、**写 1.25×（5 分钟）/ 2×（1 小时）**。
生产数据：把动态内容移到缓存断点之后，ProjectDiscovery 的 LLM 账单降 **59%**。

### 2. SillyTavern World Info / Character Card V2·V3 — 角色卡场景的事实标准

这是**与本项目形态完全一致**（角色卡 + 人设 + 长期聊天）的行业标准，直接回答用户的问题：

**V2 字段语义（"常驻 vs 条件"是核心分野）**

| 字段 | 注入方式 |
|------|----------|
| `description` / `personality` | **永久注入**（"fixed tax"，每轮都付） |
| `scenario` | **"situational frame, **sets the scene before the first message**"** —— 开场框架，**不是永久事实** |
| `first_mes` | 作为第一条 assistant 轮次 |
| `mes_example` | 示例对话，**风格锚点**（"Three well-formed exchanges outperform a paragraph of prose describing the same voice"） |
| `character_book`（lorebook） | **关键词触发的按需注入** |

**Lorebook 条目结构（本 ADR 要照搬的部分）**

`keys`（触发词，支持正则）/ `secondary keys`（AND 条件）/ `selective` /
`constant`（无视关键词恒注入）/ `position`（before_char / after_char）/
`depth`（插入到倒数第 N 条消息附近）/ `insertion order` / `scan_depth` /
`probability` / **递归激活**（条目互相引用）

**V3 的 `@@` 装饰器**（把"简单关键词转储"升级为"精确注入工具"）：
`@@depth` / `@@position` / `@@role` / `@@scan_depth` / `@@activate_only_after` /
`@@activate_only_every` / `@@keep_activate_after_match` / `@@dont_activate_after_match` /
`@@additional_keys` / `@@exclude_keys` / `@@ignore_on_max_context` /
`@@dont_activate` `@@activate` / `@@is_greeting`

**两条直接可用于本项目的结论**：

1. **成本模型**：「400 token 的 description + 2000 token 的 lorebook，
   比 2400 token 的 description **每轮便宜得多** —— 因为条目只在关键词出现时才触发。」
2. **位置即权重**：「放在 prompt **靠后、靠近最新消息**的内容，影响力强于埋在顶部的；
   前端把它暴露为 `depth` / `position` 设置。」—— 这正是"该压制的放前面、
   该生效的放后面"的机制化表达。

## 决策

**采用「四层上下文金字塔 + 按需注入」，并以段落注册表（Segment Registry）替代字符串拼接。**

### 分层定义（按稳定性排序，稳定在前）

| 层 | 内容 | 变化频率 | 缓存 | 预算 |
|----|------|----------|------|------|
| **L0 平台静态** | 全局行为准则、安全边界、工具定义 | 跨用户/跨角色恒定 | ✅ 可缓存 | 不限（越稳越好） |
| **L1 角色常驻** | 角色身份 / 说话风格 / 口头禅 / `core_anchors` | 每个角色恒定 | ✅ 按角色缓存 | **护栏式硬预算**：实测 25 个角色为 364–1843 字符、0 个超限，故预算取 **≤2500 字符**（约 1.5–2× 当前最大值）——超限条目降级为 L2，而非丢弃 |
| **L2 按需注入** | 背景设定 / 世界信息 / 关系史 / 具体事实（lorebook） | 关键词触发 | ❌（内容随轮次变） | 按触发数动态裁剪 |
| **L3 会话态** | 情绪、亲密度、最近 N 轮、对话摘要、**回复模式指令** | 每轮可变 | ❌ | 固定窗口 |
| **L4 当轮** | 用户这一句 | 每轮 | ❌ | — |

**关键约束（照搬 Claude Code 结论）**：
**L0/L1 必须字节稳定**——同一角色连续两轮的前缀 hash 相同；
**任何"时间戳 / 每轮态势"信息一律不得进入 L0/L1**（只进 L3 或走 message）；
缓存断点打在 **L1 末尾**（最后一个跨请求不变的块）。

### 把本项目的具体问题映射到分层

| 问题 | 归属层 | 处置 |
|------|--------|------|
| #5 `scenario` 场景漂移 | 应为 **L2 开场条目**，而非 L1 常驻 | 等价于 lorebook：`@@is_greeting` / `@@activate_only_after 0` + `@@dont_activate_after_match`；**已按此语义修**（改为"开场情境，不代表当前正在发生"） |
| #6 格式要求冲突 | 属 **L3**（会话态、可切换） | 已抽出 `utils/reply_mode.py`，指令置于 L3 末尾并声明"本节优先于角色卡中冲突的格式要求" |
| #7 设定权重压过对话 | L1 无预算 + L2 缺失 | 给 L1 设硬预算；把"背景/关系/事实"从 L1 迁到 L2 按需注入 |
| #8 追问无上下文 | L3 会话态缺失 | 已记录最近 8 条真实往来并注入追问 prompt |

### 落地形态：段落注册表（不新增重型框架）

```python
# 概念形态（伪代码）
segments = [
    Segment(id="platform_rules", layer=L0, text=..., cacheable=True),
    Segment(id="character_core", layer=L1, text=..., cacheable=True, budget=2500),
    Segment(id="lorebook",       layer=L2, text=..., cacheable=False),   # 按触发动态生成
    Segment(id="session_state",  layer=L3, text=...),
    Segment(id="reply_mode",     layer=L3, text=...),
]
prompt = render(segments, budget=window - reserved_for_history)
```

要点：
1. **每段有 id / layer / cacheable / budget**，可单独启停、可观测（能打日志说"本轮注入了哪些段、各占多少 token"）
2. **L1 超预算时按 `insertion_order` 把低优先条目降级到 L2**（关键词触发），而不是整段丢弃
3. **L2 触发规则**：关键词（支持 `@@additional_keys` / `@@exclude_keys`）+ `scan_depth` +
   `frequency`/`probability` + `@@activate_only_after`；**支持递归激活**（条目互相引用）
4. **冲突处理显式化**：段之间存在覆盖关系时（如角色卡要求"必须写动作神态" vs 模式要求"严禁动作"），
   由**层序**决定而非模型随机挑——上层（L3）显式声明优先级

### 与角色卡规范的兼容

新增字段与 Character Card **V2/V3 对齐**（`character_book` + 条目字段名保持一致），
好处：可直接导入/导出市面上的角色卡，且 V2/V3 工具链（编辑器、转换器）可复用。
本项目现有字段（`personality_text` / `scenario` / `creator_notes`）作为兼容层保留。

## 后果与取舍

**收益**
- 常驻 token 从"人格+场景全量"降到"角色核心 + 触发的少量条目"，**每轮成本与延迟双降**
- 场景漂移、风格乱跳这类"设定压过对话"的症状有**机制层面**的根治（而非再补一句提示词）
- 前缀稳定 → 对支持自动前缀缓存的 provider（OpenAI ≥1024 token 自动缓存、
  智谱上下文缓存）直接省成本；对不支持的，至少省 token
- 注入内容可观测（本轮注入了哪些条目、各多少 token）→ 可回归、可调参

**代价与风险**
- 需要为每个角色维护 lorebook（关键词质量决定效果）；**关键词过宽会每轮触发**（等于没省），
  过窄则召回不足 → 需要召回率/误触发率指标
- 段落注册表是一次中等规模重构，涉及 `_prepare_context` / `_persona` 与角色卡 schema
- 历史窗口与 L2 预算相互挤压：两者都吃 context，需明确的分配策略

## 未采纳的方案

1. **直接砍掉角色卡 / 缩小 description**：会丢人设，且治标不治本（#7 的根因是**没有分层**，
   不是"文本太长"）
2. **纯向量 RAG 注入一切**：对"格式/规则"类指令不可靠（这类内容必须稳定命中，
   而相似度检索有召回波动）；行业已验证的形态是 **常驻 + 关键词触发** 二元模型
   （RAG 适合"事实"类，与 lorebook 互补而非替代）
3. **全面 Just-in-time 工具检索**：微信端无工具调用循环，对一个"只发一条消息"的场景过重
4. **只靠提示词修补**（继续在末尾追加"不要…"）：本会话已证明其边际收益递减——
   #5/#6 都是"加了指令但机制没变"，靠指令压是概率性的

## 验收标准（可测）

1. **前缀稳定性**：同一角色连续两轮请求，L0+L1 拼接后的前缀 hash 相同（CI 可测）
2. **L1 预算**：L1 常驻段 token ≤ 2500；超限条目自动降级到 L2 而非丢弃
3. **注入可观测**：每轮日志含 `segments=[(id, tokens, triggered_by)]`
4. **场景漂移回归**：用户说「我没在路上」后，后续 N 轮内不得再出现"路上/堵/慢慢走"类表述
5. **风格一致性回归**：沉浸式模式下回复**零括号动作描写**（可正则断言）
6. **成本/延迟**：相同对话长度下，L1 常驻 token 下降 ≥50%
