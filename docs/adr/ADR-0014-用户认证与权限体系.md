# ADR-0014：用户认证与权限体系

## 状态
Accepted

## 上下文

项目原有的 API 鉴权仅依赖 `X-API-Key` 静态密钥，存在以下问题：

1. 所有用户共享同一个 API Key，无法区分操作者
2. 管理控制台（前端）没有登录机制，任何知道 URL 的人都可以访问
3. 后端无法追踪"谁做了什么操作"
4. 缺乏用户角色体系（admin / editor / viewer），无法做细粒度权限控制

随着项目成熟和多用户管理需求，需要引入完整的 JWT 认证体系。

## 决策

### 认证方案

采用 **Username/Email + Password 注册登录 + JWT (access + refresh tokens)**。

| 层 | 技术 | 说明 |
|----|------|------|
| 密码存储 | bcrypt (passlib[bcrypt]) | 不可逆哈希，即使 DB 泄露也无法还原密码 |
| Token 格式 | JWT (python-jose) | 无状态，payload 包含 user_id + role + exp |
| Access Token | 30 分钟过期 | 短时效降低泄漏风险 |
| Refresh Token | 7 天过期 | 存储在 DB（UserSession 表），可吊销 |
| Token 刷新 | POST /api/auth/refresh | 用 refresh token 换取新 access token |
| 登出 | POST /api/auth/logout | 删除 DB 中的 refresh token 记录 |

### 路由鉴权分层

```
公开路由（无需认证）：
  POST /api/auth/register     — 注册
  POST /api/auth/login        — 登录
  POST /api/auth/refresh      — 刷新 token

认证路由（需要 Bearer token）：
  POST /api/auth/logout       — 登出
  GET  /api/auth/me           — 获取当前用户信息

管理员路由（需要 Bearer token + role=admin）：
  GET    /api/admin/users     — 用户列表
  GET    /api/admin/users/{id} — 用户详情
  PATCH  /api/admin/users/{id} — 修改用户
  DELETE /api/admin/users/{id} — 删除用户
```

### 前端认证流程

1. 页面加载时，authStore.init() 从 localStorage 恢复 token
2. AuthGuard 组件检查认证状态 → 未登录跳转 /login
3. LoginPage 提供登录/注册表单
4. client.ts 请求拦截器自动从 store 注入 `Authorization: Bearer <token>` 头
5. 401 响应时自动跳回登录页

### 与现有 X-API-Key 的关系

- X-API-Key 仍然是**内部服务级**鉴权（后端之间、微信通道等）
- JWT 是**用户级**鉴权（管理控制台）
- 两个体系共存，不互相替代
- 公开路由仍可配置 X-API-Key 保护（可选）

## 影响

- 正面：每个操作可追踪到具体用户
- 正面：支持多角色权限控制，为后续功能铺路
- 正面：登出后可吊销 token，安全性大幅提升
- 正面：前端路由级保护，未登录用户看不到管理界面
- 代价：新增 2 个核心后端文件 + 1 个数据库模型 + 5 个前端文件
- 代价：用户需要注册才能使用管理控制台（增加一步操作）
- 代价：现有后端测试需要补充认证相关的 fixture

## 对应 Fitness Function

FF-014：auth 端点健康检查（register → login → refresh → me → logout 循环）
FF-015：前端路由守卫覆盖检查（所有受保护路由必须被 AuthGuard 包裹）

```
  api/routers/admin_routes.py — /api/admin/* 路由（管理员权限）

```
