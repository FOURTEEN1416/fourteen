### 1.2 三方案对照

| 维度 | A. 描述注入 | B. 多模态直传 | C. 描述 + 情绪标签 |
|------|-----------|--------------|------------------|
| 做法 | 图 → VLM 描述文本 → 作该条 `text` 入对话管线 | 图作为 `image_url` 直接进主对话 LLM 的 messages | VLM 同时输出描述 + 情绪，同时喂情感引擎 |
| 改动量 | **最小**：`_handle_message` 1 处 + 复用 `VisionHandler` | 大：需改 `orchestrator` / LLM 主链路 → **超 W3 白名单** | 中：依赖 V3 先定档 |
| 白名单 | ✅ 全在 `wechat_direct/` + `multimodal/` | ❌ 需扩权 | ⚠️ 部分跨界 |
| 情感效果 | 弱（只剩文字语义，丢掉画面情绪） | **强**（模型自己看画面） | 中 |
| 失败降级 | 沿用 ASR 既有占位模式，天然一致 | 需新设计 | 需新设计 |
| 社区证据 | 通用做法 | **Open-LLM-VTuber（13.7k★）采用**：「Visual perception，支持 camera、screen recording and screenshots」→ 多模态 LLM | — |

### 1.3 社区调研证据（GitHub-First，✅ 已验证）

| 仓库 | Stars | 活跃度 | 与本项目的相关性 |
|------|-------|--------|-----------------|
| `BradyFU/Awesome-Multimodal-Large-Language-Models` | 18010 | 2026-09-14 更新 | MLLM 权威目录（Directory-First 入口） |
| `Open-LLM-VTuber/Open-LLM-VTuber` | 13755 | 2026-09-14 更新 | **最贴近**：Python 语音交互 AI 伴侣；支持**视觉感知**（相机/录屏/截图）+ 多模态 LLM；ASR 用 FunASR/Faster-Whisper；**官方支持 HumeAI EVI 作为 Agent** |
| `moeru-ai/airi` | 49129 | 2026-09-14 更新 | 自托管伴侣，实时语音 |
| `memodb-io/memobase` | 2896 | 2026-09-14 更新 | AI 伴侣长期记忆（用户画像型） |

**关键发现**：头部开源伴侣项目对图像走的是**多模态直传**（给支持视觉的 LLM 直接看图），而不是「先转文字描述」。描述注入会**丢掉画面中的情绪信息**——这恰恰与本项目的情感陪伴定位冲突。

### 1.4 推荐

> **推荐 B（多模态直传）为主 + A（描述注入）为降级**

理由（双向论证）：
- **支持 B**：① 情感陪伴的核心价值在「看懂你的情绪」，只看描述文字会丢画面情绪；② 契约已核对通过（`_build_messages` 原样透传多模态 content 数组），技术上可行；③ 与社区主流一致。
- **反对 B**：**超出 W3 白名单**（需改 `orchestrator`），改动面大，且主对话 LLM 未必是视觉模型 → 需要 `chat(model=...)` 指定 vision 模型（该参数**已存在**，`:132`）。
- **折中**：先落 A（在白名单内、1 处接线、立即可用），把 B 作为**第二步**提交扩权申请单。

⚠️ **必须同时解决的 3 个前置**：① 入站 `image_data` 格式（裸 base64 需补 data URL 前缀）；② `VisionHandler` 透传 `model=`；③ 统一 ASR 双 owner。

## 3. V4 · 语音声学情绪（云端 API 选型）

### 3.1 候选（✅ 已验证）

| 方案 | 已证实内容 |
|------|-----------|
| **Hume AI EVI** ✅ | 官方原文：EVI「**measures users' nuanced vocal modulations** and responds to them」；用例明确列出 **Digital Companions**「Build emotionally aware companions for seniors, kids, or mental wellness support」；提供 Python SDK（`HumeAI/hume-python-sdk`） |
| 开源 SER（对照） | `abikaki/awesome-speech-emotion-recognition`（101★，2026-09-05 更新）｜`declare-lab/awesome-emotion-recognition-in-conversations`（283★）｜`aita-lab/awesome-multimodal-fusion-emotion-recognition` |

### 3.2 关键判断

⚠️ **Hume EVI 是「语音到语音」的实时对话式 API**，不是「传一段音频 → 返回情绪标签」的 drop-in 端点。而本项目 `ASRHandler` 的现有形态是「音频 → 文本」（`:118-122` 只取 `text`）。

→ 因此 V4 有**两条不同形态**：
- **V4-a（轻量）**：在 ASR 之外**并行**跑一个「音频 → 情绪标签」的调用，把标签并入情感画像。**推荐先做这条**，改动最小、可独立开关。
- **V4-b（重）**：整体切换到 EVI 式实时语音对话。**不建议本期做**（会重构语音链路）。

## 4. 显式告知 / 同意机制设计（V3/V4 共用）

| 环节 | 设计 |
|------|------|
| 首次触发 | 用户首次发图/发语音时，**先回一条明确告知**：「我可以试着理解你照片里的表情 / 你声音里的情绪，这需要把图片/音频送到 XX 云处理。是否开启？」 |
| 同意记录 | 存 `consent_records` 表（`users.db` 中**已存在该表** ✅，当前 0 行）→ 记录 user_id / 能力 / 同意时间 / 版本 |
| 拒绝后 | 不再请求，且**能力保持关闭**（不降级到偷偷上传） |
| 撤回 | 设置页提供关闭开关；关闭后清空该能力的同意记录 |
| 不落盘原文 | 图/音频**只在内存**，处理完立即释放；日志**禁止**打印 base64 或音频字节；只保留结果标签与文本描述 |
