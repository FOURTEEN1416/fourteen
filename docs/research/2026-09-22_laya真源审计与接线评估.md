> **任务**：评估 GitHub `NandhaKishorM/laya`（HF `convaiinnovations/laya`，pip `laya`）作为轻量决策框架

## 一句话结论

**有条件引入（当前不可直接替代任何判断模块）**——项目真实、许可证干净、包同源、CPU 延迟声称有仓库内实测佐证；
但其自有 benchmark 数据表明白底座 checkpoint **零样本决策接近随机**，直接替 `decide_proactive` 的「该不该发」判
是拿 0.36 精度的组件替换一个（虽有成本但）真实工作的 LLM 判。引入的前提是：收集本项目主动消息事件语料 → 微调 →
中文域校准温度拟合 → 影子模式验证，四步缺一即退回。最小落地点为 `llm_proactive` 的前置 gate（见 §3.4），
**不建议**接 `tool_gate` L0.5（违 L0 零成本设计且给每条消息加 84–460ms）。

## 2. 三个候选接线点现状（主检出代码实况，只读）

### 2.1 `proactive/llm_proactive.py::decide_proactive` + `scheduler._llm_proactive_one_user`

现状行为链（scheduler.py:835–1020 逐行核）：每 5 分钟 tick × 每用户，先过**零成本前置闸**三连
（web enabled → `_is_quiet_hours()` 静默前置（P1-49：正是为了不再白烧 LLM 调用）→ `_llm_proactive_next_ok`
等待窗账本），全部通过才组一次 LLM 调用：`build_proactive_context`（人设/画像/最后一句/热度/紧迫度信号
urgency 仅作参考注入）→ `decide_proactive` 一次云调用**同时产出** `should_contact + wait_minutes + message + reason`
→ `sanitize_message` → `_deliver`，投递失败走指数退避账本（5m→120m，块E 已落盘）。

### 2.2 `orchestrator/tool_gate.py::should_escalate`（L0 晋级线）

纯 re.compile 正则（时间/指令动词/查询/画像四组），**每用户消息必过**。设计红线写在模块 docstring：
「L0 零成本晋级线——只晋级不裁决，宁滥勿缺，未命中直接走主聊天链路，**零成本零延迟**」。误晋级代价 = 一次 L1
LLM function-calling 终审（兜底），不存在漏判代价。

### 2.3 `proactive/ase_engine.py` urgency

纯确定性算术：`missing_bonus = min(..., 时长函数)` + `base(+0.1/tick)` + 情感/场景 bonus，阈值 `total >= 4.0`
触发候选生成。**无任何「判断」需要模型**——它是被 §2.1 当作 `urgency_signal` 特征喂给 LLM 的输入。

## 3. 接线评估（逐候选：替代后行为差异 / 部署 / 延迟 / 成本 / 复杂度）

### 3.1 候选①：laya 替代 `decide_proactive` 的「该不该发」判 —— **唯一有真实价值的点位，但当前不可直替**

- **架构（若引入）**：三级门——现有零成本前置闸（不动）→ **laya `noul`「现在该主动联系吗」gate（CPU，本地）** →
  仅当 gate=true 才发起 LLM 调用（职责收缩为纯 message+wait 生成）。这正是官方 Router/Agent 的 System-1/System-2 用法。
- **行为差异与风险（致命项）**：按 §1.2 自有数据，零样本 base checkpoint 在决策类任务 **0.34–0.36 ≈ 随机**；
  中文走 multilingual checkpoint（zh-CN MASSIVE 0.63 是 20 类意图任务，非本域），且**出厂不带拟合温度**——
  即 gate 输出的「校准置信度」在零样本下既不校准也不可靠。假阴性=该发不发（用户感知的「她今天没理我」），
  假阳性=多烧一次 LLM（现状本来就在烧）。**结论：零样本直替 = 用噪声替换信号，不可接受；须先微调。**
- **部署位置**：只在云服务器（本机 16GB 且不 24h 开机——主动消息调度在生产端跑，本机引入无意义，直接排除）。
  内存占用**估算**（未实测，禁止安装纪律）：multilingual 322M，CPU 上强制 fp32（agent.py:236）→ 权重 ~1.3GB +
  torch 运行时 ≈ **常驻 2.0–2.5GB**；而 `deploy/README.deploy.md` 最低 4GB/推荐 8GB RAM——若生产为 4GB 档
  （实机内存**未证实**，本窗禁 ssh），uvicorn+chroma 之上再常驻 2GB+ 不可行；8GB 档可行。
  好消息：生产 `--workers 1`（P0-7 后，`deploy/ai-girlfriend.service` 实核）→ 单进程持有一个 Router 即可，无 4 倍复制问题。
- **延迟对 5 分钟轮询的影响：可忽略。** 84–464ms/问 × 每 tick 数用户，对比 300s 周期与 LLM 云调用本身的秒级延迟。
  ⚠️ 陷阱：`Router(max_loaded=1)` 懒加载模式语言切换重建模型实测 **CPU 7.4s/次**（README 自曝）——必须
  `preload(["multilingual"])` 常驻，禁止懒加载。
- **云调用成本节省（估算）**：现状非静默时段每活跃用户日最多 ~204 次决策调用（17h×12），
  其中绝大多数 should_contact=false（每日配额 8 条）。若 gate 精度达标（微调后 noul 参考值 0.857），
  **90%+ 决策级 LLM 调用可被本地拦截**；节省绝对金额取决于供应商单价（本项目链 agnes 首选，单价未在本窗核验，不给美元数）。
  代价：每条真实要发的消息从 1 次调用变 2 次（gate 后仍需生成 message）——净省发生在「不该发」的大多数轮次。
- **引入复杂度：中**。新依赖 safetensors+hub（低冲突，§1.5）+ 权重私有投递/镜像拉取 + 常驻内存预算 +
  **微调流水线**（官方 Kaggle 2×T4 notebook 4–5h/30k 题，零代码成本）+ 中文温度拟合 + 新增失效路径。
- **失败模式（模型挂了退化成什么）**：laya 进程内异常/OOM → **必须回落现状路径（直接 LLM 决策）**，
  即 laya 是纯旁路优化器而非新关键路径；这条降级线不写就不能上线（契合本项目「失败可见」教训族）。

### 3.2 候选②：laya 当 `tool_gate` L0.5 —— **不推荐**

- L0 的存在理由 = 零成本零延迟（docstring 原文），每条用户消息都过；laya 每消息 +84–460ms（CPU）+ 常驻 2GB，
  **直接违反被收编模块的设计契约**。
- L0 语义是「宁滥勿缺的晋级」，误晋级由 L1 兜底、无漏判代价 → 决策模型在这里**没有可赚的东西**：
  它只能在「省一次 L1 调用」上起作用，而代价是给 100% 消息（含纯闲聊多数派）加推理延迟和一个 DL 依赖。
- 中文口语托付句（「明早六点叫我」）零样本判外域 + 温度未拟合 → 漏晋级 = 「说了会叫却没叫」生产事故的复发通道
  （v1.30 家族），这是本项目最不可接受的一类回归。
- 结论：**否决**。正则 L0 维持现状。

### 3.3 候选③：`ase_engine` 紧迫度/发消息决策 —— **否决（无判断可替代）**

urgency 是确定性时间算术（§2.2），无分类问题；`_select_type_by_urgency` 是阈值查表。引入模型只会把可调试的
纯函数变成不可解释的黑盒，违背该模块 v1.13 以来的可观测性方向（`_last_skip_reason` 体系）。
laya 的正确位置在 urgency 的**下游**（§3.1 中作为特征注入，替代的是 LLM 而非算术）。

### 3.4 若引入的最小落地路径（P0 只接一处）

**P0 唯一接点 = §3.1 的 llm_proactive gate，且以影子模式起步**，四步顺序执行、每步独立可回滚：

1. **语料积累（零改动，现在就能做）**：`append_proactive_event` 账本已记录每 tick 的 sent/reason/wait——
   以「LLM 判 should_contact + 用户后续是否回应」为弱标注源，攒 ≥3k 条中文主动消息决策样本（agent_plane.db 可直接导出）。
2. **微调 + 校准**：官方 notebook（Kaggle 2×T4 免费档，4–5h）在自建 typed-decisions 数据集上微调
   `laya-multilingual` 底座；**在留出的本项目数据上拟合温度**（multilingual 出厂无温度，官方明言「fit them before
   relying on its probabilities」）。验收线：held-out「该发」判定 noul 精度 ≥0.85 且 ECE ≤0.1。
3. **影子模式**：生产 gate 并行跑 laya（只记日志不拦截），对照同轮 LLM 决策 ≥1 周，假阴性率 <2% 才进入第 4 步。
4. **正式接线**：前置闸后插 laya gate（`preload(["multilingual"])`，常驻 + 异常回落 LLM 原路径），
   LLM 职责收缩为 message/wait 生成。回滚 = 配置开关一键退回纯 LLM。

## 4. 正反双向论据与最终判定

**正方（引入的理由）**：决策闭环本地化后 90%+ 主动决策云调用可省；CPU <0.5s 对 5 分钟轮询零压力；
单次 forward pass **无 JSON 解析失败面**（现状 `parse_decision` 要处理 empty/no_json/bad_json/not_object 四种失败）；
Apache-2.0 可商用 + 权重开源；不依赖任何云 API（契合「除 LLM 外全依赖云 API」的收缩方向）；
工程成熟度实证（4 天 60+ 外部 issue、dependabot、字节级同源发布）。

**反方（风险）**：base checkpoint 零样本决策 ≈ 随机（官方自曝），价值全押在「微调后」——引入的不是现成能力而是一条
训练流水线承诺；微调后精度对本域（中文情感陪伴时机判断，比 typed-decisions 更模糊）迁移率**无任何已发表证据**；
常驻 ~2GB RAM 撞 4GB 生产机下限（实机内存未证实）；作者 4 天前注册 HF org、star 增速异常，长期维护性待观察；
校准置信度要可信必须先有可信的域内标签数据。

**推荐（明确表态，不只列选项）**：**有条件引入**——判定不是「用/不用」而是「何时用」：
第 1 步（语料积累）零成本零风险，**立即做**；第 2–4 步以语料达标 + 微调验收线过了为闸门，过了才接线，
不过则永久停在纯 LLM 现状（现状 v1.37 块D 刚把决策层接地修好，本身已在良性轨道）。
**任何形态的零样本直替（哪怕只接一处）都是不可引入级别的错误，本审计的核心否决项。**

> **后续实证补记（同日 22:50 主控窗，见 §5 #1/#2）**：两项前置「未证实」已 ssh 实测关闭——生产机 available 仅 **1.8Gi**（laya fp32 常驻推算 2.0–2.5GB 超界）且 **HF 域不可直连**（需权重私有投递）。**第 2–4 步的触发条件由「语料+验收线」追加硬性一项：生产机内存升档（或 gate 服务独立宿主）**；在此之前第 1 步语料积累照常推进。
