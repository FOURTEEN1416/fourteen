# 第三轮深挖 — 隐性系统问题与「说不清」的质量病

> 日期：2026-09-20  
> 用户指令：「继续深度挖掘！！！！！！！还是不够，我提到的问题也只是一部分，还有很多我不好描述的问题也存在」  
> 方法：对照 Artemis AgentRuntime（2458 行）/ nana 全链路，与本项目 **微信→UserManager→Orchestrator→LLM→后处理** 端到端通读，专挖「用户说不清但能感觉到」的机制病  
> 前序：`2026-09-20_AI伴侣开源对照深研…` + `…全模块对标通读…`

---

## 0. 「说不清」通常是什么

用户体感：**有时像人、有时突然机器；同一角色前后不像；答应了却没做到；回得慢还回得空；记住了又像没记住。**  
下面不是「功能有没有」，而是**链路里互相打架的机制**。

---

## 1. 双管线分叉：流式 vs 非流式（核心隐病）

| 环节 | 非流式 `process_message` | 流式 `process_message_stream` |
|------|--------------------------|-------------------------------|
| 工具调用 | `_run_tools_if_needed` + 防假承诺 | `_prepare_context` 同路径（工具在 prepare 内） |
| 一致性 | **同步** `check_and_correct_reply` — 可改写回复 | **后台** `_async_consistency_check` — **只记日志，不改已推送文本** |
| 安全输出 | 检查后可替换为 safe_alternative，**用户看到替换后文本** | 流式抽检不安全则停推 + 可能 safe；路径更绕 |
| 空/超时 | 返回罐头语（已尽量不入库） | 生成中失败 yield 罐头语 |
| 微信路径 | `_call_user_manager` → **非流式** | Web 多走流式 |

**隐病**
1. **同一句「不像人设」在 web（流式）发生时不修正，在微信（非流式）会被二次 LLM 改写** —— 两端行为不一致。
2. 流式用户**先看到坏句子**，再无修正；非流式修正会**增加延迟**且可能「改得更假」。
3. 一致性检查在流式里调用 `get_chat_context` 只为算 chat_round —— **又一次 DB 查询**，与 prepare 重复（非流式已传 chat_round 优化过，流式未必）。

**可改点（X1–X3）**
- X1：统一策略 — **生成前约束（prompt）优先，生成后修正仅对「硬违规」**（自称 AI / 明显人设违背），且两端同一策略。
- X2：流式硬违规 → 最后一段 yield「更正」或合并前先缓冲至句末再推（延迟与正确性权衡可配置）。
- X3：chat_round 从 prepare 结果透传，禁止 stream 二次查库。

## 2. 双情感引擎 / 双亲密度真源（体感漂移）

| 持有者 | 载体 | 用途 |
|--------|------|------|
| `UserManager` | per (user×character) `EmotionEngine` | 微信链路主状态 |
| `OptimizedOrchestrator._request_emotion_engines` | per (session×character) TTL 缓存 | Web/API 未注入外部 engine 时 |
| `PersonaEngine` 内嵌 emotion | 另一份 | 一致性/风格层 |
| `CharacterAggregate.emotional_state` | 角色卡数值 | prompt 当前状态段 |

**隐病**
- 微信传入 external engine 时 OK；**web 与微信若 session 键形态不同**，可能读到不同 engine → **同一用户两端亲密度不一致**。
- prompt「当前状态」读 `CharacterAggregate` 映射后的状态，**与 ASE/user engine 的 affection_points 可能不同步**（映射时机、是否 persist）。
- affinity_state 持久化挂在 **UserManager**，**orchestrator 请求级 engine 不写** → web 对话可能不进持久化。

**可改点（Y1–Y3）**
- Y1：**唯一 owner** = EmotionEngine 实例（session_key 映射），orchestrator 只引用不新建。
- Y2：prompt 状态段 **只读** 该 engine → scale 映射，禁止 CharacterAggregate 自算。
- Y3：所有路径统一 `session_key = user_key::character_id`，affinity_state 键一致。

## 3. 异步后处理：说「记住了」但下一轮还没记住

`_after_process` → 单线程 `_bg_executor.submit(after_chat)`：

- 回复已发出，**facts/history 可能尚未落库**
- 用户下一句立刻问「我刚才说什么」→ **可能读到空**
- ASE `on_chat` 在 `_after_process` 同步调用，**记忆异步** —— 情绪/配额已变、记忆未变

**隐病**：「她记性时好时坏」——不全是检索问题，是 **写路径滞后**。

**可改点（Z1–Z2）**
- Z1：关键 facts **同步轻量写入**（仅 chat_history 两行），重抽取仍异步。
- Z2：`after_chat` 返回 future，process_message 可选 `await` 超时 200ms（微信可关）。

## 4. 旁路「机器腔」注入（人设被系统句子打穿）

| 来源 | 文本 | 是否人设口吻 |
|------|------|--------------|
| `counter_rebuttal` | 「这已经是第 5 次了。你不用跟我装没事。」 | **硬编码，非角色卡** |
| 空回复兜底 | 「刚才没接上，你再说一句？」 | 通用口语，**非角色** |
| 超时/异常 | 「抱歉，处理超时…」「（消息处理异常…）」 | 机器腔（微信侧） |
| 工具结果提示 | system 内「请根据以上结果自然地回复」 | 指令腔 |
| 安全替换 | safe_alternative | 通用安全腔 |

**隐病**
- 反诘在 `process_message` **拼接到 reply 尾部**，**不经角色口吻重写**。
- 多处兜底**互不协调**，用户体感「有时温柔有时客服」。

**可改点（W1–W3）**
- W1：所有旁路句走 **角色化改写模板**（从卡 mes_example/口头禅抽 1 句），或 system 注入「若系统提示则用你的口吻转述」。
- W2：反诘改为 **进下一轮 system 约束**（「用户连续否认情绪 N 次，可温柔但坚定追问」），**不直接 append 字符串**。
- W3：统一 `utils/fallback_lines.py`：按 character_id + reply_mode 生成。

## 5. Prompt 多 Owner 叠加（人设漂移的温床）

生产 system 组装顺序（再强调）：
```
PersonaEngine 默认「十四」人格/风格/约束
→ CharacterAggregate（角色卡身份+知识+PHI）
→ orchestrator「必须扮演的角色」片段
→ persona_enhancement
→ tool_results
→ reply_mode（最后）
```

**隐病**
- **default 卡与文学角色卡共用 PersonaEngine 注入层** → 米彩说话可能带十四口吻。
- reply_mode 靠「最后一句」压制格式，**压不住身份层矛盾**（「你叫十四」+「你是米彩」）。
- `persona_enhancement` 内容不透明时再叠一层。

**可改点**：见前文 B11–B13 + **身份唯一 Owner 白名单测试**（prompt 不得同时含两个角色名）。

## 6. 上下文重复注入（token 浪费 + 模型「不知道听谁的」）

同轮可能同时出现：
1. `memory_context` 字符串（formatted facts/summary）
2. `chat_history` messages（DB 会话）
3. `chat_summary` 段
4. RAG `# 角色知识库`
5. 世界信息
6. 工具 JSON

**隐病**：模型在重复/矛盾信息上**随机采样** → 「有时记得有时不记得」「同一问题两种答法」。

**可改点（Q1–Q2）**
- Q1：**ContextPolicy**：同一事实只保留最高优先级一份（Artemis）。
- Q2：明确预算：history≤N 消息、memory≤K 条、knowledge≤C 字符，**超预算丢弃并记 inspection**。

---

## 7. 工具链 vs 对话链（假承诺的残余形态）

我们已有 L0/L1/ask_user/防假承诺。残余：
- 工具结果以 **JSON 进 system**，无 untrusted 信封 → 模型可能复述 JSON 或被结果里的指令带偏。
- 单轮 **无 max_tool_calls / 同名去重**（Artemis：step≤3 / turn≤8 / result≤6000 字）。
- 工具失败时 ToolResult(False) 进 prompt，模型可能编造成功。

**可改点**：D1/D2 + untrusted 包装 + 失败时 prompt 明确「工具失败，不得声称已执行」。

---

## 8. 微信投递层「像机器」的瞬间

`wechat_connector`：
- 空回复 → 「刚才没接上，你再说一句？」
- 拆句发送 + 打字延迟（体验好）
- `messages_today` 用 `time.strftime` **本地日**（OK）
- 错误时发送括号腔（已改部分）

**隐病**：兜底句**固定**，高频失败时用户连续收到同一句 → 机器人感。

**可改点**：兜底句池 + 角色口吻 + 当日去重。

## 9. Artemis AgentRuntime 对照（我们缺的「系统感」能力）

| Artemis 能力 | 我们 | 体感影响 |
|--------------|------|----------|
| `working_messages` 原生 tools 循环（tool 进 messages） | 工具结果进 system 字符串 | 工具上下文权重低、格式乱 |
| `structured_response=True` + `parse_chat_reply_result`（needs_retry） | 自然语言，无重试信号 | 坏输出直接给用户 |
| `visual_observation` **系统向字段与用户可见 reply 分离** | 无 | 状态回写与表演混在一起 |
| `session_state`：仅当 recent&lt;2 注入跨会话尾巴，untrusted+预算 | history 全量或 summary，无「会话刚开始才补」策略 | 新会话冷启动 vs 长会话重复 |
| `RuntimeLoopSettings` 可配置 + clamp | 魔法数散落 | 难调参 |
| `cancel_checker` / 进度回调 | 部分有超时，无统一取消 | 难以打断长工具 |
| `PromptPatchContribution` 插件补丁 | 无 | 扩展靠改 orchestrator |
| 运行时事实 **防注入信封** | 无 | 知识/工具污染指令 |
