## 机制 1：nana 记忆归档 + 用户画像 JSON 回写

### 对端实现路径
- `peer-projects/nana/backend/conversation.py`
- `peer-projects/nana/backend/prompts/memory_extract.md`

### 调用链（入口 → 中间层 → 落库/落 profile）
1. `ConversationHistory.add_dialog(user, assistant)`  
   - append `turns`  
   - `db.save_dialog(...)`（**失败只 print，不阻塞对话**）  
   - `if len(turns) >= max_turns(20): await _auto_archive()`
2. `_auto_archive()`  
   - `archive_count = len(turns)//2`（**满 20 归档 10，不是全量**）  
   - `result = await _extract_memory(archive_turns)`  
   - **无论 extract 成功与否，最后都 `turns = turns[archive_count:]`**（先推进窗口，再写侧车）
3. `_extract_memory`  
   - 无 llm → 返回 `{summary: 原文拼接, user_facts: None}`  
   - 有 llm → `memory_extract.md.format(conversation_text=...)` → `llm.chat(..., temperature=0.3)`  
   - 异常 → **同样降级为原文 summary + user_facts=None**
4. `_parse_extraction(raw)`  
   - 先 `json.loads`  
   - 失败再正则剥 ` ```json … ``` ` 再 parse  
   - 再失败 → raise（上层 except 降级）  
   - 字段默认：`emotional_valence=0.0, importance=0.5, user_facts=None`
5. 落侧车  
   - **Tier2 summaries.json**：append `{id, summary, topics, timestamp, turn_count, emotional_valence, emotional_tags, importance}` + `_save_summaries()`  
   - embedding：`_embed_summary` 失败静默跳过  
   - **Tier3 profile**：`if result["user_facts"]: _merge_profile(...)`
6. `_merge_profile(new_facts)`  
   - `load_profile()`（JSON 文件，缺字段补 DEFAULT）  
   - `basic_info.*`：**非空则覆盖**（`if value and key in profile.basic_info`）  
   - 数组字段 `preferences/interests/life_events/relationships/other_facts`：**append if not already present**（无删除语义）  
   - `_save_profile` + `last_updated=iso`

### 关键数据结构
- `PROFILE_PATH = save/memory/user_profile.json`
- `DEFAULT_PROFILE`：
```json
{
  "basic_info": {"name":"","gender":"","location":"","occupation":"","birthday":""},
  "preferences": [], "interests": [], "life_events": [],
  "relationships": [], "other_facts": [],
  "raw_notes": "", "last_updated": ""
}
```
- memory_extract 输出契约（prompt 原文约束）：
  - 只提取**用户明确说过的新信息**；没有则空数组/空对象  
  - `basic_info` 只填明确提到的字段  
  - 禁止编造

### 核心算法
- 归档触发：`max_turns=20` → 半窗滚动  
- 检索打分（`retrieve`，关键词路径）：
  - topic 命中 +2  
  - 字符重叠 +0.1/字  
  - 时间衰减 `0.5^(days/30)`  
  - importance 乘子 `(0.5 + importance)`  
  - 当前情绪与 `emotional_tags` 匹配 → **score × 1.5**  
  - 无命中 → 最近 N 条兜底
- 每轮 `reply` 槽位 `user_info` → `update_raw_notes()` **覆盖** raw_notes（不是 append）

### 失败与降级
| 失败点 | 降级行为 |
|--------|----------|
| db 写失败 | 不阻塞；窗口仍在内存 |
| LLM extract 失败 | summary=原文；user_facts=None（**不写 profile**） |
| JSON 解析失败 | 尝试代码块剥离；仍失败→上层降级 |
| embedding 失败 | 跳过缓存；关键词检索仍可用 |
| profile 文件损坏 | `load_profile` 返回 DEFAULT |

### 可迁移点 / 不可迁移点
- **可迁移**：半窗归档、extract JSON 字段集、basic_info 覆盖合并、失败不阻塞聊天、情绪共鸣加权召回、reply JSON 绑定状态回写
- **不可直接搬**：单用户 JSON 文件真源（本仓多用户微信必须 SQLite + session_key）；`MAX_TOOL_CALLS=3` 的串行 LLM 决策循环成本高（本仓已有 L0/L1）

### 对本仓落点与验收探针
- 落点：`tools/builtin/profile_agent_tools.py::run_profile_sync_agent`（已有雏形）+ `user_profile.upsert`  
- 缺口：extract **失败不写** 的契约要钉死；`basic_info` 覆盖 vs 否认清空语义；**状态回写目前不绑在主回复 JSON**（旁路 profile_sync，延迟/丢调用风险）

## 机制 2：nana 回复 JSON 状态闭环（reply 槽位 + emotion_update）

### 对端实现路径
- `peer-projects/nana/backend/prompts/reply.md`
- `peer-projects/nana/backend/main_agent.py::reply_stream/_handle_full_response`
- `peer-projects/nana/backend/emotional_state.py::update_from_llm`

### 调用链
1. `reply_stream(message)`  
   - `_run_tool_loop` → tool_results 文本  
   - `_get_relevant_memories`（n_results=2, emotion-aware）  
   - `prompt_template.format(**slots)`：  
     `user_info / current_datetime / tool_results / chat_history / user_message / memory / mood_state / time_context / relationship_context`
2. LLM **强制输出 JSON**：  
   `{reply, user_info, expression, emotion_update{emotion,direction,delta}, quick_replies?}`
3. 流结束后 `_handle_full_response`：  
   - `user_info` 非空 → `conversation_history.update_raw_notes`  
   - `emotion_update` → `emotional_state.update_from_llm`  
   - `record_interaction()`  
   - `add_dialog` 落对话

### 关键数据结构（情绪状态 JSON）
```json
{
  "mood": {"valence":0,"arousal":0.3,"dominant_emotion":"傲娇","intensity":0.5,"last_updated":""},
  "relationship": {"affection":0,"trust":0,"familiarity":0,"stage":"stranger","interaction_count":0,...},
  "daily": {"date":"","interactions_today":0},
  "heartbeat": {"response_rate":0.0,"last_proactive":""}
}
```
- `EMOTION_MAP`：情绪标签 → `{valence, arousal}`  
- `RELATIONSHIP_STAGES`：stranger→special，带 **hint 文案进 prompt**

### 核心算法（update_from_llm）
```
delta = clamp(raw_delta, 0.05, 0.2)
if emotion not in EMOTION_MAP: return  # 未知标签忽略
if direction == "up":
    valence += (target.valence - valence) * delta
    arousal += (target.arousal - arousal) * delta
    intensity += delta*0.5 (cap 1.0)
    dominant = emotion
else:
    valence *= (1 - delta*0.5)   # 向中性
    arousal = 0.3 + (arousal-0.3)*(1-delta*0.5)
    intensity -= delta*0.5 (floor 0.1)
    if dominant==emotion: dominant="傲娇"
```
- 离线衰减：启动 `0.9^min(hours,24)` 向中性  
- 跨天：valence×0.5 等向中性

### 失败与降级
- JSON 解析失败：`extract_reply_text` 回落 raw；情绪不更新  
- 未知 emotion 标签：**直接 return，不写**  
- 文件保存失败：print 后继续（内存态仍更新）

### 可迁移 / 不可迁移
- **可迁移**：「回复即状态增量」闭环、阶段 hint 进 prompt、delta 钳制、失败时状态不污染  
- **不可照搬**：nana 单 JSON 把对话与工具/画像/情绪绑死；本仓微信多用户 + L0/L1 工具管线需要 **工具结果独立信封** + **profile 服务端注入 session_key**（LLM 不可决定 user_id）

### 本仓落点
- 落点：主回复仍走自然语言（保留）；**需要 EventLedger 记「本轮情绪/关系增量」**，或可选轻量 sidecar JSON 仅用于 probed 模式  
- 探针：因果回放——给定 reply_id，能查到「注入了哪些槽位 + 状态增量」

## 机制 4：my-raze 近重复强化 + 亲密度绑定容量/召回

### 对端实现路径
- `peer-projects/my-raze/shared/memory.ts`
- `peer-projects/my-raze/server/memory.ts`

### 调用链（写入）
1. 聊天路径 **fire-and-forget** `maybeExtractMemories`  
   - 仅当 `messageCount % EXTRACTION_EVERY_N_MESSAGES(10) == 0`  
   - 取最近 `10*2` 条消息拼 transcript  
   - LLM `gpt-4o-mini` + `response_format=json_object` + temperature=0.2  
   - `parseExtractionResponse`：取第一个 `{...}` 到最后一个 `}`；**zod safeParse 失败返回 []**（不抛）  
   - content trim + 截断到 `MEMORY_MAX_LENGTH=200`
2. `storeExtractedMemories(userId, girlfriendId, candidates)`  
   - 读该 user×girlfriend **全部** existing  
   - `bigramOverlap(cand, mem) >= 0.6`（双向取或）→ **reinforce**：  
     `weight = min(100, weight+5); lastRecalledAt=now`（**不插新行**）  
   - 否则 insert：`weight = clamp(importance*10, 10, 90)`  
   - 唯一索引冲突 → SQL `LEAST(100, weight+5)`  
3. `enforceMemoryCapacity`  
   - capacity = `20 + level*10`（level clamp 1..10）  
   - 删 **pinned=false** 中 weight 最低、最旧的 excess 行  
   - **pinned 永不驱逐**

### 打分与注入（读路径）
```
timeDecayFactor(lastTouched): 0.5 + 0.5*exp(-days/14)
base = (weight/100) * freshness
overlap = max(bigram(content,msg), bigram(msg,content))
affinity = min(2.5, 5*overlap)
pin = pinned ? 0.5 : 0
score = base + affinity + pin
k = memoryInjectionK(level) = min(4 + ceil(level/2), 10)
```
- 注入文案：`【你记得的关于用户的事】` + bullet + 「自然运用，不要机械罗列」  
- 召中时 fire-and-forget 刷新 `lastRecalledAt`

### 失败与降级
- 提取异常：`log.error` 后吞掉，**聊天不失败**  
- parse 失败：返回 []  
- db 不可用：直接 return 0/空  
- 无命中仍可注入高 weight 新鲜记忆（依赖 base，不强制关键词）

### 对照本仓缺口
- 本仓 `user_facts` 已有 access_count/user_key，但 **写路径 near-dup reinforce 是否完整**需在实施批钉死  
- k(level) 包 Q B-c 已做 → 本批验收探针复测  
- capacity 驱逐：本仓回收站已有，**亲密度绑定容量**可作 P1 选项，非 P0

### 本仓落点
