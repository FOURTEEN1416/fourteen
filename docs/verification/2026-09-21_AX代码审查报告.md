## 阻断问题（必须修）

### B1 · 因果回放空转：orchestrator 未写 `turn_id` / `reply_id`

- **位置**：`orchestrator/optimized_orchestrator.py` → `append_chat_events(...)`；`runtime.append_chat_events` 默认 `turn_id=""`
- **现象**：账本里 user/slots/reply/tool_result 的 `turn_id` 全空；`/api/agent-plane/replay?turn_id=…` 与控制台回放**永远查不到切片**（除非手写空过滤）
- **影响**：交接书验收 F6「因果回放」在生产**未真正闭环**
- **修复**：每轮生成 `turn_id`/`reply_id` 并写入全部事件（含 tool_result）

### B2 · 投影读上限截断：`project_profile` / `ensure_profile_seeded` 用 `limit=500` 且不按类型过滤

- **位置**：`profile_projection.project_profile`、`runtime.ensure_profile_seeded` → `ledger.query(session_key, limit=500)`（`ORDER BY id ASC`）
- **现象**：会话事件超过 500 条后，**画像事件若落在窗口外**：
  1. `ensure_profile_seeded` 看不到 profile 类型 → **反复 seed**  
  2. `project_profile` 丢掉后续更正 → **prompt 画像回退到旧值/空**
- **影响**：长会话画像更正失效、账本被 seed 污染；串台探针也可能误判
- **修复**：画像投影只查 `profile_update` / `profile_correct`（各自 limit 后按 id 归并）

### B3 · LLM 自己的 `wait_minutes` 被完全忽略

- **位置**：`scheduler._llm_proactive_one_user` 解析并落账，**从不用于跳过后续 tick**
- **现象**：`ase_check` 每 **5 分钟** × 每个 user_key **必定再打一次 LLM**；模型已说「过 3 小时再考虑」仍每 5 分钟询问
- **影响**：成本与主动消息过密；「LLM 判时机」只做了一半
- **定性**：这是**执行 LLM 自身决策**，不是重新引入阶段硬编码闸（符合用户裁决）
- **修复**：按 `wait_minutes` 写入 per-user 下次可决策时间；窗口内 skip 并记 `llm_wait_window`
