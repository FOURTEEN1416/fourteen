# 2026-09-18 CI 门禁治理与本地拦截加固 — 验证报告

> 关联：`LOG.md` 五十七条（CI 十四连红根治）
> 触发：五十七条暴露真问题——**所有门禁只在 CI 执行，本地零拦截能力**，致 14 次失败横跨 3 天无人察觉
> 裁决：用户「执行」两项待裁决

---

## 1. 决策依据（调研实证，非推断）

### 1.1 为什么必须锁到 patch 级，而非 minor 级

对 `astral-sh/ruff` 与 `astral-sh/ruff-pre-commit` 的 releases / tags 实证：

- **发版节奏**：0.16.1（2026-07-30）→ 0.16.8（2026-09-16），**48 天 8 个版本**，约 6 天/版。
- **关键**：patch 版本之间亦含 `### Rule changes`，而项目 `select = ["E","F","W","I","N","UP","B","SIM"]` **正覆盖**这些规则：

| 版本 | 官方 release note 中的规则变更 | 对本项目的含义 |
|---|---|---|
| 0.16.6 | `DTZ901` 改为拒绝 `tzinfo=None` | 修**漏报** → 原先侥幸通过的代码可能转红 |
| 0.16.7 | `D211`/`D203` 诊断修正；`UP035` 停止推荐已移除的 `typing.no_type_check_decorator` | 诊断文本与命中面双变化 |
| 0.16.8 | `UP040` fix 转为 unsafe；`TC001-003` 于 Python 3.15+ 偏好 lazy import；`SIM117` 嵌套检测修复 | fix 行为变化 |

**结论**：原设想 `>=0.16.8,<0.17` **不能杜绝**漂移——0.16.9 起仍会自动进入。故锁定至 patch 级 `>=0.16.8,<0.16.9`。

### 1.2 为什么门禁必须单一真源

原 4 个门禁为 CI YAML **内联 bash + grep**。若本地 hook 复刻一份 grep，则产生**两套实现**——改一处忘另一处即新的漂移源，违反 AGENTS §1.2「不引入重复 owner」。故抽为 Python 单一真源，CI 与本地共用。

## 3. 验证证据

### 3.1 等价性验证（移植正确性的核心）

构造 13 行样本，**逐门禁**对照「CI 原生 grep 语法」与「ci_gates.py 的 Python re」：

| 门禁 | 语法族 | grep 原生命中行 | ci_gates.py 命中行 | 结论 |
|---|---|---|---|---|
| FF-0003 | **BRE**（`\|` 为「或」） | `[1,2,3,4,5,6,7]` | 同 | **等价** |
| FF-0006 | **ERE**（`grep -qE`） | `[10,11]` | 同 | **等价** |
| FF-0007 | **BRE** | `[1,2,3,4,5,7,8]` | 同 | **等价** |
| ADR | `grep -oP '\K'`（PCRE） | `ADR-1.A` → `1` | 同 | **等价** |

⚠️ 移植要点：FF-0003/0007 用的是 **BRE**（`\|` 表示或），FF-0006 用 **ERE**——二者不可混用 grep 开关，否则语义漂移。`\K` 为 PCRE 专有，Python 需改写为捕获组。

### 3.2 门禁负向验证（证明「能拦截」而非仅「通过」）

向 `frontend/src/api/client.ts` 注入 `export function __gate_probe()`：

```
[1/1] FF-0006 client.ts 只做 re-export
  ❌ FF-0006 违规：client.ts 包含函数定义，应移到领域文件中
  frontend/src/api/client.ts:300:export function __gate_probe() {
```

exit=1，且**精确定位到行号**；还原后 `git diff` 无输出（无损）且门禁恢复通过。

## 4. 顺带修正的既有缺陷

**`adr-integrity` 的 Supersedes 检查形同虚设**：

```bash
# 原实现（bash）
if [ -n "$supersedes" ] && [ ! -f "docs/adr/ADR-$supersedes-*.md" ]; then
```

`-f` **不展开通配符**，该断言对含 `*` 的字面路径恒为真 → 检查无实际判别力。

已改为 `Path.glob(f"ADR-{ref}-*.md")` 真实匹配。该门禁只告警不失败，故不影响 CI 红绿，但修正后行为正确。

**现存告警（非本次引入，留待裁决）**：`docs/adr/ADR-0002-统一API全集.md` 引用 `Supersedes ADR-1.A`，而实际文件名采用四位补零（`ADR-0001-…`）——编号格式不一致导致匹配不上。属 ADR 文档自身的一致性问题，未在本批次处理。

## 5. 边界与遗留

1. **生效前提**：pre-commit hook 需执行 `pre-commit install` 才装载（不装则配置文件零作用，不阻塞提交）——满足「不强制阻塞」的要求。
2. **可绕过**：`git commit --no-verify` 可跳过；在 GitHub 网页直接改文件亦绕过 → **CI 仍是唯一权威**，pre-commit 只是提前拦截。
3. ⚠️ **版本一致性铁律**：`pyproject.toml` 的 ruff 约束与 `.pre-commit-config.yaml` 中 `ruff-pre-commit` 的 rev **必须同源**（当前均 0.16.8）。改一处须同步另一处，否则又是一处漂移源（两文件已互写注释提示）。
4. **实测规避的环境坑**：本机 PATH 中 `python` 指向 WorkBuddy 自有解释器（3.13.12），非项目使用的系统 Python 3.12 —— 故 `ci_gates.py` 被刻意限制为**仅标准库**；若将来该脚本需要项目依赖，须改用官方隔离 hook 或显式解释器路径。
5. **未落地（建议后续）**：开启 GitHub Actions 失败通知（Settings → Notifications → Actions）。理由：14 连红的**真正元凶**是「CI 红了没人看」，pre-commit 解决的是「下次能提前发现」，但若 CI 持续无人值守，问题只会换形式复发。

## 6. CI 失败通知链路（同日追加）

### 6.1 动因

CI 转绿后仍需回答一个问题：**下次红了，谁会发现？** 09-15~09-18 的 14 连红本质是"无人值守"。

个人通知偏好（Settings → Notifications → Actions）**无公开 REST API**——实测 4 个候选端点均 404，`gh` CLI 亦只有读取型 `status`，只能网页操作。为不把该环节留给人工记忆，改用**仓库自洽**的方案：失败即开 Issue，借 GitHub 原生 issue 通知机制（对 watch 者默认开启）达成同等效果，且 open 的 Issue 是**持久可见**信号，不会像邮件被忽略。

### 6.2 实现

| Job | 触发条件 | 行为 |
|---|---|---|
| `notify-on-failure` | `if: failure()` | 开/更新「🔴 主干 CI 失败」Issue；同标题只保留一条（后续失败追加评论，避免刷屏） |
| `close-ci-failure-issue` | `if: success()` | 自动关闭该 Issue |

两 job 均声明 `permissions: issues: write`（避免 GITHUB_TOKEN 默认只读）。

**仓库为 public，失败 Issue 会公开可见** —— 故让 Issue 生命周期严格等于故障持续期：转绿即自动关闭，不留长期红色痕迹。

### 6.3 端到端验证（临时分支真实造失败）

本地静态检查无法证明 `GITHUB_TOKEN` 权限，故在分支 `arch/verify-ci-notify` 注入真实违规（FF-0006）触发：

| 步骤 | 结果 |
|---|---|
| 本地 pre-commit 拦截该违规提交 | ✅ 拦住，精确定位 `client.ts:300`，HEAD 未变动 |
| `--no-verify` 绕过 → push → CI | ✅ `ff-client-ts-no-functions` failure（预期） |
| `notify-on-failure` | ✅ **success** |
| **Issue 是否创建** | ✅ **#2「🔴 主干 CI 失败」OPEN，author=`github-actions`** |
| main run（CI 成功） | ✅ `close-ci-failure-issue` success |

结论：`GITHUB_TOKEN` 的 `issues: write` 权限有效，通知链路真实可用。

### 6.4 ⚠️ 验证中发现并修复的缺陷（本地静态检查无法发现）

首次实现的两个 job **双双失败**，日志为：

```
failed to run git: fatal: not a git repository (or any of the parent directories): .git
```

**根因**：两 job 刻意不 `checkout`（保持轻量），但 `gh` 无法从 `.git` 推断目标仓库，必须显式指定。

**实测复现**（非 git 目录下）：不带 `GH_REPO` → 必失败；带上 → 成功（含 emoji 匹配的 jq 查重表达式亦正常）。

**修复**：两 job 的 env 增加 `GH_REPO`（`0f495f3`）。

**严重性（本报告最重要的一条经验）**：该缺陷**只在「CI 真的失败时」才暴露**——那一刻通知直接丢失，等于回到"红了没人看"的原点。若只做本地静态检查与 YAML 语法验证，会得出"通过"的错误结论。

### 6.5 配套兜底（独立于仓库）

WorkBuddy 定时任务「CI 失败巡检」每日 09:00 检查 main 近 20 次运行，发现失败即主动报告——即使仓库侧通知被忽略，仍有第二条通道。

### 6.6 ⚠️ 上线当日即被用户实报的误报 —— 分支失败被写成「主干」

**现象**：19:37 用户收到「🔴 主干 CI 失败」通知并紧急反馈"主干 CI 严重错误"，但**主干当时全绿**。

**根因**：两个 job **不限定分支**，却统一使用「主干」措辞与固定标题。于是验证分支 `arch/verify-ci-notify` 的失败开出了一条标题为「主干 CI 失败」的 Issue —— 标题与实际分支不符，构成误报。

| Job | 缺陷 | 后果 |
|---|---|---|
| `notify-on-failure` | 分支失败也开「主干 CI 失败」Issue | **误报，错误惊动用户** |
| `close-ci-failure-issue` | 分支成功会关闭该 Issue | 可能**误关主干的真实失败** |

**修复**（`5e22c9c`）：两者均加 `github.ref == 'refs/heads/main'` 限定。主干失败是唯一需要惊动用户的场景；分支失败（`arch/*` 等开发分支）静默处理。

**教训（比 6.4 更值得记）**：**固定文案 + 不加触发范围限定 = 必然误报**。通知类机制必须让「措辞」与「实际触发条件」严格对齐——否则它比没有通知更糟，因为它消耗的是信任：第一次误报之后，真报也会被怀疑。

**清理**：`Issue #2` 标题与正文已改写为 `[已废弃·验证产物]`，保留 `closed` 状态供审计追溯。GitHub REST API **无删除 issue 的端点**（实测 404，与本仓库 admin 权限无关）——删除只能在 Web UI 操作。

## 7. 结论

- **四项治理落地**：ruff patch 级锁定、门禁单一真源、CI 改调同一脚本、pre-commit 本地拦截 —— 全部通过等价性/负向/端到端三类验证。
- **CI 失败通知链路**（notify 开 Issue + close 自动关闭）：端到端实测通过，且**在验证中发现并修复了一处只有真跑才暴露的缺陷**。
- **本地拦截已真实生效**：可拦截违规提交并精确定位行号。
- 全量回归零失败、测试数无变化（1060 passed / 4 skipped）。
- 仍建议（非必须）：在 GitHub 网页开启 Actions 失败通知——这是最短路径，但已非唯一路径。
