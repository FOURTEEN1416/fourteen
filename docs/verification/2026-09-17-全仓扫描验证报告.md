## 1. 缺陷清单

### 1.1 路径与配置正确性（CWD 依赖类，12 处）

**共同成因**：以 `Path("config/...")` / `Path("data/...")` 形式声明模块级常量或默认参数。Python 相对路径以**进程 CWD** 为基准，而本项目的启动方式多样（`python main.py`、`uvicorn api.run_api:app`、systemd `WorkingDirectory=/opt/ai-girlfriend`、pytest、脚本），并非都从仓库根启动。

**共同影响范围**：从非仓库根启动时，读操作**静默返回空/默认值**（不报错），写操作**在错误位置新建文件**。表现为「配置改了没生效」「开关打开无效」「历史数据查不到」等无告警故障。

**修复思路**：新增 `utils/project_paths.py` 作为唯一真源：

```python
PROJECT_ROOT: Path = Path(__file__).resolve().parent.parent

def project_path(*parts: str) -> Path: ...        # 拼接到项目根
def resolve_project_path(path) -> Path: ...       # 绝对路径原样返回，相对路径锚定项目根
```

> **设计取舍**：锚定 `PROJECT_ROOT` 而非「启动时冻结 CWD」。后者仍是隐式全局状态，多入口场景下不可靠；前者让路径与进程状态解耦。副作用是**依赖 `chdir` 的测试会失效**——因此所有受影响测试改为显式注入路径（见 §3）。

### 3.1 修复一处**时间相关假失败**（D29，非本次改动引入）

`tests/test_persona_binding_fixes.py::test_scheduler_deliver_in_plain_thread` 在第二轮跑测中失败：

```
AssertionError: assert 'hello-proactive' in []
```

**成因**：该用例构造**真实** `ProactiveScheduler()`，而 `__init__` 会读
`data/scheduler_config.json` —— 该文件的免打扰时段被用户在控制台设成了 **22–08**。
`_send_to_all()` 开头就有免打扰门禁，于是：

| 跑测时刻（本地） | 是否落在免打扰 | 结果 |
|---|---|---|
| 21:25 / 21:34 / 21:44 / 21:50 | 否 | **PASS**（首轮四次跑测） |
| 22:09 / 22:11 | 是 | **FAIL** |

**证明**（直接复现，隔离 vs 不隔离）：

```
不隔离（旧测试行为）: quiet_hours=(22, 8) 当前是否免打扰=True  → sent=[]
隔离（修复后）      : quiet_hours=(23, 7) 当前是否免打扰=False → sent=['hello']
```

**结论**：这是**存量**的时间相关假失败 —— 白天跑全绿、晚上 22:00 后必红，与本次任何改动无关。
只是恰好在本批次跨越了 22:00 边界才暴露。

**修复思路**：与同文件姊妹用例一致，在构造前隔离配置真源：
`monkeypatch.setattr(ProactiveScheduler, "_CONFIG_PATH", tmp_path / "sched.json")`。

**最终落地（23:40 收尾加固）**：仅上层隔离不够——构造默认 `_quiet_hours=(23,7)` 在 **23:00–07:00** 之间运行仍会触发门禁（当晚 23:40 复跑即踩中）。故再加第二层 `monkeypatch.setattr(sched, "_is_quiet_hours", lambda: False)`，使该用例与挂钟时间彻底解耦。

**影响面清点**：全仓构造 `ProactiveScheduler(` 的用例共 9 处，其中
`test_persona_binding_fixes.py` 的 4 处已隔离/免疫（2 处显式 monkeypatch、1 处只断言
`assert True`）、`test_proactive.py` 的 3 处只断言构造属性不触发投递 —— **仅此 1 处受影响**。
