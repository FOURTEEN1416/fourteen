## 1. 根因（按任务书缺陷编号）

生产为 4 uvicorn worker，而**调度主 / 微信连接器 / WS 端口三者各自独立选主、互不知情**，
叠加「状态只在本进程内存」的写法，形成一族「**同一件事在四个进程里有四种说法**」的缺陷。

| 缺陷 | 一句话根因 | 真因位置（修复前） |
|---|---|---|
| **A** 投递平面 | 调度主、连接器宿主、WS 持有者可能分居 A/B/C/D 三个 worker，A 的本地 registry/holder 恒空 → 主动消息与提醒判「通道不可用」→ 3 次判死；且没有任何进程能回答「后台运行时到底活没活」 | `api/run_api.py` 本地 registry 判全局；`proactive/scheduler.py` 无跨进程存活面 |
| **B** 断连/停用 | `disconnect` / 停用只是进程内 `dict.pop`，别的 worker 的 poller 照跑、`restore_on_boot` 照凭证复活 | `wechat_direct/connector_registry.py`、`wechat_connector.py` 轮询循环 |
| **C** 投递归属 | run_api 的微信 sender 对同 owner 的**全部 slot 逐一发送且不 break**；未点名 slot 的行可被任一 slot 消费 | `api/run_api.py` 出站分支 |
| **D** 状态不同源 | `paused` 存引擎内存 + 网页配置各说各话；`ase_hub` 缓存命中不看盘上版本；`ASEEngine.save_state` **全量快照覆写**会抹掉另一 worker 刚写下的用户互动；`utils/json_state.atomic_write_json` 无锁 + 固定 `.tmp` 名并发互踩 | `proactive/ase_hub.py:119-127`、`ase_engine.py`、`utils/json_state.py` |
| **E** 手动测试走旁路 | 取 hub「最近一个」引擎 + `_send_to_all` 广播 + `create_task` 一建立即 `delivered=True` + 发送**前**写 `sent_history`（自测吃掉当日配额，生产 09-18 实锤全天停发） | `api/routers/training_routes.py` 主动控制段 |
| **F** 提醒生命周期 | `reminders` 表只有「设」和「查待发」两条路：无取消、无改期、判死后 `active=0` 被 pending 视图的 WHERE 挡掉查不到、无恢复入口 | `shisi/memory/legacy/structured_memory.py` |
| **G** 入口装配分叉 | `main.py` 与 `run_api` 各抄一遍装配，main 抄漏 `register_reminder_task` 与 `set_llm_provider`，并把 `_send` 覆盖成**不记账的跨用户广播** | `main.py` |
| **H** 知识/热点旁路 | 知识只在被旁路的旧 ASE 生成线拼装，**当前 LLM 主动决策链从不读**；装配层注入的 resolver 不带 user_manager，且角色只在引擎创建时快照 | `proactive/llm_proactive.py`、`orchestrator/_init_mixin.py` |
| **I** 入站幂等 | `message_id` 幂等账只挡「整回合重放」，回合**内部**的工具副作用（`set_reminder`）在 release 后重放、终审补跑、双 worker 重复投递时各写一行 → 用户被叫两次 | `tools/builtin/reminder_tool.py` |
| **J** 节流状态 | LLM 自判的 `wait_minutes` 只进内存字典（重启归零，在她明确说「X 分钟后再说」的窗内提前开口）；追问日预算同族；退避账本此前已修、成功侧漏修 | `proactive/scheduler.py` |

**共同机制**（本窗的公共底座）：用一块 SQLite（`data/runtime_plane.db`，WAL + 单语句 CAS）
把「谁活着 / 期望态 / 出站命令与受理回执 / 入站幂等 / 追问预算 / 副作用幂等」变成**跨进程可见的持久事实**，
不引入消息栈。控制面不可用即**明确失败**（不静默降级为广播、不假成功）。

## 6. 未验证风险（登记，不粉饰）

1. **真实四进程 / Linux 拓扑未实测**（§4 表末列已标层级）。跨进程唯一性靠共享 SQLite CAS + 线程级真实竞态证明；进程间差异仅剩 WAL 读写不互阻的既有前提与 flock 语义。
2. **调度器 takeover 仍缺**：若 master 进程活着但其 APScheduler 线程死掉，本窗只做到「**可见**」（`runtime_beat` 过期 ⇒ `/api/proactive/state` 与 `/api/ready` 显示 `beat_alive=false` 且不再续租），**不会自动接管**——接管意味着双调度器并存风险，判据未裁。
3. **web/console 回合不带 `message_id`**：缺陷 I 的副作用幂等对微信入站生效，网页与控制台回合按设计不去重（无入站身份可锚）。
4. **两条拓扑对「通道一直缺席」的容忍度不一致**（D 类未裁决，见 `proactive/reminder_delivery.py:38-51`）：本机直发路径跳过记账，控制面路径的「30s 无宿主受理」仍按未送达计一次失败。
